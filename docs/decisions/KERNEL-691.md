**A started teammate's wait ends only once its branch contains the merged base.** When Kernel sends the rebase message, it fetches and saves `<remote>/<base>` on the wait as `tip`. When the turn Kernel started ends, `git merge-base --is-ancestor <tip> refs/heads/<branch>` decides. The check reads the workspace's branch, not HEAD as the issue said: a rebase stopped on a conflict leaves HEAD detached on top of the base, so HEAD would pass while the branch never moved. When the tip is missing, the wait stays without `releasing` and keeps its `tip`, and the Lead gets `wait.rebase_missing`. That kept wait ends at the end of any later turn in the PR chat whose branch has the tip, so the Lead's message_agent is enough. `wait_for_merge` with an empty list ends it without asking again, where any other started wait with its targets merged would send the rebase message once more. A restart sends the rebase message again, as it does for every merged wait. A wait saved before this change has no tip and ends as it did, and so does one where git can't tell. KERNEL-691
