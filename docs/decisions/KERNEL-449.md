**Values the user writes can use Kernel's own variables as `${KERNEL_*}`, and nothing else expands.** `buildEnv` fills in `${KERNEL_PORT}`, `${KERNEL_WORKSPACE_SLUG}` and the rest of `KERNEL_VARS` in values from app variables, env files, room variables and setup's `$KERNEL_ENV`. Only the braced form counts, and only Kernel's names. `$KERNEL_PORT`, `${HOME}`, an unknown `${KERNEL_X}`, `$(...)` and backticks stay as written. That way a value can't read the Mac's environment or run a command, and a setup script that writes a literal `${KERNEL_WORKSPACE_SLUG}` gets the same answer as one that lets the shell expand it. The Mac's own environment is left alone. KERNEL-449.

**`KERNEL_WORKSPACE_SLUG` comes from the workspace id alone.** It is `kernel_` and the first 12 letters and digits of the id, in lowercase, so it is at most 19 characters and works as a Postgres or MySQL database name and as a Docker Compose project name. Setup creates the database once, so the name must hold for the workspace's whole life. A chat with Rowan renames its branch, its name and its worktree folder after setup ran (KERNEL-424), so neither the name nor the folder would do. The id never changes. `\l` in psql lists names that only match a workspace through its id, and that is the price. KERNEL-449.

**Each worktree workspace gets `COMPOSE_PROJECT_NAME`, unless anything the user controls sets it.** Kernel puts it in a defaults layer under the Mac's environment, so the Mac, app variables, env files, room variables and setup all win over it. A current-branch workspace gets none. It runs in the room's own checkout, and Compose's default there is the project the user's own terminal already uses, so Kernel's agents see the containers the developer started. A compose file's `container_name:` and fixed host ports still collide, and Kernel can't change those. `$KERNEL_PORT` is the answer for ports. KERNEL-449.

**The agent's environment comes from the room's `[env] files` list, and when no settings file sets that key, from `.env.kernel` in the room's checkout.** This is CJ's open decision 1 from the "Kernel for other users" plan. `[env] files` already existed (KERNEL-247). The `.env.kernel` fallback is new. It is the user's file for agents, kept next to the `.env` they use themselves, and `${KERNEL_*}` makes one file give each workspace its own database. It is read from the checkout, not copied, so it works for every workspace without being in files.copy, and an edit counts for the next process started. Setting `[env] files`, even to `[]`, turns the fallback off. Copying `.env` keeps working as before, and the settings file Kernel writes still copies `.env` and `.env.local`. The list replaces copying only when the user chooses it. KERNEL-449.

**`.env.kernel` counts only while git doesn't track it.** A file in the environment can set `BASH_ENV`, `ZDOTDIR` or `PATH` and run repo code in every shell, which is why a repo's `[env] files` waits for trust (KERNEL-247). An untracked `.env.kernel` is the user's own, the same as their personal settings file. A tracked one may have come from anyone's commit, so the fallback skips it, and a repo that wants to share one lists it in `[env] files`, which goes through trust like any env file list. `envFor` is synchronous, so it keeps the file's stamp (inode, size, mtime) per room and asks `git ls-files` again, synchronously with a 3 second limit, only when the stamp changes. A `git pull` can't turn an untracked file into a tracked one without the user removing it first, and a removed file clears the stamp. The page that lists env files shows `.env.kernel` only when it is read. KERNEL-449.

**A file to copy looks like production when it holds a live payment key, a database URL on another host, or an environment name set to production.** Only env files are read: a name that starts or ends with `.env`, up to 1 MB. A live key is a Stripe secret or restricted key (`sk_live_`, `rk_live_`). A publishable `pk_live_` key isn't, because it is public. A database URL is any `postgres`, `mysql`, `mariadb`, `mongodb`, `redis`, `sqlserver`, `cockroachdb`, `libsql` or `prisma` URL, with `jdbc:` allowed in front, whose host isn't local. A password may hold `/`, `?` or `#` unescaped, so the host is read both up to the first of those and after the last `@`, and either one being remote counts. Local means loopback, a private or link-local address, `.local`, `.localhost`, `host.docker.internal`, or a one-word name like a Compose service's `db`. A Neon or Supabase branch made for development still warns, because from a worktree it is as reachable as production, and the copy says "a remote database", not "production". The environment names are `ENV`, `ENVIRONMENT` and anything ending in `_ENV` or `_ENVIRONMENT`, set to `production`, `prod` or `live`. Each file shows its strongest variable: live key first, then remote database, then the environment name. KERNEL-449.

**The warning names files and variables, and no value leaves the main process.** `files.production` returns the path, the variable's name and the reason. Tests check that hosts, passwords and keys from the file never appear in the answer. KERNEL-449.

**Don't copy these files adds the paths to `[files] exclude` in the personal settings file. Keep copying remembers the files on the room, with the variables they hold now.** `exclude` takes exact paths and patterns, applies after files.copy resolves, and needs no trust, because it only copies less. It goes in the personal file without touching `files.copy`, so a shared copy list keeps coming from `settings.toml`. Files to copy doesn't show the exclusions yet, because the drawing has no place for them. They are lines in `settings.local.toml`. Keep copying covers each file whole, though the banner names one variable per file: it stores `<path>:<NAME>` for every variable in that file that looks like production at the time, in `Room.keepCopying`, in Kernel's data. A variable added later still warns, so a new live key in a kept file shows again. Room setup's Copy local files step warns with the same files and links to Files to copy. The warning doesn't wait for trust, because it reads files and runs nothing. A warning stops Brief Rowan right away, so the user sees it before Rowan starts. This settles what KERNEL-437 left to B7: what counts as production. KERNEL-449.
