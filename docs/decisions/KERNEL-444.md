**The default Always ask list names no one stack's commands.** It used to hold `drizzle-kit push` and `pnpm db:reset`, two commands from the stack Kernel was built on. Now it holds `rm -rf` and `git push --force`. settings.json is sparse (KERNEL-225), so a file that never changed the list follows the new default and loses the two entries on upgrade. That is the intent, and the release note says so and names Settings, Permissions as the place to add them back. A list the user saved stays as saved. A file from before KERNEL-225 saved the old list on every launch, and since that list no longer equals the default, it reads as the user's own and stays too. Nothing marks it unset, because guessing wrong would take commands off a list that guards against them. KERNEL-444.

**A new room's install and run example come from every stack the repo uses.** Amends D-078. `lockfileInstall` reads the root of the checkout for each language Kernel knows and takes the first match in each. Python picks uv (`uv.lock`), then Poetry (`poetry.lock`), then pip (`requirements.txt`). Ruby uses a `Gemfile`, Elixir `mix.exs`, PHP `composer.json`, Rust `Cargo.toml` and Go `go.mod`. JS keeps D-078's order: pnpm, yarn, bun, npm, then a bare `package.json`. A repo with more than one stack gets one install per language, joined with `&&`. JS comes last, as in the setup scripts Rails and Laravel ship, so a Rails app with a JS bundle runs `bundle install && yarn install`. The commented run example in the settings.toml Kernel writes is the first stack's, so that Rails app shows `bin/rails server`, not `yarn dev`. The examples are guesses a user edits, and each passes `$KERNEL_PORT`.

pip gets `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`, not a bare `pip install`. A bare one installs into whichever Python comes first on the PATH, Homebrew's Python refuses it (PEP 668), and workspaces would share one set of packages. Rust gets `cargo fetch`, which downloads the dependencies without building, and Go gets `go mod download`.

Room setup's Install step skips a stack whose install left its folder in the checkout: `node_modules`, `.venv` for uv and pip, `deps` for Mix and `vendor` for Composer. Bundler, Poetry, Cargo and Go install outside the checkout, so their install runs every time. That is harmless, since a second run of any of them changes nothing. KERNEL-444.

**An install that runs the repo's own code waits for trust, like package.json's install scripts.** Amends KERNEL-260. `bundle install` evaluates the Gemfile, which is Ruby. `mix deps.get` evaluates `mix.exs`, Composer runs `composer.json`'s scripts, uv, Poetry and pip build the project itself, and rustup reads `rust-toolchain.toml`, which can name a toolchain inside the repo. Running any of them in a fresh clone runs the repo's code before anything asked, which is the hole KERNEL-260 closed for JS. `go mod download` runs nothing from the repo, so Go is the one new stack that doesn't wait.

So for those stacks, the settings.toml Kernel writes is not trusted on its own, and the first workspace waits in `trust`. The dialog shows the setup script, such as `bundle install`. The Install step ends with "Skipped until you trust this repo's scripts", and trusting runs it in the background, as KERNEL-260 does. A repo whose own settings.toml has nothing to trust never brings up the dialog, so holding its install would hold it for good. There the step ends with "Skipped: bundle install runs this repo's code, so run it yourself if you trust it". Kernel doesn't run it.

package.json's install scripts join the trust subject only when a JS install is still to run (`runsPackageInstall` on the Install step's command). Before this, any pending install counted, and a `bundle install` that runs every time would have kept them in for good. KERNEL-444.
