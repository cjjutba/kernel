**Kernel owns dependencies between tasks.** Kai built KERNEL-198 on top of KERNEL-197 and ended a turn saying it would wait for PR #164. CJ merged #164 and nobody moved. The merge wasn't the last one Rowan's chat had handed off, so it didn't wake Rowan (D-116), and the dependency lived only in chat text. Now a workspace can carry a saved `waitsFor` record. Rowan sets it with `wait_for` on `create_workspace`, or later with `wait_for_merge`, which also ends a wait when given an empty list.

A hand-off that waits still creates the worktree and runs setup right away, so a broken setup shows now and not hours later. Then Kernel holds the brief and marks the workspace ready, in that order. The Lead's messages queue behind the brief, there is no start checkpoint, no run script and no turn, and the chat says what it waits for. When every PR it waits for has merged, Kernel fetches origin and fast-forwards the branch onto `origin/<base>`, even when the workspace started from the local base, which a merge on GitHub doesn't move. It only fast-forwards, and only on a clean tracked tree. Otherwise the brief goes out with a Kernel message after it asking for a rebase. Setup runs again only if HEAD moved, the start checkpoint is taken at the new HEAD, and the wait clears in the same tick as the brief goes out. A teammate that started before the merge gets Kernel's rebase message instead, posted to an idle chat or queued behind a busy one. `waitsFor.releasing` stays saved until a turn Kernel started there ends, because a queue doesn't survive a quit.

A target counts as merged only when its `prState` is `merged`. `mergedAt` doesn't count, because Continue keeps it from the PR before. Release happens in Kernel's own PR push handler, in a sweep at start that catches a merge saved just before a quit, and on the PR poll. It doesn't happen in LeadUpdates, which drops events while Lead updates are off. A target that closes or is archived without merging leaves the waiter as it is and wakes the Lead once, unless the PR reopens before the update goes out. Send now on a held brief starts it without waiting. Archiving a waiter, or its own PR merging or closing, ends its wait. `archive_workspace` treats a held waiter as idle.

Amends D-116: a merge that releases a wait rides along like any merge that isn't the last, and a broken wait wakes the Lead. Amends D-122: a Run again that passes while the wait still stands says the teammate still waits, and the brief stays held. Amends KERNEL-136's invariant: for a workspace that waits, ready no longer means the brief went out, and `Sessions.restore` holds a ready waiter's brief again after a restart. It doesn't do that for a workspace still in setup, which `recoverSetups` already holds. KERNEL-259.
