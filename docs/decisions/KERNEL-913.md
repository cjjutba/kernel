**A project's setup, run and archive scripts run without asking, the way Conductor runs them.** Amends KERNEL-209, KERNEL-218, KERNEL-247, KERNEL-260, KERNEL-261, KERNEL-327, KERNEL-405, KERNEL-444 and KERNEL-682. The trust gate held the first workspace of every project with committed scripts above the composer until the user read and trusted the scripts. CJ wants setup to start as soon as a workspace exists, with no prompt, banner or held workspace. So Kernel no longer hashes the repo's text, keeps no `trust.json`, and has no `trust` workspace status, `ScriptTrust`, trust banner, Inbox row or modal.

What now runs with no step: the setup script on create and on Run again, the run script after setup and from the Run tab, named run scripts, the archive script on archive (still subject to "Run the archive script on archive"), the project's one-time Install step whatever it installs, the repo's `[env] files`, and what setup writes to `$KERNEL_ENV`.

The accepted risk: a script someone commits, or one that arrives with a pull, runs with the user's rights in the login shell, outside the Bash permission rules that govern agents. Cloning a hostile repo and opening a workspace in it runs that repo's code. The same holds for package install scripts and for an env file that sets ZDOTDIR or BASH_ENV. The reviewer notes any PR that changes a script or files.copy in `.kernel/settings.toml`, quoting the new lines, so a change is at least seen before it merges. That note doesn't block.

What stays: `files.copy` confinement. An entry that leaves the repo, by an absolute path, `..` or a symlink, is refused, and the copy never writes through a link (`services/filesToCopy.ts`, `copyLocalFiles`). The whitelist that reads a script only when it is a string stays too, and so does `localSettingsOwn`, which auto-merge still reads. A `.env.kernel` the repo commits still counts only when `[env] files` lists it (KERNEL-449).

The upgrade: at start, `recoverHeld` in the setup feature takes the place of the trust feature's queue recovery. A workspace saved as `trust` gets its queue held, moves to `setup`, copies its files and runs setup, then sends its brief or fails as a new workspace does. One whose brief also waits for a PR ends ready and still waiting. A workspace in `setup` with no `setups` hold, left by a quit partway through a trust release, is held and failed with the usual note, so Run again sends its brief. Each project in the `heldInstalls` meta installs once in the background and the meta goes, and `trust.json` is deleted from the data folder. KERNEL-913
