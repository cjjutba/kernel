**Plan approvals are the one kind of approval that outlives a quit, a crash and Ctrl+C on `pnpm dev`.** Before this, `expirePending()` at quit and `expireStale()` at launch ended every waiting card. An agent blocked on its plan came back with no card, and a Claude chat in the `working` journal got `RELAUNCH_NUDGE`, so it explored or planned again. The plan itself was never at risk: it is saved in `.kernel/plans/` and on the approval row.

`Sessions.shutdown` calls `Approvals.quitting()` first. From then on a plan whose waiter ends, as the stopping turn aborts it, resolves null and keeps its row pending. `expirePending()` does the same for plans. At launch `expireStale()` keeps a pending plan whose chat is open in a workspace that isn't archived, and expires the rest. Tool, question and agent cards still expire as before (D-137, KERNEL-215, KERNEL-563). Archiving the workspace (`expireWorkspace`) still ends the card, and so does closing its chat, which now ends the chat's waiting plans itself, since no session holds them after a restart.

At launch, a chat in the `working` journal that has a waiting plan gets its running tool rows stopped and the quit note, but no nudge, and it doesn't carry on by itself. When it had messages queued, they still go first through `carryOn`, and the card stays up. A new plan in the same chat, from ExitPlanMode, a Codex plan turn or `request_plan_approval`, expires the older waiting one first.

A card with no live waiter is answered through `approvals.decide` like any other, so the Inbox and the chat card take the same path (`Inbox.answerPlan`). Approve runs `planApproved` (plan mode off, the Lead's hand-off reminder armed, D-059) and queues the note as Kernel's message, with the plan's path and the restart sentence. Request changes queues "Revise the plan in `<file>`: <notes>", with images saved as for a live card (D-134). The revision overwrites the same file through `revisedPlanFile`, unchanged. The message waits in the queue like any other while a pause, the agent limit, offline or a sign-out holds the chat.

**An approved plan sends one note, built in one place (`planApproval` in `handoff.ts`), on every provider.** On a normal approval the agent still has its plan in context, so the note is short and names no file: "Plan approved." for a Claude teammate, the same line followed by `HANDOFF_NOW` for the Lead, and "Plan approved. Carry it out." for Codex, whose note is a message that starts a turn. The chat shows "Plan approved." Before this, Claude got only the tool's allow, Codex got `PLAN_APPROVED` and the Lead got `HANDOFF_NOW`.

The path is named only after a restart, because the turn that planned was cut off and the agent may not have the plan in front of it. Then a teammate reads "Plan approved. Build it from `.kernel/plans/<name>.md`." and the Lead "Plan approved. Hand off each task from `.kernel/plans/<name>.md` now." followed by `HANDOFF_NOW`, and both end with "Kernel restarted while the plan waited, so check git status before you start." When the file is missing, the plan's text from the approval stands in for the path.

How the note travels depends on whether a turn is waiting on the answer, so an approval never starts a second turn. A Claude agent still blocked on ExitPlanMode reads it as `PostToolUse` `additionalContext`, now for every agent and not only the Lead. The Lead's `request_plan_approval` returns it as the tool's result. Codex, whose plan waits after its turn ended, and any approval after a restart get it as a queued message from Kernel. That replaces `PLAN_APPROVED`. In the first two cases the chat shows the note's line as a `note` item. In the queued case the message itself, drawn as a note, is the one note.

Amends KERNEL-215 and KERNEL-563.
