**Team flags an agent whose file pins a model no signed-in provider offers.** An agent file's `model:` pins the agent to that model on its provider (KERNEL-406). When the user isn't signed in to a provider that offers it, the agent's chats can't run on it, and Team said nothing. Now the agent gets a `model-unavailable` warning, which Team, the agent's profile and Room setup show as "Pins a model you're not signed in for." Kernel places the pin the way `rolePick` does, so `inherit`, an id Kernel can't place and a file with no `model:` line pin nothing and get no warning. Claude offers `MODELS`, matched by id or alias, so a Claude id outside that list (`claude-sonnet-3-7`) warns even while Claude is signed in. Codex offers what its `model/list` returns for the active account. `Team.flagPins` in `features/team.ts` adds the warning after `resolveTeam`, which stays pure, because only the features know who is signed in. Every team read asks again, so signing in clears the warning on the next read, and only the providers the pins name are asked, so a team without a pin starts neither CLI. When Kernel can't tell (the sign-in check throws, or Codex's list can't be read) it flags nothing. The check runs only on a Kernel built with `checkPins`, which the app passes and tests leave out, so no test starts Claude Code or Codex by reading a team. Signing in doesn't push a new team by itself. The warning goes on the next read: opening the room, or any change to the team. KERNEL-550.

**Kernel's safety rules hold through tools whatever an agent file says, and its workflow rules come after the agent's own text.** An agent file is instructions to a model, and Kernel doesn't rewrite or filter it. Instead the rules that keep the user safe are checked on every step, outside the model. Protected branches, Never allow and Network off are decided by `decide` and `hookVerdict` in `services/permissions.ts`, with `guardVerdict` and `bashVerdict` (`services/bashGuard.ts`) reading each command. Claude chats ask them in `canUseTool` and the PreToolUse hooks (`services/providers/claude.ts`). Codex chats run under `approvalPolicy: 'untrusted'`, so every command Codex doesn't trust reaches `decide` in `services/providers/codex/runner.ts`, and the turn's sandbox takes its network access from Settings, Permissions. No direct push to main follows from the same check: `main` is a protected branch and `git push origin main` is on Never allow by default, and a push that might reach a protected branch is denied even in Bypass permissions (KERNEL-447). An agent file can only narrow what its chats may do. Its `tools:` and `disallowedTools:` take tools away, and its `permissionMode:` can only make the chat's mode stricter (`effectiveMode`, KERNEL-432). Kernel's workflow rules are prompt text, not checks. `agentPrompt` in `services/sessions.ts` joins the agent's own prompt first, then the Lead's rule, the rule `rulesFor` in `features/tools.ts` picks (teammate, reviewer, sharing, auto review), the worktree and the port. Claude Code gets that text appended to its own preset prompt, and Codex gets it as developer instructions. So the agent's text comes first and Kernel's workflow comes after it, as it always has, and a file that tells its agent to work differently is read with Kernel's workflow after it. Room setup's instruction conflicts (KERNEL-452) read the repo's CLAUDE.md and AGENTS.md files, not agent files. KERNEL-550.
