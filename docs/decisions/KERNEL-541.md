**Bypass permissions on Claude runs `pnpm shots` and `node design/canvas/source/render.mjs` outside the sandbox.** Amends KERNEL-458. Electron and Chromium register a Mach service when they start, and Chromium treats a refused registration as fatal: `FATAL:base/apple/mach_port_rendezvous_mac.cc:159 Check failed ... bootstrap_check_in com.github.Electron.MachPortRendezvousServer.<pid>: Permission denied (1100)`. Registering is the sandbox's `mach-register` operation. The profile Claude Code 2.1.292 builds never allows it, under any setting. `network.allowMachLookup` only writes `(allow mach-lookup (global-name ...))` rules, which let a command look a service up but not register one, so the issue's first option can't fix this. Chrome hits a second wall in the same sandbox, binding its `SingletonSocket` in the temp folder, so render.mjs would still fail even with a registration rule. That leaves `excludedCommands`, set to `pnpm shots:*` and `node design/canvas/source/render.mjs:*`. Claude Code takes exclusions from the SDK's `--settings`, so `allowUnsandboxedCommands: false` keeps them, and it excludes a command only when every part of it matches: `pnpm shots Settings && curl example.com` runs sandboxed. `pnpm shots:compare` only joins two PNGs and runs fine in the sandbox, so it isn't excluded. `allowAppleEvents` stays off, and the write and network rules are unchanged. The list applies in every room. `test/live.sandbox.test.ts` checks it with Claude in Bypass. KERNEL-541.

**The exclusion lets an agent in Bypass permissions run any code outside the sandbox, if it sets out to.** The sandbox lets commands write the worktree, and the excluded commands run the worktree's own files: the `shots` script in package.json, `scripts/shots.ts`, the Electron build in `out/` and render.mjs itself. An agent that edits one of them and then runs the command gets the user's full rights, with no write limits, no domain allowlist and, in Bypass, no prompt. Any repo with a `shots` script works the same way. Claude Code documents `excludedCommands` as a convenience, not a security boundary. What still holds: Kernel's hooks and canUseTool see the command first, so Never allow rules and protected pushes apply, and in plan mode or the stricter mode a switch out of Bypass leaves the process in, the command asks like any other. Every other command stays in the sandbox. Closing the gap needs either a Mach registration setting Claude Code doesn't offer, or a launcher Kernel ships outside the worktree that runs Electron and Chrome under a profile of its own. Neither is part of this change. KERNEL-541.
