**A worktree workspace still starts when fetching origin fails, and Kernel says so in the activity log, the workspace chat and the Lead's `create_workspace` result.** D-053 fetched origin before resolving an `origin/` base, but nothing read the result, so offline or after the 30 second timeout a workspace quietly started from whatever `origin/main` was last fetched. `createWorkspace` now calls `fetchOrigin` (`services/worktrees.ts`) itself and then `resolveBaseRef` without `fetch`. When the fetch fails, the workspace starts anyway. Failing Create would block all work offline, and the stale base is usually close enough. Kernel then tells everyone how stale it is. The workspace stores the reason in `fetchFailed`. The activity log gets one warn line with git's first line of stderr, or "timed out after 30 seconds". The chat gets a note that it may be missing recent merges, and `create_workspace` adds the same sentence after its `Created <id> on` prefix. The time comes from `FETCH_HEAD`'s mtime. Git empties `FETCH_HEAD` as soon as a fetch starts, even one that fails, so `fetchOrigin` reads the time before it fetches and ignores an empty file. After a fresh clone, or a second failure in a row, the time reads "its last fetch". A folder with no `origin` remote skips the fetch and the warning, since there is nothing to fetch (KERNEL-62). A review workspace's base (`reviewBase`) still fetches through `resolveBaseRef` and says nothing. A fetch that succeeds adds nothing anywhere. Amends D-053. KERNEL-179.
