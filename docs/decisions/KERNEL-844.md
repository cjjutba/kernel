**A long chat's move is decided as its turn starts, not when the switch happens.** Sessions asks `Moves.plan` each time a turn is about to run on another account than the chat's last. Two quick switches therefore move a chat once, to where it goes last. A summary done for a move is kept by (chat, target account) until the next turn starts, and a turn with another target drops it and decides again. Kernel never summarizes during a turn: a summary already running when a switch lands finishes, and the chat moves on from there. KERNEL-844.

**The order of rules for a long chat that moves.** A chat that doesn't fit the target model's window is summarized. Then the chat's own choice (`chats.moveChoice`) applies, once. A chat under Settings, Account "Long chat" continues. A move onto an API key account asks, whatever the policy, since the key pays for every token. Then the provider's policy: Summarize first, Continue or Ask. Keep is the one choice that outlives a turn: the chat stays on the account it last ran on, past a Move all switch and the move threshold, until that account can't run it (signed out, limited, gone). Summarize and Continue choices end when the next turn starts, moved or not, so an old choice never answers a later move. KERNEL-844.

**A summary runs on the old account when that account can still run the chat and its cache there is warm, else on the new one.** On the old account the summary reads from the cache, and the move then reads only the summary. Cold or limited, the old account saves nothing, so the summary runs on the new account and is the chat's move: it reads the chat once there, and later turns read the summary. Claude gets `/compact` with instructions to keep the task, files, decisions and open questions. Codex's `thread/compact/start` takes no instructions. Codex runs a compaction as a turn of its own, so the runner waits for that turn to end before the chat's next one starts. KERNEL-844.

**Ask holds the chat with the queue reason `move`, and one Inbox item per room lists what waits.** What the user sends meanwhile waits behind it. A switch that takes the chat's target away lets the hold go and decides again. A held chat a limit cut off carries on once the user chooses. KERNEL-844.

**A turn too long for the model is summarized in the same process and sent again, once.** Claude says so with `terminal_reason: 'prompt_too_long'`, Codex with `contextWindowExceeded`. This applies to every turn, not only one after a move. A second refusal ends the turn as it came. KERNEL-844.

**Ahead of the limit, Kernel switches with Keep.** With Settings, Account "switch at a limit" on and chats kept on their account, the account in use crossing the move threshold (5 hour 90%, weekly 95%) switches the provider to the account `spareFor` picks, once per crossing. Chats on the old account move at their next turn, since it fails the threshold. Its idle long chats with a warm cache are summarized there first, one at a time, largest first, only while the policy is Summarize first. The Lead's chats are left out so the Lead can always answer. The switch reports as `reason: 'limit'`, the only automatic reason the contract has. KERNEL-844.

**Kernel stops switching by itself when an account it switched to fills within 30 minutes.** "Fills" means a rejection, or crossing the move threshold. Kernel doesn't switch that provider by itself again, one Inbox item says why, and the rooms wait for the limit as with the switch off. Any switch the user makes, from Settings, the banner or Undo, lets Kernel switch by itself again. KERNEL-844.

**Cold re-reads start two at a time, smallest first.** A turn counts as cold when it runs on another account or model than the chat's last turn (`coldSize`). One only idle past the cache lifetime doesn't count: it would re-read wherever it ran, and holding it would slow ordinary work. The Lead's chats neither wait nor take one of the two, as with the agent limit (D-094). Only Kernel's own messages and carry-ons wait for one, under the queue reason `moving`, which is not the agent limit's `capacity`. A message from the user or the Lead goes at once, whatever else is re-reading. KERNEL-844, KERNEL-1032.

**Each switch Kernel makes by itself posts one Inbox item** naming the account it left and why, and the long chats that move with what the policy does to them. KERNEL-844.
