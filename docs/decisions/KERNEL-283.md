**A PR GitHub is still checking for conflicts is never ready.** Each time the base branch moves, GitHub reports `mergeable: UNKNOWN` until it has worked out again whether the PR conflicts. `prStateOf` reads that as `checks` where it would have said `ready`, and `PrInfo.conflictsUnknown` marks the read. Only the conflict question is open, so the rest of the read stands: failing checks still read `cifail` and requested changes still read `changes`. A PR that was in `conflict` stays there until GitHub settles, so it can't flip to another state and back in a few seconds. KERNEL-283.

**One quick read follows an unknown one, on one shared timer.** After an unknown read, Kernel queues that PR, and one timer reads every queued PR 15 seconds after the first one joined. A merge makes GitHub check every other PR again, so a timer per PR would start a burst of them at once (from KERNEL-298). Each PR gets one quick read. If GitHub still hasn't settled by then, the 45 second poll takes over until a settled read clears it, so a slow PR doesn't cost a `gh` call every 15 seconds. Archive takes a PR off the queue, and stop drops the timer. KERNEL-283.

**Ready again on the same commit isn't news to the Lead.** A ready PR now reads as checks for a moment each time main moves, then ready again. Once an update has told the Lead a PR is ready, a return to ready from checks on the same head commit adds no `pr.ready` event, so it neither wakes the Lead nor rides along. Any other state in between, or a new commit, makes the next ready news again. This also quiets a manual rerun of checks that pass again, which `collapse` already treats as old news while the update waits. Kernel keeps what it told the Lead in memory only, so the first such flip after a restart can still repeat once. Amends D-115 and D-116. KERNEL-283.

**A ready PR alerts once per head commit.** The same flip made `Notifications` settle the "PR #N is ready to merge" row, save a new one that needs the user, and alert the Mac, for every open ready PR on every merge into main. Ready again from checks on the head commit its row was made for now adds no row and no alert. Any other state in between, or a new commit, makes the next ready a new row again. At start, a ready PR that already has a merge row counts as told about its current head, so a restart doesn't alert again either. KERNEL-283.

**The loop guard starts over once per ready head commit.** The flip read as the PR becoming ready, so `Nudges` started over on every main move, and the three automatic requests per workspace stopped meaning anything while main kept moving. The guard now remembers the head commit it last started over on for a ready PR. Ready again from checks on that commit doesn't start it over. Ready on a new commit does, and so does ready after any other state, such as a conflict or failed checks. A manual rerun of checks that pass again on the same commit no longer starts it over either. Amends D-124 and D-129. KERNEL-283.
