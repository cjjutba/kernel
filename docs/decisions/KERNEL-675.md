**The installed app and Kernel Dev run at the same time.** Replaces the "One Kernel at a time" half of KERNEL-408. Opening one build while the other ran used to show "Kernel Dev is open. Quit it, then open Kernel again." and quit. That refusal is gone. The single-instance lock per data folder stays (KERNEL-208), so two copies of the same build still hand over. Kernel Dev's first launch still won't move the data while the installed app holds `Kernel`, because the move must not copy a database that is open. That one case keeps a dialog, and the next launch moves. Kernel Dev logs to `~/Library/Logs/Kernel Dev`. KERNEL-675.

**Each build has its own hook token, port and entries, told apart by the URL path.** The installed app posts to `/hooks` on 7420 and Kernel Dev to `/hooks/dev` on 7430. The path is the tag because releases from before this change match their own entries with a pattern that ends at `/hooks`, so they leave Kernel Dev's alone while the installed app catches up. A header or a comment in the command would have matched, and an old installed app would have deleted Kernel Dev's entries at every start. Entries from before this change post to `/hooks`, so they count as the installed app's. The move no longer copies `hook-token`. A Kernel Dev that still has the installed app's token removes its copy at launch and makes a new one. On that launch, or right after a move, Kernel Dev installs its own set next to the installed app's when those are there, since they were the hooks both builds ran on. Every other start still only rewrites entries that are there (KERNEL-206). A Kernel Dev `settings.json` that says 7420 came from the installed app, so it loads as 7430. 7430 is ten ports away, so the installed app moving to the next free port never lands on it. KERNEL-675.

**A session one build started never shows in the other.** Kernel's own Claude sessions load the user's settings (`settingSources` includes `user`), so they run both builds' curl entries. `isManaged` only knows this build's sessions. Every session, terminal and script a Kernel starts now gets `KERNEL_BUILD` (`app` or `dev`) in its environment, and the hook command sends it as `X-Kernel-Build`. A server records nothing for a post that names the other build and answers `{}`, so no approval opens. A post with no build is from outside every Kernel and goes through as before. A `claude` an agent runs by hand inherits the variable, so it reports only to the build that started the agent. Releases from before this change ignore the header, so until the installed app updates, it can still show a session Kernel Dev started in a folder it knows. KERNEL-675.

**Worktrees needed no change.** Both builds default to `~/kernel/worktrees`. Archive, Delete in History, the trash and setup act only on workspaces in their own database. History lists a repo's worktrees only to keep a branch another worktree has checked out, which protects the other build's. A new worktree never takes a folder that exists, and `git worktree prune` drops only records whose folder is gone. The same repo open as a room in both builds is out of scope: a `claude` run by hand there reports to both. KERNEL-675.
