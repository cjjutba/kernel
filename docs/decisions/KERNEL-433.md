**The eight questions, as far as the types, the docs and KERNEL-406 answer them.**

1. *A hook `ask` in `bypassPermissions` doesn't reach `canUseTool`. Bypass approves it.* Reading to confirm live. `sdk.d.ts:1990` says bypass skips "all permission checks", and nothing in the types carves out a hook's ask. The pinned CLI's code that predicts whether a file edit will ask keeps an ask in bypass only when its reason is a rule, a safety check or the mode, and a hook is none of those.
2. *A hook `ask` in `auto` reaches `canUseTool`, but the classifier may get it first.* Reading to confirm live. `decision_reason_type` lists `'hook'` among the reasons "auto-mode escalated" to the host (`sdk.d.ts:4814` to `:4816`), so a hook ask can arrive. Nothing says a hook ask skips the classifier. The pinned CLI's prompt text says it for an ask rule ("Ask rule ... overrides auto mode") but not for a hook ("Hook ... requires confirmation").
3. *`setMcpPermissionModeOverride(server, 'default')` sends that server's calls to `canUseTool` in bypass and in auto.* Per the types and docs. `sdk.d.ts:2870` to `:2885`: "'default' to force per-action prompts", applied "only when the session mode would already auto-allow (bypassPermissions/auto)". It covers a whole server, not one tool, and a name that matches no server only warns.
4. *Ask rules passed through `Options.settings` reach `canUseTool` in auto, and in bypass too.* Auto is per the types and docs: `Options.settings` is the `--settings` flag tier (`sdk.d.ts:2201`), and `matchedAskRule` (`:289`, `:4831`) exists so a host knows "the user's stated intent is a human prompt". The pinned CLI's prompt text for an ask rule in auto says "Ask rule ... overrides auto mode". Bypass is a reading to confirm live: the implementation plan reads the SDK docs as saying ask rules hold in bypass, and the same CLI code keeps a rule's ask there.
5. *AskUserQuestion and plan approval reach `canUseTool` in bypass.* AskUserQuestion is per the types and docs: `requires_user_interaction` (`sdk.d.ts:4844`) marks a tool whose card is the user's answer, so no mode can answer it. Plan approval is a reading to confirm live: a chat with Plan on runs in `plan`, not `bypassPermissions`, and ExitPlanMode asks there. The probe starts in `plan` with `allowDangerouslySkipPermissions`, as a Bypass chat with Plan on would.
6. *`approvalsReviewer: 'auto_review'` with `on-request` decides every approval request, and Kernel can't send an Always ask command to the user.* The first half is per the types and docs. `ApprovalsReviewer` routes "sandbox escapes, blocked network access, MCP approval prompts", and the review's action covers a command, an execve, `writeStdin`, a patch, network access, an MCP tool call and a permissions request (`v2/GuardianApprovalReviewAction.ts`). Kernel hears about a review only through `item/autoApprovalReview/started` and `completed`. A denied action can be approved afterwards with `thread/approveGuardianDeniedAction`, but only after the reviewer said no. The second half is a reading to confirm live. Under `on-request` a command the sandbox allows makes no request at all (question 7), so Always ask would need a `prompt` exec-policy rule, and nothing says whether the reviewer or the user answers one. Codex's own PreToolUse hook can't help: the pinned binary rejects `permissionDecision: ask` and `allow` there and honors only `deny`.
7. *Under `on-request` and `never`, Kernel never sees a command that runs inside the sandbox.* Per the types and docs. Both policies send a request only for an escalation, and KERNEL-406's live run on 0.153.4 saw the same write run in the sandbox and fail under both, with no request. Kernel sees only `item/started` for the command, too late to refuse it. So Never allow, Always ask and room rules can't hold through approvals there, and Codex keeps `untrusted`.
8. *A call to a user MCP server from `~/.codex` reaches Kernel as `mcpServer/elicitation/request`, under `untrusted` and under `granular` with `mcp_elicitations: true`.* Reading to confirm live. The generated `ServerRequest` has no other way to ask about an MCP call, and the pinned binary tags MCP tool approvals with `codex_approval_kind` in the elicitation's `_meta`. Whether Codex asks at all about a tool with no annotations isn't in the types. Today `CodexRunner.requested` answers that method with error -32601, which Codex most likely reads as a decline. KERNEL-433.

**Always ask in Auto on Claude goes through Kernel's own hook (A2) until the live run confirms question 2.** The guard's hook `ask` reaches `canUseTool` in Manual and Accept edits today. In Auto the classifier may answer it first (question 2), and a classifier allow is exactly what the Always ask list exists to prevent. So A3 builds Always ask in Auto on A2: the guard asks the user through Kernel's approvals, waits under the same long matcher timeout as the room-pause hold (`HOLD_TIMEOUT_SEC`), and returns `allow` only on the user's yes. Abort, expiry and no decision return `deny`. That path doesn't depend on how the CLI routes a hook ask in any mode. If the live run confirms question 2 with no `permission_denied` from the classifier, the plain hook `ask` is enough in Auto. The other fallback, the list as `permissions.ask` rules in `Options.settings` (question 4), would need Kernel's patterns rewritten as Claude Code rules and could drift from them, so it isn't the default. In Bypass the guard gives no opinion, as the maintainer decided. KERNEL-433.

**The tools gate (D5) on Claude asks from Kernel's own hook in every mode, bypass included.** The gate hook sees every call, MCP or built-in, in the session and its subagents. In Manual and Accept edits it can return `ask`, the same path Always ask takes today. In Auto and Bypass it uses A2, since a hook `ask` likely goes to the classifier in Auto (question 2) and likely isn't asked at all in Bypass (question 1). `setMcpPermissionModeOverride` (question 3) works for MCP servers in both modes, but only for a whole server and not for built-in tools, so D5 doesn't build on it. Until A2 lands, the gate keeps denying, as it does today. So A2 stays open, as the mechanism behind Kernel's own asks in Auto and Bypass. It closes only if questions 1 and 2 both come back yes. KERNEL-433.

**In Bypass on Claude, what still stops does so through a hook deny or through `canUseTool`, which always asks.** Never allow, network off and a push that might reach a protected branch are hook denies. The SDK lists a PreToolUse deny among the denials that resolve before `canUseTool` runs (`sdk.d.ts:5540`), and the probe "Bypass: a hook deny holds" checks that bypass honors it. The tools line is the gate above. AskUserQuestion and plan approval reach `canUseTool` (question 5). The SDK's critical-path `rm` is a safety check that "requires manual approval" (`classifier_approvable: false`, `sdk.d.ts:4819`) and also arrives at `canUseTool`. No probe covers it, because if the reading were wrong the probe would delete real files. So in Bypass, `canUseTool` treats every call that reaches it as one the CLI insists on asking about, and asks the user. It never auto-allows a call there. KERNEL-433.

**Auto on Codex falls back to Accept edits.** Under `auto_review` the reviewer answers every approval request (question 6), and under `on-request` a command the sandbox allows reaches neither Kernel nor the reviewer (question 7). That leaves Always ask with no path to the user, and Never allow with no hold on sandboxed commands. The maintainer's rule applies: Auto on Codex uses `auto_review` only if Always ask can still reach the user, and until then a Codex chat in Auto runs as Accept edits, and the availability line says Auto isn't available on Codex. Two things could reopen it. A `prompt` exec-policy rule that reaches Kernel under `auto_review` would carry Always ask, and the second question 6 probe checks that. A `forbidden` rule or a Codex PreToolUse deny hook would carry Never allow for sandboxed commands. Neither is built here. KERNEL-433.

**Bypass on Codex keeps `untrusted`, so Kernel sees every command, and accepts whatever Never allow, network off and protected branches let through.** This is the maintainer's call. It rests on question 7 and on KERNEL-406's live run, not on a new reading. In Bypass, a command request is declined for Never allow, a push that might reach a protected branch, or network off with a command that reaches the network. Every other command is accepted, including one that leaves the sandbox. Always ask gives no opinion, as on Claude. File changes accept. A permissions request is granted unless it asks for the network while network is off. Commands Codex runs on its own without a request (its short list of safe reads) still run without Kernel seeing them, in every mode. An accepted command runs with no sandbox, as every command does on Claude in Bypass until A10. A3 records this as an amendment to KERNEL-406, which keeps "every command asks" for Manual and Accept edits. KERNEL-433.

**The tools gate (D5) on Codex answers `mcpServer/elicitation/request`, and until the live run confirms question 8 it leaves unlisted servers out of the thread.** If the elicitation arrives, the gate answers it in every mode, bypass included: Allow once accepts, Keep blocked declines. Today the runner answers that method with an error, so nothing is allowed by accident in the meantime. If the call runs without a request, Kernel can't ask about it. The safe behavior is then the room's `hide` behavior: the thread starts without the server the agent file doesn't list. The probe also records whether a tool marked read-only asks, which decides whether a read-only unlisted tool could slip through. KERNEL-433.
