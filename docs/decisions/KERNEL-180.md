**Kernel tells a teammate with no PR when main moves under its branch in a way that would conflict, and doesn't wake the Lead.** A workspace fetched origin only when it started, and a conflict showed up only once its PR existed, as `pr.conflict` from GitHub. A teammate that started two hours ago didn't learn that three PRs merged since.

`BaseWatch` (`features/baseWatch.ts`) checks the ready, worktree workspaces that are not reviews or the Lead's, whose PR state is `none` or `creating` and whose folder exists. An open PR is left to GitHub. `behind` is `rev-list --count HEAD..<base>`. The merge test is `git merge-tree --write-tree --name-only` of the worktree, with its uncommitted tracked changes (or HEAD when there are none), against the base. Those changes are a commit that `snapshotCommit` makes in a copy of the index: `add -u`, `write-tree`, `commit-tree` on top of HEAD. It does not use `git stash create`, which takes `index.lock` and rewrites the index, so a teammate's `git add` or `git commit` at that moment could fail on the lock. The copy leaves the folder, the real index and the stash list alone, so a check changes nothing the user can see and blocks nothing. Untracked files aren't in it. With unmerged paths, mid-merge or mid-rebase, it reads the committed work alone. Git older than 2.38 exits 129 and is skipped without a word, like any other merge-tree failure, and a failed fetch stops the check quietly.

The state, `{ sha, behind, conflicts, told }`, is kept per workspace under store meta `baseWatch`. A conflict sends one Kernel message through `sessions.post`, naming up to ten files and then "and N more", and logs one line. `told` holds the base commit the teammate was told about, so a second check on the same base sends nothing, and a base that moves again, with the conflict still there, tells it again. `post` sends only to an idle chat with nothing queued, so a busy teammate is told at its next turn end and never mid-turn. Behind with a clean merge says nothing. Once the branch has caught up, its state is cleared.

Triggers are real events, with no timer: a PR in the room merged (with a fresh fetch, since the merge is why it runs), a teammate's turn ended (local only, for that workspace), and a workspace was created after a fetch that worked. One check runs at a time per room, so two triggers can't tell a teammate twice.

Why the teammate and not the Lead. The teammate is the one who can rebase, the Lead has nothing to do about a conflict in work it didn't write, and a message to the Lead is a turn that costs the user usage. The teammate's reply reaches the Lead through the normal team update. Not built: a visible "N commits behind main" indicator, which needs a design first. KERNEL-180, KERNEL-404.
