**A paired browser runs the same Kernel UI the window does, over the Remote access socket.** The renderer talks to the main process only through `window.kernel` (`invoke`, `on`, `appearance`, `pathOf`). When that is missing, `src/renderer/src/main.tsx` hands the page to `remote/start.tsx`, which puts a `Bridge` (`remote/bridge.ts`) there that speaks the protocol in `remote-access-server.md`. No screen knows which one it has, apart from the few that call `isRemote()`. The server serves the renderer build at `/` through the `assets` seam, so the page and the socket come from one origin and one Mac.

**The bridge carries a call as `{ id, channel, req }` and fails it in plain words.** A call made before the socket opens waits and goes out when it does. A call that was already sent when the socket dropped fails with "connection lost", because it may have run on the Mac and sending it again could run it twice. A call with no answer fails after 60 seconds, and if the socket has also said nothing for that long it is treated as half open (a phone that slept) and closed, which starts the retry. A message over about 1 MB fails in the browser with a sentence, since the server would close the socket for it. A lost socket is reopened after 500 ms, doubling to a 15 s cap, each wait cut by up to half at random so a Mac that comes back is not hit by every device at once. A phone that returns to the front or regains its network retries at once. While it is down a small "Reconnecting to your Mac" notice sits over the app.

**After a reconnect the app loads again what it shows, with `resync` in the store.** Pushes sent while the socket was away are gone, so the lists (projects, workspaces, approvals, notifications, activity, usage, settings, shared files, threads, running chats, pending PR actions) are replaced from the Mac, and every project and every workspace whose chats were loaded is read again. The route, tabs and drafts stay. It is the same set `boot` reads, minus the choice of a first screen.

**A browser can't see why a socket was refused, so the server says.** A refused upgrade reaches `onclose` as code 1006 with no status, the same as a Mac that is asleep. When a socket fails before it ever opens, the bridge asks `GET /session` with the token as a bearer header: 401 means the token was revoked or ended, anything else means keep retrying. A socket closed with 4401 says the same. Either one clears the token, leaves a notice and reloads the page into the pairing message, so a revoked device never sits on a broken app. `/session` answers 204 or 401 and nothing else, under the same Host and Origin checks as every other path.

**Pairing is one small screen in the one modal shell.** The link is `http://<host>:<port>/#pair=<code>`. With a code, the page shows "Pair this device" with a device name field filled from the browser (for example "iPhone Safari") and a Pair button that is busy while it waits. It posts to `/pair`, keeps the token in `localStorage` under `kernel.remote.token`, removes the hash from the address bar and starts the app. A used or expired code shows its reason in the dialog and stays there. With no code and no token the page says "Open the pairing link from Settings, Remote access on your Mac." The token sits in `localStorage`, so a script on the page could read it. The page's policy lets only its own scripts run (below) and the app renders no HTML from an agent, which is why that is acceptable; a cookie would have meant a second way in for cross-site requests.

**The page is served with a strict Content-Security-Policy.** `services/remoteAssets.ts` serves `out/renderer`, the folder the window loads, at `join(here, '../renderer')` from the main bundle, in the package too. A path maps to one file in that folder and nothing else: the URL is decoded once and must not hold a NUL, a backslash, an empty segment, `.`, `..` or a dot-file, a folder is never listed, only listed file types go out, and the real path of the file (symlinks resolved) must stay inside the real folder. Double-encoded forms such as `%252e%252e` decode to a literal name that does not exist. Responses carry `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data: blob:; connect-src 'self' ws://<host> wss://<host>; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. `'unsafe-inline'` is for styles only, which the app sets from code. The `ws://` source is named next to `'self'` because older Safari does not count a WebSocket as the same origin. The host in it was already checked against the Host rules of `remote-access-server.md`. With no build in the folder, `/` keeps the placeholder page and everything else is 404.

**What the Mac does for itself stays there, and the browser says so.** Every `system.*`, `terminal.*`, `scripts.*`, settings write and `app.*` channel is refused by the allowlist, and a browser would meet an error on each click. Where the renderer can tell (`isRemote()`, true when `window.kernel.remote` is set), these controls are hidden: Open in (editor, Finder, Terminal), Open in editor on files and plans, Show in Finder and Open in Preview on shared files, Settings and Help in the sidebar footer, the account menu, the add-project items in the projects menu and first-project pills. `openSettings` and the dialogs that pick a folder or clone to disk (`MAC_ONLY_MODALS` in the store) show a toast "Only available in Kernel on your Mac" instead, which also covers the keyboard shortcut and the command palette. A fresh project, which would open its Agents page in Settings at launch, opens the Inbox. Links to web pages (`system.openExternal`) open in a new tab of the browser. A few channels the app calls at start, which only make sense in its window (`system.fixture`, `system.zoomChanged`, `telemetry.track`, `notifications.playSound`), are answered in the bridge without asking the Mac.

**Attaching a file reads its bytes in the browser.** `pathOf` returns an empty string, so the composer's existing path for a file with no path on disk applies: an image goes as an inline `dataUrl`, a text file up to 1 MB as inline `text`. No part carries `src` or `path`, which the server refuses. Not available from a browser: an attached PDF or other binary file, a drop of a folder, and an `@` mention of a file in the workspace (its part carries `path`, which `remoteChannels` refuses). Files beyond the 1 MB message limit can't be sent.

**Phone width.** Below 640 px (and only with `data-remote` on the page, set by `start.tsx`) the sidebar toggle moves to the left edge, Back and Forward leave the header, and the sidebar opens over the page and closes when a place is picked. The right panel and sidebar already fold below 1024 and 900 px, and the screens already lay out for the width of their own container. Approvals, the composer and the transcript fit in 390 px. This was checked in Chromium at 390 by 844 against a real Kernel, not as a fixture: the shots harness draws the app in an Electron window that has the preload, so it has no way to turn the remote layout on.

**Limits.** The browser has no Settings, no accounts, no project adding, no terminals or run scripts, no editor or Finder, and no preview of shared HTML or PDF files (those draw in a native view on the Mac, `system.preview.*`). Comments on shared pages are off. It speaks plain HTTP in `Other devices on my network` mode, with the caveats in `remote-access-server.md`; `localStorage` holds a 30 day token. The end to end test (`test/remoteWeb.test.ts`) starts a Kernel, pairs a real Chromium over HTTP, loads the page and reads the project list through the socket. It needs `pnpm build` and Playwright's Chromium and is skipped, with a message, when either is missing.
