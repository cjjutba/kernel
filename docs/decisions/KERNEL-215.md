**Agents that were working when Kernel quit, crashed or lost power carry on by themselves when it opens again, Lead chats included.** Before this, a quit aborted every session and cleared its queue, and a relaunch only carried on chats a usage limit had stopped. A chat cut off by a quit looked idle for good, its tool rows stayed on running, and what was queued was gone. CJ decided a quit, a crash, a force quit and a Mac shutdown should all end the same way: every agent that was working picks up where it left off.

Sessions keeps a journal of chats with a running turn under the meta key `working`, written in `setRunning` at every turn start and end. Nothing has to run at quit time for it to be right, which is the point: a `kill -9` or a power cut leaves the list as of the last turn change. `stop()` writes `cleanExit: true` once every session has ended, and `start()` reads and clears it, so the note can say "Kernel quit while this agent was working." or "Kernel closed unexpectedly while this agent was working."

On quit, `Sessions.shutdown(budgetMs)` replaces `stopAll()`. It freezes the journal first, so turns that end during the quit stay in it. It interrupts every running turn at once, waits up to 3 seconds for them to end, then ends every process. Queues are kept. An interrupted turn's end doesn't call `onTurnDone`, adds no interrupted row and sends nothing, because the turn isn't over. KERNEL-214's quit waits up to 5 seconds for `stop()`, so the 3 seconds fit inside it. Until KERNEL-214 lands, `before-quit` doesn't wait for `stop()` at all, so a quit may end before the interrupt and reads as a crash at the next launch. The journal is right either way. Close chat and archive still use `stop()`, which drops the queue as before. A Stop the user pressed just before the quit stands: `shutdown` leaves that turn's interrupt as a Stop and takes the chat out of the journal, so its queue is dropped and it doesn't carry on.

Two callers can stop Kernel at once once KERNEL-214 lands, Restart to update and `before-quit`. `stop()` keeps its promise, so the second caller waits for the same stop instead of returning while `shutdown` is still interrupting.

The 3 seconds and the rest of `stop()` have to fit KERNEL-214's 5-second cap, or Electron quits before `cleanExit` is written and the next launch says Kernel closed unexpectedly. Everything after `shutdown` is quick except the hook server's `close()`, which waits for open requests. An outside session waiting on an approval in the Inbox holds its request open for up to the approval timeout, 300 seconds by default, so `stop()` used to hang there. Two changes cover it. `stop()` ends every hook connection before it closes the server: Kernel can't answer that approval once it quits, and Claude Code falls back to its own prompt when the hook fails. And `cleanExit` is written before the hook server closes, not after, so even a close that still hangs can't turn an ordinary quit into "closed unexpectedly". Nothing after it changes what carries on: the journal, the queues and `cutOff` are final once `shutdown` returns. Every approval still waiting ends as expired in `stop()` itself, right after `cleanExit`, while the database is open. The next start would expire it anyway (D-137). Ending the connections alone wasn't enough: a dropped connection's `close` event, which aborts its approval, fires a tick after the server's `close()` callback, so the abort reached a closed database. Settling first also gives the outside session its fallback answer, so Claude Code asks in its own window, before the connections end. With a turn that ignores its interrupt and an approval waiting, `stop()` takes the 3-second budget plus a few milliseconds.

Every chat's queue is saved now under `queues`, not only the briefs held for setup (`held`, D-123, unchanged). At launch Kernel loads every room's agents before `restore`, because `agentFor` returned nothing until then. Chats that carried on at launch, after a limit or now after a quit, came back without their agent prompt, and a Lead without its Kernel tools.

At launch each journal chat that is still open and not archived gets its tool rows still on running marked failed ("Stopped when Kernel quit"), the note, and a place in `cutOff` with the reason `quit`. `cutOff` is now a map from chat to `limit` or `quit`. A list saved before this reads as `limit`. `carryOn` is the one gate for both, so a pause, an offline or signed-out hold, a known limit and the agent limit all make the chat wait, as they do for a limit.

At launch nothing has run yet that would notice being offline or signed out. Kernel only learns of a sign-out when a session fails, and the network monitor's first probe is still running. So when something will carry on (the journal or `cutOff` isn't empty), `start()` waits for that probe and reads the account once, before `restore`, and holds every room on a sign-out. That costs one `claude auth status` at launch, only when there is work to resume. It doesn't catch everything, since a sign-out or a dropped connection can come partway through a carry-on. So a turn that carries on a quit (the nudge, or a message queued before it) and ends in failure after an `auth` or `network` failure goes back into `cutOff` as `quit`, the way a limit puts a chat back. It only does that while a hold is in place, since that is what will lift. A connection error with the network check still saying online sets no hold, and that chat stays stopped like any failed turn rather than retrying in a loop. A limit sends `LIMIT_LIFTED`. A quit sends `RELAUNCH_NUDGE`, which tells the agent its last step may not have finished and to check git status, open PRs and hand-offs before redoing anything. A Lead could otherwise run `create_workspace` twice. KERNEL-287 also refuses a duplicate hand-off. A chat that had messages queued gets the nudge at the end of its queue, once however many times Kernel quits, so what the user queued goes first. This differs from a limit, where a queued message replaces the nudge. A message queued before a quit was written for a turn the agent hadn't finished, so the agent still needs to hear its step was cut short. A message sent after the relaunch, while the chat waits, is the user taking over, and the nudge isn't added after it.

This amends D-116 for interrupted turns: a Lead chat that was mid-turn starts a turn by itself at launch. Team updates still never start a Lead turn at launch (D-118). A teammate that carries on is reported through `onExit` with `resumed: true`, so it rides along as a `crash` in the Lead's next update and doesn't wake it. One whose carried-on session then dies mid-turn goes through the existing crash path and wakes the Lead (D-119). The team update says "Kernel quit while Kai was partway through a turn. Kai carries on by itself once nothing holds it, such as a paused room or the agent limit." and not "ended unexpectedly … is working again", which was wrong twice over: a quit isn't unexpected, and a paused or capped chat isn't working yet. Adding the event arms the usual 5-second batch. If updates that wake the Lead were already waiting from before the quit, they can go out then, which is when they would have gone without the quit.

`claude` processes outlive a `kill -9` of Kernel. I tested it on SDK 0.3.292: the orphan moved to launchd, finished its running Bash step (a file the step wrote appeared 40 seconds later) and only then exited. A resumed session would work in the same worktree alongside it. So Kernel starts Claude Code through the SDK's `spawnClaudeCodeProcess` with the same `spawn` call the SDK makes, and saves each live pid with its binary path under `claudePids`. At launch, before anything resumes, each saved pid that is still alive and still started the same way, the binary and its first argument (checked with `ps`, so a reused pid is left alone, even one running `node` with another script), gets SIGTERM, then SIGKILL if it hasn't gone within 2 seconds. The saved list is cleared only after that, so a crash during the wait still finds them next time. SIGTERM comes first because the CLI then ends the shells its tools started, and a SIGKILL would leave them running. The quit path sends the same SIGTERM after it ends the sessions, because the SDK waits about 2 seconds after closing stdin before it kills the process, and Kernel is gone by then. With a custom spawn the SDK no longer reads stderr, so Kernel keeps the last 4,000 characters itself and adds them to the "Session stopped" note. The SDK also skips its default `--debug-file`, which it only writes when its debug environment variable is set.

The lost-session fallback, for a chat whose Claude Code transcript is gone, is KERNEL-286. Until it lands, a chat that carries on with a pruned session fails the way any send to it does. KERNEL-215.
