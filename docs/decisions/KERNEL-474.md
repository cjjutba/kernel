**A room uses Jira only when it says so.** `[tracker] kind = "jira"` is the only way in. A saved Jira account plus a `[jira] project` doesn't pick Jira the way a Linear token plus `[linear] team` picks Linear (KERNEL-462), because a Jira site is one account for every repo on the Mac and nothing in a repo points at it. The room's `[jira] project` is optional. Without it the room lists open issues from every project the account can see. KERNEL-474.

**The Jira account is one per Mac, in its own file.** Kernel keeps the site, email and API token together in `jira.json` in the data folder, encrypted with the `Cipher` (the Keychain). When the Keychain can't be used, the file holds them in plain text with mode 600, the same fallback KERNEL-445 gives the Linear token. They get their own file instead of a key in `integrations.json` so this branch and KERNEL-445 don't both rewrite that file. An account the Keychain can't decrypt, say one saved on another Mac, reads as none until the user connects again. Connecting asks Jira who the account is (`/rest/api/3/myself`) before saving, so a wrong token or site is never saved. An empty token disconnects and deletes the file. KERNEL-474.

**Starting work on a Jira issue runs one transition the room picked, and only from To Do.** Jira moves an issue through workflow transitions, and the right one differs per project, so Kernel doesn't guess. The room saves a transition id as `[jira] transition`, in the personal settings file unless the caller asks for the shared one. With none saved, `start` moves nothing. With one saved, `start` reads the issue's status and the transitions it offers in one call (`expand=transitions`), and runs the saved one only when the issue's status category is To Do, so an issue in progress or done stays put, as D-140 has it for Linear. A transition the issue's status doesn't offer is an error, which lands as a warning note on the workspace and never fails it. `jira.transitions` lists what a given issue offers, or without one, what the room's last updated To Do issue offers, since Jira only lists transitions per issue. KERNEL-474.

**Kernel searches Jira with the enhanced JQL search and never retries a rate limit.** Lists go through `POST /rest/api/3/search/jql`, which replaced `/search` in Jira Cloud: open means `statusCategory != Done`, last updated first. The query matches the summary as a prefix (`summary ~ "words*"`) with Jira's text operators stripped. A query that is a key, or a number in a room with a project, also fetches that issue directly and lists it first when it's open, because JQL rejects the whole search when `key = X` names an issue that doesn't exist. A 429 rejects at once with Jira's Retry-After in the message. A screen shows it and the user can try again, and a move to In Progress lands as a note. Nothing waits on a timer. KERNEL-474.

**Descriptions and comments become Markdown, and what Markdown can't show is dropped or noted.** Jira v3 sends Atlassian Document Format. `adfToMarkdown` handles the nodes Jira's editor writes: headings, marks, lists and task lists, code, quotes, panels (as quotes), tables (first row as the header), mentions, dates, status lozenges, cards and expands. Underline and colour lose their style and keep their text. A file uploaded to Jira shows as `[attachment: name]`, since an agent can't open it from the brief. A node it doesn't know shows the text it holds. A blocker is an issue linked as "is blocked by" that isn't done. KERNEL-474.
