**In Bypass permissions, an MCP tool the agent file doesn't list runs without a card while the room's `unlisted_tools` is `ask`.** Amends KERNEL-433, where the tools gate asked in every mode, bypass included, and KERNEL-537, where such a call showed a card in every mode. The user's call: Bypass permissions behaves like Claude Code's `--dangerously-skip-permissions` here. What refuses without asking still refuses: Never allow, a push that might reach a protected branch, network off, disallowedTools, built-in tools outside the tools line, and a room with `unlisted_tools = "hide"`. Questions (AskUserQuestion, Codex's requestUserInput) and plan approval still go to the user, and so does whatever Claude Code itself insists on asking about in bypass (`canUseTool`). A room's Always allow rule still answers first, as before.

**On Claude, the gate counts a step as Bypass only when every mode Claude Code might run it in is Bypass permissions.** That is the runner's `rules()` view, the one Kernel's other asks use (KERNEL-447): the mode Kernel last set, the modes a switch is still asking for, the one Claude Code last reported and the one the chat should be in. So a chat leaving Bypass, a switch that is pending or refused, a status that reports a stricter mode, and plan mode in a Bypass chat all get the card again. A process started with `allowDangerouslySkipPermissions` (`mayBypass`) does not count on its own. It keeps Bypass's denials for the process's life, which makes Kernel deny more, so it can't also be a reason to ask less. The gate reads the mode at each call, since it changes during a process's life, and answers `allow` as it does for a room rule. The `tool.blocked_by_agent_file` count still records refusals only. The gate sees one tool at a time, so on Claude a tool of a server the tools line names in part (`mcp__linear__get_issue` named, `mcp__linear__save_issue` called) counts as unlisted and runs in Bypass too.

**On Codex, a thread in Bypass permissions keeps the MCP servers its tools line leaves out, and crossing into or out of Bypass restarts the process.** With `unlisted_tools = "ask"`, `mcpOverrides` no longer switches those servers off. Servers the room switched off and servers disallowedTools takes away whole stay off. Tools it names still join `disabled_tools`. A server the tools line names in part keeps its `enabled_tools`, because the file says which of its tools the agent wants, so Codex and Claude differ there. "In Bypass" is the chat's `effectiveMode`, so plan mode doesn't count, as on Claude, where the gate asks while a chat plans. Codex reads a thread's MCP config only at `thread/start` and `thread/resume` (KERNEL-451), so a process keeps the list it started with. Kernel restarts it when the chat crosses the line rather than letting the new list wait for the chat's next start. Waiting would leave unlisted servers on after a chat leaves Bypass, in a mode that keeps them off, and Kernel can't ask about a Codex MCP call yet (KERNEL-433, question 8). The restart follows the Claude one (KERNEL-447): an idle process ends at once, and a busy one when its turn and background tasks end. The next message resumes the thread with the new list. Approvals still follow the new mode from the next request, so until a running turn ends its approvals and its server list can disagree. A Bypass chat that plans restarts once its plan is approved. The plan turn has ended by then, so the build turn resumes the thread on a new process with the servers on. Every Codex chat that crosses restarts, tools line or not, which costs one process start on the next message.
