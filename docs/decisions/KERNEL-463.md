**The agents in `~/.claude/agents` join every room's team, and a repo file with the same name wins.** Claude Code runs a user's personal agents in every folder, so Kernel reads them with the same parser as the repo's files (KERNEL-451) and marks them `origin: 'personal'`. When a file in the repo's `.claude/agents` that Kernel can read has the same `name:`, the personal file is left out with no warning, which is what Claude Code does. An unreadable repo file doesn't hide a personal one, because Claude Code skips the unreadable file. Each room watches `~/.claude/agents` the way it watches the repo's folder, so a file added, edited or removed there shows up on every team. Personal agents follow the same team rules as repo files: they take tasks when their tools can open a PR, and a personal file marked Lead or with a reviewer role leads or reviews a room that has neither. KERNEL-463.

**Plugin agents come from Claude Code's own list, and their prompts from the plugin's files.** `supportedAgents()` returns a name, a description and a model for each subagent, and nothing else, so it says which plugin agents exist but not what they do. Plugin agents are the ones named `<plugin>:<agent>`. No file's name can hold a colon (KERNEL-451), and Claude Code's own agents (Explore, Plan, general-purpose) have none. Kernel finds the plugin's folder in `~/.claude/plugins/installed_plugins.json`, preferring a user install, and reads the agent from its `agents` folder or from a file or folder its `plugin.json` lists under `agents`. A listed path that leaves the plugin's folder is ignored. An agent whose file Kernel can't find or parse stays on Team with an `unreadable-file` warning, like any file Kernel can't read. The agent's id is Claude Code's name, `feature-dev:code-reviewer`, so `[team]` names it the same way. KERNEL-463.

**Kernel asks for plugin agents once a launch, from the home folder, with only the user's settings.** The ask starts Claude Code with `settingSources: ['user']`, all hooks off, no MCP servers and no message, and takes about a second. Asking in each room with its project settings would find plugins turned on for a single project, but it would start one process per room at launch and run each repo's settings before the user had opened a chat there. So plugin agents turned on only in a project's `.claude/settings.json` don't show up. The first team reads go ahead without plugin agents. When the list comes back, every room reads its team again, and the plugin agents don't walk in as new hires. A failed ask leaves no plugin agents until the next launch, so a Mac without Claude Code doesn't start a process at every read. A plugin installed or turned off while Kernel runs shows up at the next launch. The app passes the ask as `KernelOptions.claudeAgents`, and tests pass a stub or leave it out. KERNEL-463.

**A plugin agent leads or reviews only when `[team]` names it.** One plugin puts its agents in every room on the Mac, and they were written as subagents for someone else's workflow. Under KERNEL-397's rules, feature-dev's `code-reviewer` would have replaced Kernel's Theo as the reviewer in every room without a reviewer file, and a plugin file with `lead: true` would have replaced Rowan. So `resolveTeam` skips plugin agents when it looks for a file marked Lead or a role that says review. Every other team rule applies to them as written: they take tasks when their tools can open a PR, `[team]` can make them members or helpers, and `[team] lead` or `reviewer` can name one. Amends KERNEL-397. KERNEL-463.

**Kernel doesn't edit or retire a personal or plugin agent.** Saving a profile or retiring rewrites or moves a file in the repo's `.claude/agents`. A personal agent's file is shared by every room, so Kernel refuses and says where the file is. D9 will let "for me" edits write there. A plugin's files belong to Claude Code, which replaces them on update, so Kernel never writes them, and retiring one says to turn the plugin off in Claude Code. KERNEL-463.
