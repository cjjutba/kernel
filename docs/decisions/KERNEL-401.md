**A room's optional checks are edited on its Git page.** The room's Git settings have a Pull requests section with one row, Optional checks: a list with one check name per line, saved as `[pr] optional_checks` in the room's personal file. It shows which file the list came from and has Reset, like Files to copy. An empty field saves an empty list when settings.toml sets one, since removing the key would bring the shared list back and the field couldn't be cleared. With no shared list, an empty field removes the key. The list lives on the Git page and not on a page of its own because it is one row, next to Cleanup's other PR settings. Amends KERNEL-388, which had no control in Settings. KERNEL-401.

**The footer says when a GitHub rate limit holds Kernel's PR reads off.** While the poll is paused (KERNEL-388), the footer's left side shows "GitHub paused" and "PRs update at 3:41 PM", beside where Hooks down shows. The tooltip says why: GitHub's rate limit is almost used up, or GitHub asked Kernel to slow down. It is a focusable status with the reason as its description, not a button, since there is nothing to do but wait. Main pushes the pause (`github`, with `github.status` to read it on load) when it starts, moves or ends. Its end goes out on the poll the pause's own timer brings, so the window never times the status out by itself. The slower reads below a fifth of the limit show nowhere. `PrCadence` keeps the reason of whichever limit set the pause's end, so a short slow-down inside a longer rate-limit pause doesn't relabel it. Amends KERNEL-388, where the pause showed nowhere. KERNEL-401.

**Kernel hears when GitHub starts or stops blocking a ready PR.** A block (`prBlocked`: a required review, a branch behind its base, another rule) that starts, ends or changes reason while the PR stays ready pushes `pr.blocked`. Kernel's updates get a `pr.blocked` event for a block, or a new reason, it hasn't heard. They get `pr.unblocked` only for a block it did hear. What Kernel last heard is saved with the queue in the `leadUpdates` meta, so a restart doesn't lose it. A PR usually falls behind as its base moves: GitHub reads it as checks, then ready again on the same head, which KERNEL-283 keeps from being news. On that ready, the block is checked anyway. A block that starts and lifts before an update goes out says nothing. Amends KERNEL-388, under which the Lead heard nothing new. KERNEL-401.

**One To do line covers each block, and a branch behind its base goes back to its agent.** For a PR behind its base, Kernel asks the agent to fetch, rebase onto the base, re-run the tests and force push, the way a released wait asks (KERNEL-259). That ask comes before any review request, since the update makes a new head that a review would have to see again. For a required review or another rule, Kernel tells the user. The `pr.blocked` event, a ready PR's "ready to merge" lines and a reviewer's approval of a blocked PR all use the same words, so the line shows once. An approval names the PR's author, not the reviewer. A `pr.unblocked` wakes Kernel only when the PR can merge: it was approved, or auto review is off or no reviewer is on the team, with no review open or stale. Otherwise it rides along and doesn't count as news for a turn. Amends KERNEL-388. KERNEL-401.

**The loop guard holds while a ready PR is still behind its base.** A ready read that GitHub reports behind doesn't start the guard over (KERNEL-125), and catching up does. Without that, an agent that rebases onto a stale base makes a new head each round, the guard starts over each time, and the request limit never trips. KERNEL-401.

**The Inbox says ready to merge only once GitHub would merge it.** A PR that becomes ready while GitHub blocks it gets no "ready to merge" row. A block that starts settles an open row with "GitHub blocks the merge.", and a block that lifts makes the row a ready PR gets, with its alert. The check runs before KERNEL-283's same-head rule, since a PR that falls behind comes back ready on the same head. At start, a blocked PR's old row doesn't count as its row, so an unblock after a restart still makes one. Amends D-033. KERNEL-401.

**A ready PR GitHub blocks reads "PR open" in the sidebar and the Lead's PR list,** as the header reads Open (KERNEL-388). On the Team update card, a lifted block is green like a ready PR, and a block is grey, brighter when it needs Kernel. KERNEL-401.

**The canvas template carries KERNEL-378's Merging row.** That row existed only in `project/SettingsPRs.dc.html`, so `build.py` would have dropped it. It is now in `templates/Settings.dc.html` as it was, and every Settings page builds it. KERNEL-401.
