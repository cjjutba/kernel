**A Codex server that is off on purpose reads `off`, not `not-set-up` or `failed`.** Amends KERNEL-646. Two cases: a server `config.toml` switches off (`enabled = false`, vapi and computer-use on CJ's Mac) reads "Off in Codex config", and a plugin's server that Codex lists but never starts on the ephemeral thread (code-review and codex_app, the bundled plugins) reads "Not started by Codex". KERNEL-646 showed the first as not set up and the second as failed, so both warned about something the user chose or can't change. A server with no plugin that Codex doesn't start stays `failed`, and so does any server whose start Codex reported as failed. A server that is `off` on every account that has it is `off` on the accounts missing it too. KERNEL-660

**`needsYou` and `ready` are counted in one place, `mcpCounts` in `src/shared/mcpCounts.ts`, and every `McpAccount` carries them.** A server needs the user when it needs a sign-in, failed or isn't set up, and isn't ignored, `off` or switched off in every room. The issue lists ignored and off. Kernel also leaves out `roomOff`, since KERNEL-646 keeps those out of the row warning and Sign in to all, and the numbers have to agree. A not-set-up server counts whatever its kind. The Skills and MCP page counted only connectors before, so its number moves to `needsYou` with KERNEL-661. KERNEL-660

**Set up this account is Sign in to all with a plan.** `accounts.mcpSetUp` and `accounts.mcpSignInAll` share one queue in `Mcp`, so Cancel, the one-run-per-provider rule, the `account.mcpSignInAll` pushes and the failure list behave the same. What isn't ticked is ignored through `Providers.ignoreMcp`, one write to `accounts.json` for all of them. Ticked servers go in the order the renderer sends. The claude.ai connectors that aren't set up become one `account.mcpConnect` push, with claude.ai's connector settings, the account's email and their names, at the first connector's turn. Kernel doesn't open claude.ai itself: the renderer opens it once. A ticked server Kernel can't act on, failed or a user or plugin server not set up, stays as it reads until the next check. **Kernel checks an account again after each sign-in, and `mcp.recheck` re-checks pending accounts when the window gets focus.** The renderer calls `mcp.recheck` on focus. It re-checks only accounts with `needsYou` above zero or a failed check, at most once every 10 seconds, and a call inside that window answers with what Kernel knows. Main doesn't push on focus because the focus event lives in `index.ts`, which this lane doesn't own. A check asked for while one runs on the same account runs once more after it (`fresh`), and `checkedAt` is when a check started, so a sign-in that finishes during a check is never hidden by the older result. A Codex sign-in re-checks only the account it ran on. The other Codex accounts read the server as ready from `codexSignedIn` until their own next check, as in KERNEL-646. KERNEL-660

**Codex accounts whose servers read the same carry `sharedWith`.** KERNEL-646 found that Codex keeps MCP sign-ins in one store for every Codex account. Two checked Codex accounts match when they list the same servers with the same states. Each gets the other's id, so the page can show one Codex tab. Ignoring a server on one account makes them differ, which is right, since ignore is per account. Claude accounts never get `sharedWith`, because their connectors belong to each claude.ai account.
