**A Build here chat's own PR is drawn as rows and wakes the Lead only when the user has to decide or act.** Amends KERNEL-778, which sent the chat's own PR down a teammate's path, so every opened, ready, approved and merged event cost a full Lead turn that repeated what was on screen. The chat's own workspace still routes through `ownChat`, but `decide` no longer wakes for `pr.opened`, `pr.ready`, `pr.unblocked`, an approving review of the current commit, or a `pr.merged`, whether Kernel or GitHub merged it. It still wakes for blockers, `pr.cifail`, `pr.changes`, `pr.conflict`, `pr.blocked`, `pr.closed`, a capped `pr.updated`, a review of a commit the PR no longer has, and a ready PR GitHub blocks or whose review can't start. Hand off chats keep their teammates' Team updates and wake rules unchanged. A merge still never archives the chat (KERNEL-405). KERNEL-990.

**Events about the chat's own PR that don't wake are dropped, not held.** A teammate's quiet events wait and ride along with the next update that wakes the Lead. The chat's own would only repeat news the transcript already shows, so `compose` keeps just the events that woke, and a Team update that wakes for the chat's own PR carries no row of status-only events. A review of the chat's own PR that approved its latest commit is posted as a chat item of kind `update`, holding only the reviewer's row. It is drawn with the Team update card and never sent to the session, so it costs no turn. Blockers still go to the Lead as a Team update. KERNEL-990.

**The PR's progress is notes, at most one opened, ready and merged per PR number.** `prs.moved` posts "Opened PR #N" and "PR #N is ready to merge" for the chat's own PR, through `prNote` in `github.ts`, with `note.pr` of `opened` and `ready`. A refusal by auto-merge is added to the ready note in place. Kernel's own auto-merge reads "Kernel merged PR #N automatically, since ...". The notes are saved with the transcript, so a double event from polling or a refresh, or a replay after a restart, finds the note already there and adds nothing. The Inbox row and the system notification still come from the `pr` push alone. KERNEL-990.

**The merge note takes the new-branch ending in place, and no row names a branch.** `Lead.freshNow` no longer posts "This chat now works on ...". It adds "Next changes start on a new branch" to the PR's merge note with a `chat.item` push, or posts it as a note of its own when there is no merge note. A fetch that fails (with a remote to fetch from) leaves the chat where it is and ends the merge note with "Kernel couldn't update to the latest main". A kept branch is a note of its own and says why, such as "Kernel kept this branch because it has uncommitted changes". The merged branch's name is passed to `freeBranch` as taken, so the new branch never reuses it, even when the remote branch was deleted. An archived chat or a missing folder gets no switch and no row. KERNEL-990.

**The chat's next turn starts with one line about the merge.** After the switch, Kernel saves "PR #N merged. This chat is now on a new branch from <base>." under the workspace and the next turn takes it once, the way a revert's note goes (KERNEL-764), so the Lead doesn't assume its PR is still open. KERNEL-990.

**The chat's own PR gets no opened row, and a ready row only when the screen doesn't already say it.** In Build here the Lead opens the PR and says so, and a review only starts once checks pass, so an approval already means ready. `prs.moved` posts no "Opened PR #N". The "PR #N is ready to merge" row (`Prs.readyNote`) is posted only when no review ran (auto review off, or none covers the change, from `Reviews.onReady`), when auto-merge is on and didn't merge it (the reason is added to the row), or when GitHub blocks the merge (the reason is added). `note.pr` keeps `opened` and `ready`, since old chats store them. Hand off chats are unchanged. KERNEL-990.
