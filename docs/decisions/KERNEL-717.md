**With "Review every pull request automatically" and "Wait for the reviewer's approval to merge" both on, a PR waits for every required review Kernel plans for its head commit, from the ready event on.** Amends KERNEL-115 and KERNEL-549. Before this, `mergeBlock` waited only on kinds that already had a verdict, so "a PR nobody reviewed merges as before" also covered a PR whose review hadn't started or hadn't reported yet. It read Ready to merge, with Merge, until the first verdict landed.

Two markers on the workspace carry the plan, since `mergeBlock` reads only the workspace and GitHub's read. `reviewPending` names the head `Reviews.onReady` is working out the reviews for. It is set before the first await, so nothing merges while `planFor` reads `[review]` with git. The saved round replaces it in the same write, and an empty plan, a failed start or a round `[review] rounds` stopped clears it. The round's required kinds then hold the merge until each approves the head: its `kinds`, less the ones it `skipped` near the usage limit and the new `optional` list. A kept approval moves to the new head, so it counts as it did. A required kind held near the usage limit is in the round and not skipped, so it waits.

The rule doesn't read `autoReview` itself. Only an automatic review writes either marker, and turning automatic review off clears a pending one at the next ready. That keeps the renderer's rules as they are. No review planned (`[team] reviewer = "none"`, or no kind matches the PR's paths) leaves no marker, and the PR merges as before. The wait gets no Merge anyway: only blockers do (KERNEL-501).

Both markers live in the workspace row, so they survive a restart. A quit while Kernel worked out the plan leaves `reviewPending` set, and no ready event comes for a PR already ready, so `Reviews.start()` runs `onReady` again for each ready PR whose marker names its head, and clears the rest. Until then the PR stays held. KERNEL-717
