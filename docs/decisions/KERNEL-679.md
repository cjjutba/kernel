**A dev run started inside a Kernel workspace is its own copy.** Adds a third case to KERNEL-675 and replaces nothing in it. Pressing Run in a workspace of the Kernel repo starts `pnpm dev` while Kernel Dev is open. That Electron asked for the single-instance lock on `Kernel Dev`, lost it, handed over and quit, so the Run tab went back to Run. An unpackaged launch whose environment has `KERNEL_WORKSPACE_ID` now uses `~/Library/Application Support/Kernel Dev Runs/<workspace id>` and logs to `~/Library/Logs/Kernel Dev Runs`. The folder is per workspace, so two workspaces can each run a copy, and a second Run in the same workspace still hands over. The copy starts empty. It skips the move from `Kernel` and the hook token cleanup, because both read another build's folder. Fixture runs and the smoke test are checked first and keep their own folders. A packaged app is never a workspace run, whatever its environment says. KERNEL-679.

**A workspace run never writes `~/.claude/settings.json`.** Its build is `run`, next to `app` and `dev`. It has no entries in Claude's settings, so no pattern matches any, and start, Install, Reinstall, Remove, Turn on and the rewrite after a settings change all leave the file alone. Its hook status carries the problem `workspace-run`. Settings, Hooks shows that in place of Install or Reinstall and Remove, and hides the snippet, since nobody should paste `/hooks/run` entries. Onboarding skips Check hooks for it, because the copy starts empty and would otherwise stop there. The engine still refuses Install, Remove and Turn on for build `run`, in case something calls them anyway. A throwaway copy that added and removed entries in the file every agent on the Mac reads would be a bad trade for a dev window. Its hook server still listens, on the last port of the workspace's block (`KERNEL_PORT + 9`), so it stays clear of 7420, 7430 and the ports the run's own scripts use. Sessions and terminals it starts get `KERNEL_BUILD=run`, and the installed app and Kernel Dev ignore their posts as they ignore each other's. KERNEL-679.

**What a workspace run can't do.** It sees no `claude` session started outside it, since nothing posts to its port. Its data folder stays on disk after the workspace is archived, because archive runs in the Kernel that owns the workspace and knows nothing about what the run script created. Delete `Kernel Dev Runs` by hand to clear them. Starting the main Kernel Dev with `pnpm dev` from a terminal tab inside the installed Kernel makes it a workspace run too, since that terminal has `KERNEL_WORKSPACE_ID`. Start it from a terminal outside Kernel, or unset the variable. KERNEL-679.

**A run script's log ends with how it ended.** The last line is "Run script ended" for exit 0, "Run script exited with code 1" for any other code and "Run script was stopped" after Stop. It goes to the terminal output and the plain lines, before the exit event. A script that a restart replaced gets no line, because its log carries on as the new run's. Setup and archive keep their own wording. KERNEL-679.
