**Kernel finds every MCP server Claude Code and Codex would load for a room, and only reads their files.** `discoverMcp` (`services/mcp.ts`) used to read `.mcp.json` and the top-level `mcpServers` in `~/.claude.json`. It missed the servers `claude mcp add` writes by default, which sit under `projects[<repo>].mcpServers` in `~/.claude.json`. Those now come first as `local`, then the repo's `.mcp.json` as `project`, then the user's list, and the first one to name a server wins, as in Claude Code. Claude Code keys a project by its folder with links resolved (`/private/var` on a Mac), so Kernel tries the room's path as given and resolved. Codex's servers come from `[mcp_servers]` in `config.toml` in the active account's Codex home, which links back to `~/.codex`, and carry `provider: 'codex'`. `enabled = false` there reads as status `disabled`. A missing or broken file adds nothing. `mcp.list` lists one provider, Claude unless asked, so Settings, Skills and MCP keeps one row per name. KERNEL-464.

**A probe asks Claude Code which servers are up, with every hook off.** claude.ai connectors and plugin servers are in no file Kernel can read, so the status comes from the CLI. `probeClaudeMcp` starts Claude Code in the room's folder with the user's settings sources, no prompt and no saved session, and calls `mcpServerStatus()`. That sends no message. Servers connect on their own time, and on the maintainer's Mac the claude.ai connectors joined about 4 seconds in and everything settled by 7. So the probe reads every 1.5 seconds and stops once two reads agree and none is `pending`, or after 30 seconds with the list as it stands. A live run showed that a SessionStart hook fires even with no prompt, so the probe sets `disableAllHooks`. Without it, the user's hooks would run on every check and Kernel's own installed hooks would report an outside session. The room's switched-off servers go in `deniedMcpServers`, so a server the user turned off never starts for a check, and Claude Code then leaves it out of the list. The env is what a session gets from the app and the room, plus the account's token. The first `mcp.list` for a room starts one probe per run and answers at once. The result comes as an `mcp` push. `probe: true` waits for a fresh one. Kernel never probes on a timer. KERNEL-464.

**A room's statuses live in memory, and every report adds to them.** The `Mcp` feature keeps the last report per room, provider and server. A probe's list replaces Claude's, so a server taken out of every file goes. Each Claude session's init (sent at the start of every turn) and each Codex report only add or update, because a session may not list a claude.ai connector yet, and never lists one the room switched off. A change pushes `{ type: 'mcp', roomId, provider, servers }`. Nothing is saved, so a status is never older than the app's last start. KERNEL-464.

**A server that failed, needs sign-in or is switched off no longer counts as connected.** KERNEL-397 counted any server whose name matched, on the grounds that the problem was elsewhere. But a failed server's tools fail the same way a missing server's do, and the user can fix each case in one step. `missingServers` now takes each server's status and says why one can't be used: `failed`, `needs-auth`, `disabled` (Claude Code's own switch, `/mcp`) or `off` (the room's switch). Pending and unknown servers still count as there. The check also had a naming bug. A session reports a claude.ai connector as `claude.ai Linear` while its tools are `mcp__claude_ai_Linear__*`, so a tools line naming the connector was always called missing. `toolServerName` now copies Claude Code 2.1.292's own function. The chat note checks the session's own list, plus what the room heard about claude.ai connectors that join after the first init, plus the room's off list, and says what to do for each status. Amends KERNEL-397. KERNEL-464.

**On Codex, status comes from app-server's startup notifications, and a tool call speaks for any server Codex reported nothing on.** codex-cli 0.153.4 sends `mcpServer/startupStatus/updated`. `ready` is connected, `starting` is pending, and `failed` is failed, or needs-auth when `failureReason` is `reauthenticationRequired`. `cancelled` says nothing about the server. For a server with no startup report, a finished MCP tool call sets its status: a failed call marks it failed with the call's error, and a later call that goes through marks it connected again. The room hears only when that changes. The room's off list now holds on Codex too. The thread's config turns those servers off even for an agent with no tools line, so the switch in Settings, Skills and MCP means the same thing on both providers. KERNEL-464.

**An alias is the user's word, and Kernel only suggests one.** `[mcp.aliases]` (KERNEL-432) maps a name agent files use to the server this Mac has (`linear = "claude_ai_Linear"`). Kernel never writes it. An `mcp-missing` warning carries a `suggestion` when a usable server's name contains the missing one, and the user confirms it with `settings.setRoom`. `toolPolicy` reads both the tools line and disallowedTools through the aliases, keeping the original name as well. So `mcp__linear__get_issue` allows `mcp__claude_ai_Linear__get_issue` without blocking a Codex server still called `linear`. Either side may be written as Claude Code lists the server or as its tools name it. An alias to or from `kernel` or `*` is ignored, because Kernel's own server is never the user's to remap. Like the room's off list, aliases are read as a session starts and reach the next session. KERNEL-464.

**MCP warnings name a missing server only once the room's list is whole.** `mcpWarnings` turns what an agent's tools line can't reach into P0's kinds: `mcp-failed`, `mcp-needs-auth`, `mcp-off` (the room's switch or Claude Code's) and `mcp-missing`. Their `detail` is the server's name as the room has it, or the name the file uses for a missing one. Until a probe has listed Claude's servers, a name no file has may still be a claude.ai connector, so a Claude agent gets no `mcp-missing` until then. Codex's list is its config, so it is whole from the start. The check reads the tools line only. `mcpServers:` in the frontmatter can define a server in place, and AgentDef keeps only the names, so Kernel can't tell such a server apart from a missing one. `Mcp.warnings(roomId, agent)` is ready for KERNEL-487 to join to the team and for KERNEL-486 to show.
