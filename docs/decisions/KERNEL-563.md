**A card ends with the turn or the process that asked for it.** Each chat's process keeps the ids of the cards it put up. Stop and Send now end the ones still waiting when the turn ends, and the process ending ends them too: Close chat, archive, Restart session, the idle stop, and a crash. Those cards end as expired, the same as a card whose timer ran out. A card answered first keeps its answer. A quit leaves them to `expirePending`, since the database closes right after. When a send right after a stop starts a new session, the old process's late end touches only its own cards. On Codex every request also waits on its turn's abort signal, and so do Kernel's tools through `extra.signal`, so the Lead's cards on Codex take the KERNEL-496 path. Codex's own docs for 0.153.4 say `turn/interrupt` doesn't wait for an open request: Codex clears it, sends `serverRequest/resolved` and completes the turn as interrupted. Kernel aborts the turn's signal before it sends `turn/interrupt`, and again when the turn completes, so a request Codex cleared on a failed turn ends too (KERNEL-563).

**A Codex plan belongs to the chat, not the process.** A Codex plan comes after its turn ended, so a Stop or a Send now on a later turn leaves it, and so does Kernel ending an idle process: the idle stop, an account switch, an agent file change. Approving it then resumes the thread and sends the agent on, as before. The user's own next message ends it, as typing instead of answering ends Claude's ExitPlanMode card. A Kernel update, a nudge and a message from the Lead leave it waiting, since none of them is the user's answer. Close chat, archive, Restart session and a crash end it (KERNEL-563).

**A card that ended with its process leaves the agent's status alone.** Before, a card that resolved after its process was gone set the agent back to working, so after a crash the status went from offline to working. Now the status the process's end set stays (KERNEL-563).
