**A terminal seat reaches Kernel's tools over local HTTP, not through an in-process server.** Amends D-001, whose "the big terminal is the exception" no longer holds for seats. A seat is a terminal chat with a role (Lead, Build here or teammate), and the tools it gets are the ones `Tools.toolsFor` gives that chat, adapted from each `SdkMcpToolDefinition` by name, description, zod shape and handler. No tool exists twice, so a rule fixed in `kernelMcp.ts` holds for the chat and the terminal alike, and a merge from either goes through the same `mergePr` and the same one-at-a-time guard. The Lead's seat also gets `LEAD_INSTRUCTIONS` as the server's instructions.

The transport is Streamable HTTP from `@modelcontextprotocol/sdk` on its own listener, 127.0.0.1 only, on a free port, at `/mcp`. It is stateless: each POST builds a server from the seat's current tools and ends with the response, so a Settings change reaches the next call and no session outlives a token. A request passes the hook server's `hostOk` first (a foreign Host is DNS rebinding), then a bearer token, compared in constant time over digests. Other methods get a 405 and a body that isn't JSON a 415.

Each seat has one bearer token, held in a registry as token to `{ chatId, workspaceId, role }`. A token is made when the seat's pty starts, and making another for the chat ends the first. It is revoked when the tab closes, the workspace archives and Kernel quits. A token for a chat whose workspace has archived finds no tools. The registry and server do not touch `kernel.ts`; wiring the token into the pty's environment is KERNEL-998.
