**A chat runs in one of four permission modes, and plan mode, the chat, the room and the app pick it in that order.** The modes take Claude Code's names: Manual (`default`), Accept edits, Auto and Bypass permissions. `effectiveMode` in `services/permissions.ts` decides. Plan mode comes first, then the chat's own mode, the room's, and Settings, Permissions. An agent file's `permissionMode` only tightens it. Its `plan` and `dontAsk` count as Manual, the strictest mode that still builds, because Kernel's plan step owns plan mode and a teammate held in it could never act. Auto runs as Accept edits where the chat can't run it: on Codex, under a policy that turns it off, or on a Claude model whose `supportsAutoMode` isn't true. Bypass permissions runs as Accept edits under a policy that turns it off, and on a current-branch workspace while Only in worktrees is on, which an unset value counts as. A mode Kernel doesn't know counts as Manual. While Kernel is still reading the policy or Claude Code's models, the chat runs in the safer mode and moves once the read lands. The default stays Accept edits until the onboarding step (KERNEL-457) lets a new user pick. KERNEL-447.

**In Bypass permissions, only Kernel's denials and the asks Claude Code insists on stop an agent.** Amends D-016 and PRODUCT.md's "risky commands need approval". The maintainer's call. These still stop it:
- Never allow
- a push that might reach a protected branch
- network off
- the agent file's tools line
- AskUserQuestion
- plan approval
- the SDK's critical-path `rm`

Always ask gives no opinion, and room rules don't matter. A push that might reach a protected branch is denied with "push your own branch by name", and the message names the workspace's branch: `git push origin feat/x`. That covers the pushes the guard denies or asks about elsewhere, plus a `git push` that leaves the destination to git (bare, remote only, or `HEAD` and `@` without `:dst`) and a `git` whose command is only known at run time. `--tags` alone pushes no branch and goes through. A worktree branched from `origin/main` tracks it, so under `push.default = upstream` a bare push lands on main. Every other mode leaves those pushes as they were. On Claude, `canUseTool` never allows a step by mode, because in Bypass permissions Claude Code only sends what it insists on asking about, so the user answers whatever arrives (KERNEL-433). Three gaps stay open. A git alias set in a config file that pushes without naming a protected branch gets through. So does a `remote.<name>.push` mapping that sends a named branch somewhere else. And `gh pr merge` isn't guarded in any mode. KERNEL-447.

**Always ask waits for the user inside the Bash hook in every mode but Bypass permissions.** Amends D-016, where the hook returned `ask` and canUseTool asked. The guard now asks through `awaitDecision` (KERNEL-446) with the matcher at `HOLD_TIMEOUT_SEC`, and only the user's yes lets the command run. KERNEL-433 needs this in Auto, where the classifier may answer a hook `ask` first. Manual and Accept edits use it too, so the path doesn't depend on how Claude Code routes a hook `ask` in a given mode, or on a mode switch still under way. Always allow on that card saves the command itself, since the hook has none of Claude Code's suggestions. A command the agent file's tools line refuses isn't asked about, because the gate denies it anyway. KERNEL-447.

**Kernel asks about a Claude step as the strictest mode Claude Code might run it in, and keeps Bypass permissions' denials for the whole life of a process that can take it.** Bypass is looser than the other modes about asking, and stricter about pushes, so no single mode covers a switch out of it. Theo found the gap. A chat leaving Bypass permissions was checked as Accept edits at once, which leaves a bare `git push` alone, while Claude Code still ran in bypass until it took the switch, and so ran the push. Asks now follow the strictest of four modes: the one Kernel last set, the ones a switch is still asking for, the one Claude Code last reported in an init or status message, and the one the chat should be in. Always ask has no opinion only when every one of them is Bypass permissions. Bypass's push denials hold as long as the process started with `allowDangerouslySkipPermissions`, on top of whatever the stricter mode asks. That covers a switch that is pending, one Claude Code refused, and one that landed mid-turn, since a subagent with its own bypass can still push from that process until it ends with the turn. Never allow and network off deny in every mode anyway. A refused switch leaves a note in the chat. KERNEL-447.

**Only a chat whose own choice is Bypass permissions starts with `allowDangerouslySkipPermissions`, and crossing that line restarts the process.** The SDK needs the flag for a subagent's own `bypassPermissions` too, so a session that always had it would let a repo's agent file run a subagent in bypass from a chat in Manual. Plan mode doesn't count, so a chat that plans and then bypasses has the flag from its start. A process keeps its flag for life. Moving into or out of Bypass permissions ends an idle process at once, and a busy one when its turn and background tasks end. The next message resumes the conversation in the new mode. Leaving Bypass switches the stricter mode in first. Entering it waits, and a running turn says so in the chat. KERNEL-447.

**Codex keeps `untrusted` and `workspace-write` in every mode, and Kernel reads the mode at each approval request.** Amends KERNEL-406 and KERNEL-434. The maintainer's call, from KERNEL-433:
- Bypass permissions declines what Never allow, network off and protected branches refuse, and accepts everything else. That includes commands that run outside Codex's sandbox, file changes outside the workspace, and requests for more permissions.
- Auto runs as Accept edits, and the availability line says why, until Always ask can reach the user under `auto_review`. No thread gets an `approvalsReviewer`.
- Manual and Accept edits keep KERNEL-406's rule: every command Codex asks about goes to the user.
- Plan mode asks about everything Codex asks about, where it used to follow Settings, Permissions' mode.

Thread settings never change with the mode, so a new mode applies from the next approval request, at the latest with the next turn. KERNEL-447.

**Admin policy comes from Claude Code's settings and turns a mode off on both providers.** `services/claudeSettings.ts` is the only caller of the SDK's @alpha `resolveSettings` and `filterEscalatingDefaultMode`. Kernel reads `disableAutoMode` and `permissions.disableBypassPermissionsMode` from the settings left after the trust filter, the same filter Claude Code applies, so a repo's committed files can't widen a mode. Turning a mode off is a restriction, so it counts from any source. The availability line says whether an admin turned it off through managed policy or the user's own settings did. Bypass policy holds for Codex chats too, because it is the user's admin saying no to bypass. `features/permissions.ts` reads the app's policy and every open room's at launch, a new room's when a chat there first asks for Auto or Bypass, and Claude Code's models when a Claude chat first asks for Auto. The models come from a live session's initialize answer on the active account, else a throwaway session, the way the / menu reads commands. Another account reads them again. A failed read keeps the mode off and waits a minute before Kernel tries again. KERNEL-447.

**What Claude Code says about an ask goes on the card, and Auto mode's refusals go in the chat.** `Approval.reason` takes canUseTool's `decisionReason`, `blockedPath` and `description`. On Codex it says the command is on the Always ask list or runs outside the sandbox. A `permission_denied` message from Auto mode's classifier leaves a note naming the step and the reason. Denials from rules or hooks leave none, because the tool row already shows them. Codex never runs `auto_review` here, so there is no Codex decline to report. KERNEL-447.

**Kernel hides the SDK's warning that canUseTool doesn't see every call in Bypass permissions.** The SDK prints `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` for every session that starts in bypass with a canUseTool. Kernel relies on hooks there on purpose, so the warning would only fill the log. `muteShadowedWarning` wraps Node's own warning listener and passes every other warning on. KERNEL-447.
