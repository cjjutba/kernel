**Setup runs in the background, and nothing waits for it unless the user turns that on.** Until now a teammate's brief, the Lead's messages to it and a review's briefs were held until the setup script passed, behind the "Sends when setup finishes" card. KERNEL-490 let Kernel's own chats skip that by default and kept the hold for hand-offs. A failed install then stopped a teammate that could have done most of its work without it. Now `workspace.leadWaitForSetup` (the key is unchanged, a project's own file still overrides it through `cleanupSwitch`) decides for teammates and reviews too, and `Setup.holdsForSetup` is the one rule that `Lead.buildChat` and `Workspaces.setUpWorkspace` both read.

With the switch off, the default, the brief goes out once the worktree exists and files.copy has run, then the Lead's messages that came meanwhile, in order. The setup script runs alongside in the Setup tab (`Setup.runInBackground`). The trust hold and KERNEL-542's worktree-pending hold stay as they were. The chat's queue reason is `setup` only when something is actually held for it, which is now only with the switch on. With the switch on, today's hold, card, Run again and Send anyway are unchanged.

A failed background setup holds nothing and blocks nothing. The renderer reads it as `status: 'ready'` with `setupRun.endedAt` set and `setupRun.end` not 0 (`null` when it was stopped). No type changed. A chat held for setup is a chat whose queue reason is `setup`. The Lead still hears of a failure once, worded as "{Agent} already started and keeps working without it", and `create_workspace` and `message_agent` no longer say the teammate hasn't started unless it is held.

The agent hears about it too. The teammate and reviewer rules say setup may still be running, that it shouldn't run its own install, and that a note arrives only if setup is still running. They never tell it to wait for the note, because a workspace with no setup, or one whose setup already passed, never gets one. When setup ends, Kernel stores a short note for each of the workspace's chats. A Claude session gets it as `additionalContext` on its next tool call, and a Codex session gets it appended to its next Kernel tool answer, or to the input of its next turn if that comes first. Each note arrives once and never starts a turn. When setup passes, `Sessions.restartIdle` runs so `$KERNEL_ENV` applies from the next turn.

`wait_for_merge` still holds a brief for a merge, and no longer for setup. A quit during setup with the brief already sent holds nothing: `recoverSetups` marks the setup run stopped, the setup line says so, and Rerun setup works. With the switch on, the old recovery stays.

Amends KERNEL-490, KERNEL-430, KERNEL-542, D-044, D-120, D-122 and D-123. KERNEL-1012.
