**In Bypass permissions, a push of `HEAD` goes through when the branch checked out where it runs is not protected.** `git push [-u] <remote> HEAD` (or `@`) lands on the branch checked out, so the guard reads that branch from the checkout's HEAD file at hook time, in the folder the step runs in, and lets the push through when the branch is known and not in Settings, Permissions, Protected branches. It reads the HEAD file instead of running git so the hook can answer at once. Agents ask for this push often: it is the one `prCreate` uses, and they end a commit chain with it. The guard still refuses a bare `git push` and one naming only the remote, because git picks their destination from the upstream and `push.default`. It also refuses `--all` and `--mirror`, anything naming a protected branch, a detached HEAD, and a reftable repo, whose HEAD file can't say. A push not written as plain `git push …` is refused as before: `git -C`, `--git-dir`, `-c` options, an assignment such as `GIT_DIR=…`, a wrapper, `ssh host git push`, or a command with `cd`, `pushd` or `popd` anywhere in it, since any of these can push from another checkout. One gap stays open: a `remote.<name>.push` set in the repo's config can still send `HEAD` to another branch. The guard covers the commands agents write, and it isn't a sandbox (KERNEL-230). KERNEL-687.

**New workspace branches have no upstream until their first push.** `createWorktree` runs `git worktree add --no-track`, so a branch started from `origin/main` no longer tracks `origin/main`, and a bare `git push` can't land on the base under `push.default=upstream`. The first `git push -u origin HEAD` sets the upstream to the same branch name on origin. Existing worktrees keep their upstream, and the guard above still covers them. The prompt Kernel gives an agent in a worktree tells it to push with `git push -u origin <branch>` or `HEAD`, never a bare `git push`. KERNEL-687.
