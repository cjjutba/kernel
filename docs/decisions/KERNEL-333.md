**History can delete archived workspaces, so Restore is no longer always the undo.** History had no way out. Archive removes the worktree folder, but each archived workspace kept its rows in `kernel.db`, its local branch, its checkpoint refs and its Claude Code transcripts. Delete on a History row, or on the whole tab or search in view, removes all four, plus the files agents shared from it. A deleted workspace can't be restored. This amends D-037, where Restore always brought an archived workspace back, and D-090, which leaned on Restore as the undo for the Lead's `archive_workspace`. Delete is a separate action the user confirms, and the Lead has no tool for it. `History.png` doesn't draw it, so the buttons and `ConfirmDeleteHistory` follow DESIGN.md and the other confirms. KERNEL-333.

**Delete removes four things, and keeps three.** It removes Kernel's rows (chats, chat items, shared files, and the approvals, activity and notifications that name the workspace), the local branch when the rule below allows it, the workspace's `refs/kernel/checkpoints/<id>/` and `refs/kernel/checkpoint-head/<id>` refs, and its Claude Code transcripts. It keeps the main checkout, the room folder and its `.claude/agents`, and the `kernel/backup/*` branches that Revert made, which are the user's. The checkpoint commits become unreachable and git collects them in its own time. Tasks on the Board that name the workspace are left alone, since the Board is hidden (D-104). KERNEL-333.

**Transcripts are always deleted, through the SDK's `deleteSession`.** This is the first time Kernel deletes files under `~/.claude`. It never touches that folder itself: `deleteSession(id, { dir })` removes `<id>.jsonl` and the subagent folder next to it, and the SDK owns the layout. A workspace that owns its folder (worktree mode, and no remaining record shares its path) lists the folder with `listSessions({ dir, includeWorktrees: false })`, so the sessions Kernel forgot after `/clear` or a fresh session (KERNEL-286) go too. Listing a deleted folder works: the SDK maps the path to its project folder name and never reads the path itself, and a run against the real SDK listed and deleted both sessions of a folder archive had removed. Any other workspace, every current-branch one included, deletes only the session ids its chats recorded. Its folder is the main checkout, where `listSessions` would also return the user's own Claude Code sessions and the Lead's. The SDK leaves the project folder behind, empty, and Kernel doesn't remove it, since the folder name is the SDK's to derive. A session that is already gone is ignored. Any other failure leaves the workspace in History and Delete can run again. KERNEL-333.

**A branch goes when its PR merged or nothing on it is unpushed, and a branch with unpushed commits stays unless the box is ticked.** Worktree workspaces only. A current-branch workspace has no branch of its own. The branch is kept first when another workspace record that isn't being deleted uses it (review workspaces can share one, KERNEL-265), when a worktree has it checked out, or when it is the room's current branch. Otherwise it goes when `prState` is `merged`, or when `unpushedCommits` is 0, or when `deleteUnpushed` is set. `prState` comes first because a squash merge leaves the branch's own commits off the base, so `unpushedCommits` counts merged work as unpushed. A count that can't be read keeps the branch, as in KERNEL-70. Branches shared by workspaces deleted together count once. The confirm shows how many branches hold unpushed commits and offers the box, off by default. The branch is deleted with `git branch -D`, as archive does. KERNEL-333.

**Disk goes first and the rows last, one workspace at a time.** The order is branch, checkpoint refs, transcripts, then rows. A failure halfway skips that workspace, names the reason in the result and leaves its row in History, so Delete can run again, and the others carry on. A failed checkpoint delete is logged and doesn't block. A workspace is also skipped, with a plain reason, when it isn't archived, is the Lead's, or a live workspace still waits on it (KERNEL-259), so deleting it can't break that wait. Only one delete runs at a time. The preview and the delete read the same facts, so the numbers in the confirm are the ones the delete reports. KERNEL-333.

**The database compacts the next time Kernel starts, not right after a delete.** Deleting rows leaves free pages, and the file keeps its size. `VACUUM` rewrites the whole file and can take seconds on a large one, so it never runs while the user is working. The `Store` constructor runs it after pruning and before any session starts, when free pages are over 32 MB and over 20% of the file, then truncates the WAL so the files shrink. This also reclaims what pruning frees (KERNEL-210). The toast says "The database shrinks the next time Kernel starts." Compaction needs room for a second copy of the file, and a failure is logged and leaves the file as it was. KERNEL-333.
