**Archive moves the worktree folder aside and deletes it after the workspace is archived.** `git worktree remove --force` deleted the whole folder before archive marked the workspace archived, and a Kernel worktree carries its own `node_modules`, so one of 24,000 files kept the sidebar row in place for seconds. Archive now runs in this order: stop the sessions, terminals and scripts, run the archive script, count unpushed commits, move the folder to `.trash/<name>-<time>` next to it, prune git's record, delete the branch when the rules allow, mark the workspace archived, then delete the moved folder in the background. The archive script still runs before the move because it runs inside the worktree and may need its files, such as a `docker compose down` that reads the compose file or a script that saves something out of the folder. The rename stays on the same disk, so it is instant. If it fails, archive falls back to `git worktree remove --force` and waits as before. The guards stay: a folder that is already gone only prunes (KERNEL-109), and one Kernel can't read, one that isn't the repo's worktree, or the repo itself throws before anything moves, so the workspace stays open and the sidebar shows its error. A locked worktree throws too. `git worktree remove --force` refused one before, and prune keeps a locked record, which would leave the branch undeletable and Restore blocked. Folders still to delete are saved under the meta key `trash`, each one before its rename, so a quit between the move and the archive still deletes it. A path leaves that list only once it is deleted, so a delete cut short by a quit, or one that fails, runs again at the next start without telling anyone. Kernel only deletes a saved path whose parent folder is `.trash`, so a bad entry in the list can't delete anything else. `fs.rm` unlinks a symlinked `node_modules` and leaves the folder it points to alone. Refines D-079: what archive deletes and when ConfirmArchive opens don't change, only when the deletion happens. KERNEL-284.
