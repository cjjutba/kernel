**A review round is one set of review runs on one head commit, and Kernel saves each round on the reviewed workspace.** Part of KERNEL-548. `Workspace.reviewRound` holds the latest: its number, the head, the PR, `[review] rounds` as it was when the round started, the kinds chosen, and which of them kept an earlier approval or were skipped to save usage. Kernel starts at most one round per head. A ready on a head that already had one, as when the base moved and GitHub checked the PR again, starts nothing, so a change to `[review]` committed meanwhile waits for the next round. A PR with a new number, after Continue, starts again at round 1. Only the latest round is kept: nothing reads older ones, and the verdicts already say what each found. A round that runs nothing, every kind kept or skipped, still moves the head but doesn't count toward `rounds`. Amends KERNEL-549, whose in-memory "asked" map this replaces. KERNEL-552.

**After a round, a kind that approved its head keeps that approval unless the new commits touch its paths, and every other kind runs again.** Kernel diffs the last round's head against the new one in the room's repo (`git diff --name-only --no-renames`). Empty `paths` cover every file, as `kindsFor` reads them, so the code review on its default runs again after any fix. Only a kind scoped to paths the fix didn't touch keeps its approval, as the UX review does after a fix in `src/main`. Reading empty paths as "no paths, so always kept" would have let a UX fix carry the code review's approval over code nobody reviewed. When either commit is gone, as after a force push and a gc, Kernel can't tell what changed, and every kind runs. A kept approval is carried, not trusted silently: Kernel moves the verdict's `sha` to the new head and records the commit the reviewer saw in `keptFrom`, so `kindStates`, `mergeBlock` and every reader count it with no change of their own. A kind that never reported, or was skipped, has no approval to keep and runs. KERNEL-552.

**After `[review] rounds` rounds with blockers left, Kernel starts no more reviews by itself, and the Lead brings the PR to the user.** The cap is checked when the next round would start, with `[review] rounds` from the base branch then, so raising it lets the next push run. A round that ended approved never stops the next one: the cap is about sending work back. `reviewState` says `stillBlocked` once the last round allowed is over with blockers on its head, and the update says "Still blocked after 2 review rounds" on the card and in the text. The To do line tells the Lead not to send it back and to ask the user with ask_user how to go on, both on the last verdict and on a later push Kernel didn't review. Kernel's wording lives in To do lines, not `LEAD_RULE`, which KERNEL-554 edits. KERNEL-552.

**A kind's blockers wait for the rest of their round, then reach Kernel together.** Before this, each kind's blockers woke Kernel as they came, so the author could push a fix for one while another still reviewed the old commit, and Kernel never saw two kinds' blockers side by side. Now a verdict with blockers on the head waits while another review of the PR runs, as an approval already did (KERNEL-549). When two kinds or more block, the To do line asks Kernel to send them in one message and, where two contradict, to ask the user which to follow with ask_user instead of passing both on. Kernel can't tell that two blockers contradict, so the Lead judges, with both in front of it. A review chat that stopped without a verdict doesn't count as running, so blockers never wait on it, and the next PR poll sends them. KERNEL-552.

**Near the usage limit is the rule that already holds teammates: "Pause new work when close to the limit" on, and a window at its threshold.** `Account.nearLimit(provider)` reads the saved limits for the provider's account in use, through `nearLimit` from `@shared/usage`, so reviews and Sessions agree on when it starts. As a round starts, an optional kind that would run is skipped and named in the update ("Skipped the UX review to save usage"), and the To do line asks Kernel to tell the user it didn't run. A required kind starts as usual, and its brief waits in the queue the near-limit hold already keeps, so it runs once usage drops, with no timer of Kernel's own. `reviewState` reads such a chat as `held` rather than running, and the update says "The code review waits for usage to drop below the limit." With the setting off, the user chose to keep working near the limit, so nothing is skipped and nothing waits. A skipped kind isn't brought back when usage drops during the round. It runs in the next round, since it has no approval to keep. KERNEL-552.
