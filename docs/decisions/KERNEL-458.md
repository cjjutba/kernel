**Bypass permissions on Claude runs every command inside Claude Code's sandbox, and the other modes run as they did.** Amends KERNEL-447. CJ's call: the sandbox is Bypass only for now. It follows KERNEL-436's draft. `bypassSandbox` in `services/providers/sandbox.ts` builds the session's `sandbox` option, and the runner passes it to every process started with `allowDangerouslySkipPermissions`. A chat that plans before it bypasses has the sandbox from its start, and a process keeps it for life, because crossing the Bypass line restarts the process (KERNEL-447). Bypass that runs as Accept edits gets none. Commands may write:
- the folder
- the room checkout's `.git` folder, except its `hooks` and `config`
- the main checkout's `node_modules`, when `linkNodeModules` linked it in
- Kernel's own temp folder
- the package manager caches that exist at their default paths

They reach GitHub and the npm registries and nothing else (`strictAllowlist`), may listen on localhost, and can't ask to leave the sandbox (`allowUnsandboxedCommands: false`). Kernel's hooks and canUseTool decide before a command reaches the sandbox, so Never allow, protected pushes and network off deny as they did. Network off stays the guard's job. The sandbox's domain list is fixed when the process starts, and the setting can change while a chat runs. Codex's Bypass keeps KERNEL-447's `untrusted`. KERNEL-458.

**The sandbox turns `autoAllowBashIfSandboxed` off, which the draft left at its default.** Claude Code allows a sandboxed command without asking unless told not to. In Bypass that changes nothing. A sandboxed process can also run in plan mode, and in the stricter mode a switch out of Bypass puts it in until its turn ends. With auto-allow on, both would stop asking about commands. KERNEL-458.

**Kernel denies writes to the git folder's `hooks` and `config` itself.** The draft expects both to stay read-only because the CLI protects them. Kernel doesn't depend on how the CLI finds them in a git folder outside the folder the commands run in. A hook planted there would run the next time Kernel runs git outside any sandbox, and the extra `denyWrite` costs nothing if the CLI already covers it. One gap stays open. A submodule's git folder inside `.git` has its own hooks and config, and Kernel's `git status` runs git in each submodule. This doesn't deny them, because a worktree's submodules keep their git folders under `.git/worktrees/<name>/` and denying those needs the worktree's name, which comes from a file the sandbox lets commands write. KERNEL-458.

**The git folder the sandbox opens is the room checkout's own `.git` folder, not what `git rev-parse --git-common-dir` says in the worktree.** The draft names that command. Git answers it from the worktree's `.git` file and from a `commondir` file inside the git folder, and the sandbox lets commands write both. A command could rewrite `commondir` to name the home folder, and the next process for the chat, after an idle stop or a restart, would open the home folder for writing. So Kernel takes `<room checkout>/.git` when it is a real folder, and follows no `.git` file and reads no `commondir`. For a worktree Kernel made, that is the folder git names too, and a test checks both, then rewrites the files and checks that the answer stays put. A room that is itself a linked worktree or a submodule gets no git folder, and neither does a repo in a parent folder, such as a dotfiles repo in the home folder. Commits fail in the sandbox there. The `node_modules` target counts only when the worktree's link is the one `linkNodeModules` makes and the main checkout's `node_modules` is a real folder, so a repo that commits a `node_modules` link to the home folder can't open it either. Kernel reads all of this from files, without running git, because the runner and `Sessions.start` are synchronous and a git call would block the main process. KERNEL-458.

**The chat says when Claude Code runs a Bypass chat's commands without the sandbox.** With `failIfUnavailable: false`, Claude Code 2.1.292 prints `⚠ Sandbox disabled: <reason>` on stderr and carries on unsandboxed. The SDK and the init message say nothing else about it. Kernel spawns the process itself, so it watches that stream and leaves a note with the reason. On macOS the CLI's dependency check has nothing to miss, so the line only appears where Claude Code doesn't support the sandbox. Two cases leave no line. A managed `sandbox.enabledPlatforms` that leaves macOS out turns the sandbox off silently. A sandbox that fails to initialize ends the process with `Sandbox Error`, which the chat shows as a stopped session, so that case fails closed. KERNEL-458.
