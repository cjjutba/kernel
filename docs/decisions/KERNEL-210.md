**kernel.db carries a schema version and upgrades through an ordered list of migrations.** Amends D-005. Drizzle can still come later, but the first release that changes a column needed a safe path for real users' data now. `src/main/migrations.ts` holds the list, and `PRAGMA user_version` records the last one applied. Version 1 is the schema every earlier build created. A file at 0 that already has tables is treated as version 1. Each migration runs inside one transaction with the version it sets, so a failure leaves the file at its old version. Shipped migrations are never edited. A change goes in a new one at the end. KERNEL-210.

**Kernel backs up the file before it migrates it, and keeps two copies.** The copy goes next to the file as `kernel.db.bak-v<from>`, where `<from>` is the version the file had. It uses `VACUUM INTO`, not better-sqlite3's `db.backup()`. `db.backup()` is async, and `new Store()` runs synchronously from `kernel.ts`. `VACUUM INTO` writes the same consistent copy, WAL included, before any migration starts. It refuses a target that already exists, so a leftover copy of the same version is deleted first. The copy just made always stays, plus the newest other copy. That covers a user who restored an older backup: their new copy has the lowest version and would otherwise be the one deleted. A new file gets no copy. KERNEL-210.

**A file written by a newer build is refused before SQLite opens it.** Kernel reads `user_version` from the file header, and from the newest committed copy of page 1 in a leftover `-wal`, by parsing the bytes. If it is higher than this build knows, Kernel throws "This data was written by a newer version of Kernel. Update Kernel to open it." and boot fails with that message. Opening the file with SQLite, even read-only, would create a `-shm` file. Closing it would checkpoint the WAL into the file. Parsing the bytes leaves the folder exactly as it was, so the newer build can still open it. KERNEL-210.

**Approvals record when they settled, and old settled tool input shrinks to a summary.** Migration 2 adds `approvals.settled_at` and `approvals.pruned`, and indexes `approvals(room_id, status)`, `chats(workspace_id)` and `activity(ts)`. `saveApproval` sets `settled_at` the first time an approval is saved as no longer pending and keeps it after that. Rows that were already settled at the upgrade get the migration time, so their input waits a full week after the upgrade rather than being pruned on the first start. A settled row saved by an older build after a downgrade has no `settled_at`, so pruning counts from `created_at` for it. At start and once a day, the store deletes activity older than 30 days. It also cuts the input of tool approvals settled more than 7 days ago down to its string fields, each cut to 200 characters, plus numbers and booleans. That keeps the command, file path or URL the Inbox and approval cards show, and drops the contents of a Write. Pending approvals, plans, questions, hires, chats and chat items are never pruned, so History transcripts and plan cards stay whole. Activity older than 30 days also leaves the "last active" times, which read the same log. KERNEL-210.

**A row whose JSON doesn't parse is skipped and logged, not thrown.** One bad row used to empty its whole list. `Store.all()` now drops that row and warns in the console, and a single read such as `store.approval(id)` treats it as missing. KERNEL-210.
