**New chat's composer picks where the chat works, and the pick reaches the engine.** A chip beside + names the choice and opens a menu titled Workspace with Current checkout, New worktree and Previous worktree. It replaces the + menu's Run in and Branch rows, and the line "Work on the current branch, not a new worktree." that New chat appended to the first message. `lead.start` takes `where` (`{ kind: 'current' }`, `{ kind: 'worktree' }` or `{ kind: 'previous', workspaceId }`) and `newLeadChat` passes it to `cutWorkspace` as its `mode`, so the folder follows the pick whatever Settings, Git and worktrees, Workspace type says. Amends one-lead-chat, which cut every new chat by that setting alone.

**Left out, `where` follows the project's file and Settings.** The box sends it only when the pick differs from Settings' workspace type, or is a previous worktree, so a box nobody touched behaves as before. The default pick on screen is the setting. The pick is remembered per project in the box's draft (`place`, and `previous` for a previous worktree) and survives a send and a restart, as Worktree or Local did. A remembered previous worktree that is no longer on offer falls back to the pick before it.

**Current checkout is the project's own folder on whatever branch is checked out,** cut with the existing baseline snapshot, so its diff shows only the chat's own work. With "One current-branch workspace per project" on, another open workspace on the checkout keeps a second chat off it: the row is disabled with the holding chat's title under it, and the engine refuses `where: current` with a sentence naming that chat and pointing to New worktree. The renderer and the engine read the same rule (`checkoutHolder` in `@shared/leadWorkspace`). A taken checkout shows New worktree as the pick.

**New worktree is a fresh worktree and branch, set up as before.** The base branch picker belongs to this option, so its Branch from row shows under New worktree only while it is picked. The base is ignored for the other two choices.

**Previous worktree adds a tab to the earlier chat's workspace; it does not cut a second chat record onto its folder.** A workspace owns its folder, branch, ports, setup and archive, and a Lead chat workspace is one record per chat (`threadId`). Pointing a second workspace record at the same path would give two owners to one folder, so archiving one would delete files the other still uses, and each would move the folder to a fresh branch after a merge. A larger engine change (a folder with several workspace records, or a chat detached from its workspace) was not worth it for this pick. So `where: previous` calls `tabIn` on that workspace: the new chat is a new tab of the earlier chat, in its folder and branch, with its message sent there. The sidebar shows one row for that chat, and the new tab opens on it. Only a workspace that can take a tab is offered and accepted (`canTakeTab`): a chat's own worktree that is ready, whose folder exists and whose chat is open. The menu lists up to five, the chat touched last first, each with its chat title, branch and age. The engine refuses an archived, missing or other project's workspace with a sentence.
