**A room's scripts and files.copy list run only after the user trusts that exact text, and files.copy can't leave the repo.** `.kernel/settings.toml` is meant to be committed, and `scripts.setupOnCreate` defaults to true. Cloning a hostile repo, or pulling a teammate's change to that file, used to run its setup script in the login shell for the next workspace, with the user's rights. A `files.copy` entry like `../../.ssh/id_rsa`, or a symlink pointing out of the repo, copied that file into the worktree, where the agent could read it.

Kernel now hashes what the room would run: the setup, run and archive scripts and the files.copy list, read after merging settings.toml and settings.local.toml (`scriptsToTrust` and `trustHash` in `services/settings.ts`). A room with no scripts and Kernel's default copy list (`.env`, `.env.local`) has nothing to trust. The trusted hashes live per room in `trust.json` in Kernel's data folder, never in the repo, so a commit can't trust itself. Each room keeps its last 20, so going back to an older version doesn't ask again. Removing a room forgets them.

A new workspace whose room text isn't trusted is created with its worktree and its node_modules link, and nothing else. It gets the status `trust`. Its brief, and any Lead messages sent after it, wait in the chat's queue the way they wait for a failed setup. Kernel pushes `room.trust` with the scripts, the copy list, the hash and the held workspace ids. `rooms.scriptTrust` returns the same thing on demand, or null. `rooms.trust({ roomId, hash })` saves the hash and releases every held workspace in the room. Each one copies its files, runs setup and sends its brief, the same as a workspace that never waited, and a failed setup ends in `failed` with Run again as before. If the text changed after the user read it, the hash no longer matches and `rooms.trust` rejects and pushes the new text.

The same check covers every other place the text runs. Run again and the Setup and Run buttons ask for trust instead of running. Run after setup is skipped. Archiving never waits: an untrusted archive script is skipped, with a line in the archive output, and the workspace archives. Restore skips the copy.

Two writers count as trusted without asking. Scripts and files saved through Settings, Scripts (`settings.setRoom` with `scripts` or `files` in the patch) trust the room's whole merged text, because that screen shows all three scripts and the copy list. Other room settings saved there trust nothing. The settings.toml Kernel writes for a new room, holding its own install command (D-078), is trusted too. A repo that brought its own settings.toml is not.

`copyLocalFiles` resolves each entry with `realpath` and refuses anything outside the repo root: `../` paths, absolute paths, and symlinks in the repo that point out. It also refuses to write through a symlink in the worktree, a file or a folder on the way, since a repo can commit those too. Missing files are skipped quietly as before. The setup output names each refused entry. Confinement applies to trusted text too.

Existing rooms get no free pass after the upgrade. A room that already has scripts or its own copy list has no trusted hash yet, so its next workspace asks once. After that, unchanged text never asks again.

Until the trust dialog and banner land (a follow-up in the Workspace lane), nothing in the renderer calls `rooms.trust`, so held workspaces wait. The Lead's own workspace, which runs no setup, isn't held. The Lead's `create_workspace` result doesn't yet say a workspace is waiting for trust, but `message_agent` does. The room setup's "Install dependencies" step, which runs the lockfile's install command in a fresh clone, is not covered here. KERNEL-209.
