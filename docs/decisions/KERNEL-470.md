**A number in a wait names the PR with that number, or the GitHub issue with it that a workspace builds.** GitHub numbers issues and pull requests in one sequence per repo, so in a room `#41` (or `41`) in `wait_for` or `wait_for_merge` is one or the other, never both. Before, `#41` only matched PR numbers, and a wait on a GitHub issue a teammate was building was refused. Kernel tells a GitHub issue by its source's tracker tag, not by the leading `#`. A source saved before KERNEL-462 has no tag, and its id still tells, as it did then: `#41` is GitHub, anything else Linear (`issueTracker` in `services/trackers/index.ts`). Issue keys like `KERNEL-197` match in any case, from any tracker. KERNEL-470.

**A hand-off's blockers only count work on issues from the tracker that named them.** `waitOnBlockers` takes the tracker from the new workspace's own issue source. `issueSource` tags that source in the same call that reads the blockers from the room's tracker, so the tag is the tracker that named them. Asking the room for its tracker again could give a different answer if its settings changed in between. A teammate building a Jira issue with the same key as a Linear blocker doesn't count, and an untagged old record with a Linear key does. KERNEL-470.

**A new workspace asks the room's tracker for labels, and to start the issue, only when the issue came from that tracker.** `issueLabels` and `startIssue` take the issue source instead of its key, and skip an issue from another tracker. This replaces the `#` checks in `features/workspaces.ts`. So a GitHub issue picked in New workspace in a GitHub room now reads its labels, and a `bug` label starts it on a `fix/` branch, as a hand-off from Kernel already did. A `#41` picked in a Linear room still asks Linear nothing. KERNEL-470.
