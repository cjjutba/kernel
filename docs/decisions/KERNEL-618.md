**An MCP server added, changed or removed on any Claude login reaches every other login, and Kernel tells a removal from an addition by what it last synced.** Amends KERNEL-560, whose copy replaced an added login's `mcpServers` and `projects` with the CLI login's, so a server added on the account (`claude mcp add` in a session or a terminal running on it) was gone at its next process.

- `syncClaudeConfig` in `services/providers/claudeHome.ts` runs before each Claude process on an added login, as the copy did. Each `Providers.claudeEnv` also runs it for every added login, at most once every 2 seconds, so a server added on one account reaches the CLI login and the other accounts at their next process, without a switch back first.
- It merges three ways, server by server, for the user servers (`mcpServers`) and each project's local servers (`projects[path].mcpServers`). The base is what the account held after Kernel last synced it, kept in `kernel-mcp-base.json` in the account's folder. A server the account added, changed or removed since then goes the same way on the CLI login's `~/.claude.json`, unless the CLI login changed it too, and then the CLI login wins. The account then gets the CLI login's `mcpServers` and `projects` as before. A server removed on either login is gone from the base after the next sync, so it never comes back.
- Only what the account's file still has counts as a change. `claude mcp remove` leaves an empty `mcpServers`, so a file with none, or a project the account lacks, changed nothing there. A `.claude.json` that was reset or deleted never removes servers from the CLI login.
- With no base yet, as on the first sync after this change, a server only the account has counts as added there. That keeps a server the user just added. It also brings back a server removed on the CLI login since that login's last copy, once. Losing a server the user added is worse.
- A project only the account has comes along with its servers, as the account's whole entry, since Claude Code expects a project's other fields. The rest of `projects` still follows the CLI login, as KERNEL-560 decided.
- Claude Code 2.1.292 writes `.claude.json` through `saveConfigWithLock`: it takes `<file>.lock`, a folder its lock library makes and renews every 5 seconds, then reads the file again and applies its change to what it read. Kernel takes the same lock on both files for its read and write, so neither undoes the other. While a CLI holds either lock, Kernel changes nothing and tries again at the next process. A lock older than 10 seconds was left behind, as the lock library counts it, and Kernel removes it. `.claude.json.lock` stays out of the links into `~/.claude`.
- A `~/.claude.json` that is a link stays a link: Kernel writes the file it points to, at that file's mode. KERNEL-618.

**Claude Code reads the Keychain only through `/usr/bin/security`, so a Kernel update that bundles a new Claude Code shows no Keychain prompt.** Checked on CJ's Mac on 2026-10-13 with Kernel's bundled 2.1.292 and Homebrew's 2.1.260.

- Neither binary links Security.framework. Both read with `security find-generic-password -a $USER -w -s <item>` and write with `security -i` and `add-generic-password -U`. An item made that way trusts `/usr/bin/security` in its access list, with the partition `apple-tool:`. A new Claude Code binary is not on that list and needs no place there.
- A test item written the CLI's way under a temp folder's name read as signed in on 2.1.260, then 2.1.292, then 2.1.260 again, in 0.2 to 0.3 seconds each, with no prompt. The check deleted the item afterwards. `Claude Code-credentials` and `Claude Code-credentials-0175ce98`, CJ's two real items, list only `/usr/bin/security`.
- A prompt can still show: a login keychain that is locked, or an item another app made or changed. Then `security` waits on it. Claude Code 2.1.292 gives a Keychain read 2 seconds, then kills `security` and reads the login as signed out. So `auth status` and sessions don't hang. They say "not logged in", and before this change Kernel marked the account signed out and held its chats until a sign-in. KERNEL-618.

**A login whose Keychain item waits on a prompt reads as waiting for Keychain access, not signed out, and its chats wait only while the prompt is up.**

- When `auth status` reads an added login as signed out, or doesn't answer, where Kernel last read it signed in, and when a session on the account in use fails as signed out, Kernel reads the login's item itself through `/usr/bin/security`, discarding the secret (`Keychain.access`). An item that reads, or is gone, leaves the sign-out as it was. A read still running after 5 seconds is waiting on a prompt.
- Kernel then keeps its read, and with it the prompt, up for 2 minutes, so someone can click Always Allow. Meanwhile the row carries `keychainWait`, the sign-in Kernel last read stands, and the Inbox gets one notice a day. A session refused on the account in use holds Claude's chats under `keychain` instead of `auth`. Allowed, the login is read again and the chats go on. A switch to another account lets them go too. If nobody allows it in time, the hold lifts so no chat waits forever, the row still says it waits, and no new prompt shows for 10 minutes. A refused session in that time fails like any failed turn.
- One check runs per login at a time, so a read and a refused session don't raise two prompts. MCP sign-in sharing skips a waiting login, since its synchronous read would hold the main process for up to 5 seconds.
- Auto-switch and the limit banner never pick an account that waits on its Keychain. KERNEL-618.

**Two Claude accounts in one claude.ai organization have room only by their own windows.** Seats in a Team or Enterprise organization can share limits, so a reading of one seat says nothing about the other.

- Claude Code 2.1.292's `auth status` gives `orgId` and `orgName` beside `email` and `subscriptionType`. Each login's `.claude.json` holds `oauthAccount` with `organizationUuid`, `organizationType` (`claude_max` and `claude_pro` on CJ's logins), `organizationRateLimitTier` and `seatTier`. The model caches (`additionalModelOptionsCache`, `modelAccessCache`, `orgModelDefaultCache`) hold no organization. CJ's two logins are in two personal organizations, so this doesn't happen on his Mac today.
- Kernel keeps `orgId` for each added login (KERNEL-616) and now for the CLI's own login too. Each Claude row carries `sameOrg`, the ids of the other accounts in its organization, for "Same organization as Work".
- `switchChoices` in `@shared/usage` holds the rules both Kernel's own switch (`Providers.spares`) and the limit banner can use. An account in the same organization as the one in use counts as having room only when a 5-hour or weekly window was read on it and none is rejected. Any other account never read still counts, last, as before. KERNEL-618.

**When no other account has room and one is signed out, `switchChoices` names it, so the limit banner can say "Personal is signed out. Sign in to switch to it."** Auto-switch still skips signed-out accounts. `signedOut` is the signed-out subscription account that would have room by the same rules. It is unset when any signed-in account has room, an API key account included, since the banner already offers that one with "billed per token". Sign in on the banner can call `providers.signIn` with the account's id. KERNEL-618.

**A chat waiting on a permission card or a plan approval during a switch finishes its turn on the account it started on, as it already did.** A turn waiting on a card is running, so `restartProvider` marks its process stale and ends it only when the turn ends. On Claude that covers both cards, ExitPlanMode included, and an approved plan is carried out in the same turn, on the old account. On Codex an approval card is the same. A Codex plan waits after its turn ended, so that turn already finished on the old account. The switch ends the idle process, the plan card stays answerable, and the approved plan's work is the chat's next turn, which runs on the new account with "Now on Personal". Tests prove each case in `sessions.test.ts` and `codexRunner.test.ts`, so no code changed. KERNEL-618.
