**Send now goes over the agent limit, and the engine tells the renderer why a queue waits.** Kai's KERNEL-200 brief queued with 5 of 5 slots in use, and Send now did nothing. `Sessions.sendNow` fell through to `drain`, which checked the limit again and stopped. Pressing Send now is the user choosing to go over, so an idle chat held only by the limit (D-094) now sends at once. The running chats keep going and the extra turn counts against the limit until it ends. A user pause, offline and setup still hold Send now. A room a usage limit paused still sends past the pause, as before. The reason is computed from live state on every check and never saved with a held brief, because the state it describes (a running turn, a pause, a free slot) doesn't survive a restart. `chat.queue` events carry it as `why`, and `chats.queueReason` returns it on request. A step that changes both the queue and the reason, such as a held message going out, sends one event once the step ends, so the renderer never sees a halfway state. Amends D-094. KERNEL-271.
