**A comment on a shared file reaches its agent as a plain user message.** The text part names the file, the version and its source path, then a Where line and the note quoted with `> `. HTML and images also get the crop around the spot as an image part. Markdown gets no image, since the block's own text already says where. The message has no `from`, so the chat shows it as the user's, and the Lead's loop guard starts over as it does for any message the user types (KERNEL-125). The agent answers by sharing the same path again, which adds a version. When the user comments on an older version, the first line adds "You have shared v3 since." so the agent knows to check its latest copy before changing anything. PDFs take no comments. KERNEL-310.

**A comment goes to the chat that shared that version, else the workspace's first open chat, else a new chat.** A chat counts when it is open, isn't a terminal and is still in the same workspace. The new chat opens the way a message to a workspace opens one, with the agent's model. A file the Lead shared goes to the Lead chat of its room, which Kernel reopens when it was closed. An archived workspace refuses the comment and says to restore it from History, rather than reopening work the user put away. A busy chat queues the comment like any other message. A chat that `sessions.hold` still holds for setup queues it too, with the reason "setup". Kernel doesn't use the first-setup hold that holds the Lead's brief, because a comment sent from there would carry the Lead's name. A workspace that has shared a file has finished its first setup anyway. KERNEL-310.

**Comments are stored per version, in their own table.** `shared_comments` keeps each comment with its file and version number (migration 4), so pins show on the version they were made on. A comment records the chat it went to and the id of its message there, or an empty id while it waits in the queue. Deleting a room or workspace deletes its comments with its shared files. KERNEL-310.

**Pins run their page scripts in isolated world 999.** Hit, locate and scroll never touch the page's own globals, and the page can't see or change them. The scripts are plain strings, not `fn.toString()`, so the bundler can't rename or wrap anything inside them. A pinned element's selector is `#id` when that id is unique on the page. Otherwise it is a chain of up to 8 steps of tag, at most two plain class names, and `:nth-of-type` when a sibling has the same tag, stopping at the body or at an ancestor with a unique id. KERNEL-310.

**The renderer speaks in Kernel's CSS pixels, the page in its own.** Points and rects in pin requests, and the rects locate returns, are Kernel CSS pixels from the preview's top left, the same space `place` uses. The main process multiplies by Kernel's zoom factor on the way in and divides on the way out. The anchor that hit returns, and the scroll values, are in the page's own pixels, because the agent reads them against its own page. The crop around a pin is 24 px of padding around the element or point, at least 320 by 200 and at most 1200 by 800, clamped to the preview. KERNEL-310.
