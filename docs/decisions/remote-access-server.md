**Remote access is a server inside the app's main process, off by default, that answers the same handlers as the window.** Kernel has one engine, in the Electron main process, with its sessions, worktrees and database. A second process would need its own copy of all of that or a way to share it. So the server (`services/remoteServer.ts`, started by `features/remote.ts`) runs next to the window and calls the `Handlers` map the IPC uses, which means a call from a phone behaves exactly like one from the window. `ws` carries the WebSocket and `qrcode` draws the pairing code. The setting is `remote` in app settings (`enabled` false, `host` `local`, `port` 47100). A busy port moves it to the next free one, up to 20, and `remote.status` reports the real port. The server follows the setting when it changes and stops with the Kernel.

**The protocol is JSON over one WebSocket, `GET /ws`.** The client sends `{ id, channel, req }` and gets `{ id, ok: true, res }` or `{ id, ok: false, error }`, in any order. The server pushes `{ event }` for every `PushEvent`. `channel` must be an own key of the handlers map, so `constructor` and `__proto__` are unknown. A message over 1 MB closes the socket (ws's `maxPayload`), binary frames and invalid JSON get an error with `id: null`, and a socket may have 32 calls in flight. At most 20 sockets are open. `GET /` serves a placeholder page and has a seam, the `assets` option, for the web client's files, which a later change passes the built renderer folder through. `POST /pair` takes `{ code, name? }` as `application/json` only, at most 4 KB.

**Pairing uses a one-time code and the device keeps a token.** "Pair a device" makes a code of 160 random bits, good once and for 5 minutes, kept in memory only as its SHA-256 and gone when the server restarts. At most 5 are open. The URL is `http://<host>:<port>/#pair=<code>`: the code sits in the hash, so no server log or Referer header sees it. `POST /pair` spends the code on the first try that finds it and returns a 32 byte random token, base64url, once. The database keeps only its SHA-256 (`remote_devices`, migration 10) with the device name, created and last seen times and an expiry 30 days out. A connection compares the hash of its token with every live device's hash using `timingSafeEqual`, so a copy of kernel.db can't connect and timing says nothing about which row matched. A socket checks the expiry on each message and each push. Failed pair attempts are limited to 5 a minute per address and 20 in all, then 429 with Retry-After. A device is listed in Settings, Remote access and revoked there, which deletes its row and closes its sockets with code 4401.

**Where a call may come from is checked before the token.** The Host header must carry the server's own port, and for `This Mac only` a loopback name, so a DNS rebinding page can't reach a local-only server. With `Other devices on my network` any host name is accepted, since a Mac has many, and the token is the guard. A request with an `Origin` header must have the server's own origin, so a page on another site can't call it. No CORS headers are sent. The token comes as `Authorization: Bearer`, as the subprotocol `kernel.token.<token>` next to `kernel.v1` in `Sec-WebSocket-Protocol` (a browser sets it with `new WebSocket(url, ['kernel.v1', 'kernel.token.<token>'])`, and the server answers `kernel.v1`, never the token), or as `?token=`. Prefer the first two: a URL can land in a proxy log, a history or a crash report, and a header can't. The query stays as the fallback for a client that can set neither, and the server never logs URLs. In network mode the traffic is plain HTTP on the local network, which Settings, Remote access says beside the host choice: use it on networks you trust, or through Tailscale.

**A paired device is a remote control for the chats, not an admin console, so it may call only what is on an allowlist.** The first version refused a list of dangerous channels and let everything else through, which meant every new channel was open to a phone until someone remembered to list it. The reverse is the rule now. `ALLOWED_CHANNELS` in `services/remoteChannels.ts` names what a device may call, and anything else is refused, including a name that is no channel. `REFUSED_CHANNELS` lists the rest, so every channel in `KernelApi` is classified exactly once: a type check in that file fails the build for a channel in neither list, and `test/remoteServer.test.ts` fails for one in both or for a name that is not a channel. A new channel is therefore refused until someone allows it on purpose.

The allowlist covers following work: reading projects, workspaces, chats and their transcripts, queues, diffs, changed files and file contents inside a workspace, plans, approvals, notifications, PR status, activity, usage, models and settings (`settings.get`). It covers steering it: sending, queueing, stopping and retrying in a chat, answering approvals and questions, starting a chat, a Lead chat or a workspace, and the PR actions the user would click that need no app on the Mac (`pr.create`, `pr.merge`, `pr.ready` and the rest). File reads go through `workspaces.readFile`, `readImage` and `resolvePaths`, whose handlers keep the path inside the workspace and the agent's own scratchpad (symlinks included, covered by `test/files.test.ts`), so a device can't read the rest of the Mac.

Refused: every settings write (`settings.set`, `settings.setProject`, review settings), project scripts and `scripts.*`, `providers.*`, `projects.add`, `update`, `setIcon`, `remove` and anything else that takes a path outside a workspace, `env.*`, `terminal.*`, hooks, accounts and sign-ins, integrations, MCP, updates, `app.*`, `files.*`, deleting, discarding or reverting work, the agents' team and instructions, `reviews.overrule`, every `system.*` channel and every `remote.*` channel, so a paired device can't pair another, list its peers or turn the server off.

A few allowed calls are checked for what they carry. `chats.configure` and `lead.start` refuse a `mode`, so the permission mode and Bypass can't change from a phone. `chats.create` refuses `kind: 'terminal'` and a preset, so a device can't open a raw shell. `approvals.decide` refuses `always` and `scope`, so a device can't add a permanent allow rule or hire an agent. `pr.merge` refuses `override`. `workspaces.create` refuses `mode: 'current'`. A message part with `src` or `path` is refused in `chats.send`, `projects.brief`, `workspaces.create` and `lead.start`, because `src` makes Kernel copy a file from the Mac into the chat. Text, skills and inline images go through.

**A socket is dead the moment its device is revoked, its session ends or the server stops.** `closeDevice`, a session found expired at a push and `stop()` mark the socket dead, forget it, send the close frame (4401, or 1001 for a stop) and destroy it with `ws.terminate()` 250 ms later, so a client sees why. The message handler checks before each call, and again before it answers, that the socket is open, not dead, and its device row still exists and has not expired, so a revoke made in the moment between the check and the call, or by another path, still stops it. A call that was already running is not cancelled, but its answer is never sent.

**A push goes to every connected device.** All paired devices belong to the same user, who is the only one who can pair one, so a push needs no filter by device. If Kernel ever has more than one person on a Mac, this is the line to revisit.

**A later headless `kernel serve` would reuse `RemoteServer`, `RemoteAuth` and the channel list unchanged.** They take the handlers, the store and the options as arguments and import nothing from Electron. A headless process would build a Kernel without the window, and give `RemoteServer` its handlers and a folder of web client files.
