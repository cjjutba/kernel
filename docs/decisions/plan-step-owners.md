**Every step of a plan has an owner, and the user can change it on the card before approving.** The owner is Kernel (the Lead does the step in its own folder) or a teammate who takes tasks. Since one-lead-chat the Lead both builds and hands off, so which of the two a step gets is a choice the user may want to make, not a detail the Lead settles alone. `request_plan_approval` tells the Lead to write an owner on every step, keeping the "task · owner" text form. `parsePlanSteps` reads "Kernel", or the Lead's own name or id, as the Lead itself. A step with no owner, or an owner Kernel does not know, is Kernel's, and the card shows it as Kernel. The picker offers an agent only if `takesTasks` is true for it (`member`, or not the Lead when Kernel has not resolved it), it is not the Lead and it is not retired. A helper is left out: an agent whose tools can't open a pull request, one written as a subagent, one listed under `helpers` in the project's team settings, and Kernel's own code review. A reviewer is not left out because of its role, so a reviewer agent that can open pull requests is offered like any teammate, while a read-only one is not. An unknown owner in a title stays in the title as plain text.

**The decision carries the owners, one per step in the plan's order.** `Decision` on an allow has `owners?: PlanOwner[]`, where an entry is a teammate's agent id or null for Kernel. The card sends it only when the user changed something, and a pick put back to what the Lead proposed counts as no change. The Inbox handler keeps an owner only when it is null or the id of a teammate who takes tasks in the plan's project, and replaces anything else, and any entry past the last step, with the proposed owner, so a bad payload can never hand a step to the Lead's own id, a helper or a stranger. `PlanStep.ownerChanged` records which steps the user moved. A step Kernel does has no `agentId`, and its task records the Lead as its agent.

**The approval reply lists who does what.** For a plan with steps the Lead's reply names each step with "you do it yourself" or "hand it to <name>", and says in one line which steps the user changed ("Keep their choice") so the Lead does not argue it again. It then says to carry the plan out as those owners say (`CARRY_OUT_OWNED`) instead of choosing for itself. A plan with no steps, such as an ExitPlanMode plan, keeps the older reply (`CARRY_OUT`). The same lines go out after a restart, through the same path.

**Remote access passes the owners and nothing else.** `approvals.decide` from a device may carry `owners` only as a list of agent ids and nulls. The refusals for `always` and `scope` are unchanged.

**The picker lives in the plan card's task rows**, as a button with Kernel first and then the teammates, shown only while the plan waits. Its picks are kept by approval id outside the component, since the card in the transcript and Approve on the composer are different components. The menu is drawn over the window so the scrolling transcript can't clip it.
