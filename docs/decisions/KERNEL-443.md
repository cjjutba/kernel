**A copy outside Applications offers once to move there, and moves only after a yes.** Squirrel replaces the app where it runs. A copy opened from the disk image, or one macOS translocated because it was opened where it was downloaded, is read-only, so an update downloaded and then failed at install. Now a packaged copy that Electron says is outside Applications shows "Move Kernel to Applications so it can update itself?" at launch, before the kernel starts, with Move to Applications and Don't move. Kernel calls `app.moveToApplicationsFolder` only after Move, and Electron then quits and opens the moved copy. When Applications already has a Kernel that isn't running, a second dialog asks before Electron puts it in the Trash. A move that throws says why and tells the user to drag Kernel into Applications in Finder. Kernel asks once: any outcome but a successful move writes `asked-to-move` into the data folder, and later launches skip the dialog. Dev runs, headless runs, fixtures and the smoke test never ask. `runsFrom` (`loginItem.ts`) checks `inApplicationsFolder` as well as `isInstalledCopy`. A copy in Applications under another name ("Kernel Beta.app") isn't the installed copy for the login item, but Electron's move does nothing for it and Squirrel can update it, so Kernel leaves it alone. KERNEL-443.

**A copy outside Applications never checks for updates, and says why.** The updater gets the place from `runsFrom` and sets `AppUpdate.blocked`: "Kernel is running from Downloads. Move it to Applications and open it from there." It logs that once at start, never contacts GitHub, and Settings, About shows it after Check for updates. Before, the failure became "Could not check for updates" with no reason. A writable folder outside Applications, such as `~/Apps`, could install an update, and it loses updates too. One rule the user can act on beats guessing which folders Squirrel can write to, and downloading a release every 4 hours that might fail at install wastes the download. KERNEL-443.
