**A review blocks only on real problems, and a re-review checks only what it blocked on.** A blocker is one of these: an acceptance criterion fails, a user would hit a bug or regression, a CLAUDE.md rule is broken (a secret, code added to kernel.ts, a hex value in screen code, a missing release note, a file outside the issue's Owns), or a check fails. Nothing else blocks: test strength, naming, style, doc wording, decision-file bookkeeping, refactors, "could also". Of 15 reviews in the maintainer's room, 7 went back at least once, and about half of those blockers were nits. Each one cost a full round of fixes, CI and another review.

`BLOCKER_RULE` in `services/handoff.ts` holds the list. `reviewRule` and the `submit_review` description use it, and both theo.md files copy it word for word, which a test checks. A reviewer approves when nothing blocks and puts minor findings in the summary as at most three short notes. Each blocker is one or two sentences with its file and line, and no code, because the author picks the fix. A re-review checks the earlier blockers and anything the fix broke, and raises nothing new unless the fix caused it. The reviewer reads the PR's checks instead of running the suite, runs shots only for screens the PR changes, and runs a test only to confirm a bug it suspects. The Lead passes on blockers and nothing else, and mentions the summary's notes to the user in one line.

Only the prompts change. `submit_review` still takes approved or blockers plus a summary, with no field for notes, so nothing in the Team update card or the renderer changes.
