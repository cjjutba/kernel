**The PR poll runs one at a time and reads each PR on its own schedule.** `Prs.pollPrs` returns the poll already running when the 45 second timer fires again, so a hung `gh` can't start a second poll behind the first. Nothing is read while `account.network` says the Mac is offline. A read where `gh` answers nothing for a workspace that has a PR number counts as a failure, and so does a read that throws. Each failure in a row doubles that PR's wait from 90 seconds, up to 10 minutes, and the first good read puts it back on every poll. A ready or draft PR whose read hasn't changed in 24 hours waits 5 minutes between reads. A change on one of those reads puts it back on every poll. Waits count from the poll's start, less a second, so a PR due every poll is read every poll however long the reads before it took. The schedule lives in memory, so after a restart every PR is read at the full rate for a day before it can go quiet. With ten open PRs that have waited a day, that is 110 reads an hour where it was 800. KERNEL-216.

**The poll and the quick re-check take turns.** A PR waiting in KERNEL-283's quick re-check queue is skipped by the poll, since the re-check reads it within 15 seconds anyway. When the re-check's timer fires during a poll, the re-check waits for that poll to finish, so the two never read GitHub at the same moment. Offline, the re-check reads nothing and marks its PRs as read, and the first poll back online reads them. A re-check read counts toward a PR's backoff like any other read. KERNEL-216.

**A PR read that changes nothing saves nothing.** `refreshPr` compares the fields it would write with the workspace as stored and skips `updateWs` when they all match. The quick re-check from KERNEL-283, the loop guard and the PR notes run as before. Each push of a workspace also refreshes the room's tasks, so the poll no longer refreshes every task every 45 seconds. `Tasks.refresh` reads the room's pending approvals once per refresh, not once per task. KERNEL-216.

**A command has a minute unless its caller asks for more.** `exec` stops a command after `EXEC_TIMEOUT_MS` (60 seconds) when the caller gives no `timeoutMs`. The command runs in its own process group, which gets SIGTERM and then SIGKILL 5 seconds later, so a git hook or pager it started stops with it. stdout and stderr keep their first 10 MB each. Work that grows with the repo or waits on the network gets `SLOW_MS` (10 minutes): `git worktree add`, both `git push` calls, `git add -A` for a new room and checkpoints. `run` throws "didn't finish in N seconds" for a command that ran out of time. KERNEL-216.

**Setup and archive scripts have 15 minutes, and run scripts have no limit.** The limit is `scripts.timeoutMinutes` in the app settings, from 1 to 240, with no control in Settings yet. A setup that runs out of time stops its process group, logs "Setup didn't finish in 15 minutes" and fails the workspace, with `timeout` as its failure code so the Lead hears it didn't finish in time. An archive script that runs out of time is stopped and the archive goes on. Every workspace script gets its stdin closed, so a script that asks a question reads nothing instead of waiting forever. Run scripts are dev servers, which are meant to keep running. KERNEL-216.

**Script and terminal output go to the window every 50 ms.** `script.output` carries `lines`, one script's lines in order, and the window adds them in one update with `keepLines`, which trims the way `keepLine` does one line at a time. `terminal.data` keeps its string and joins the chunks of each 50 ms, since writing the joined string to the terminal draws the same thing as writing each chunk. A script's lines go out before its exit and before the URL a line printed. A terminal's replay drops output waiting for its batch, because the replay already holds it. Kernel's own one-off lines, such as "Setup failed with exit code 1", go out at once as a batch of one. KERNEL-216.
