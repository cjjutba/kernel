**A terminal Lead's launch prompt names no plan card.** The prompt a terminal Lead starts with (`--append-system-prompt`) is built with `leadRule(mode, true)`: the plan line says to plan, then exit plan mode for approval with Claude Code's own plan dialog, and it names no `request_plan_approval`. The prompt and `TERMINAL_LEAD_INSTRUCTIONS` now agree. A chat Lead keeps the old line. KERNEL-1029.

**Messages for a terminal teammate are kept in SQLite.** The queue of `message_agent` messages and review blockers is saved in the `seatMessages` meta key each time it changes, and read back on first use after a restart. The delivery rule is unchanged: after a `Stop` with no keystroke since, one bracketed paste, then Enter, once. Kernel never types at a restart. A message waits for the seat's next clean `Stop`. A message for a tab that is closed or gone is dropped when read back. An identical message already waiting is not queued twice. KERNEL-1029.

**Kernel's own nudges use the terminal delivery.** The nudges in `prs.ts` (create PR, fix conflicts, checks or review, update branch, pull after an update), `waits.ts` (a wait ended) and `baseWatch.ts` (the base moved) go through `TeammateSeats.nudge` when the teammate is a terminal seat, so they wait for a clean `Stop` like any message. Reviews always run in Kernel, so their nudges are unchanged. Plan changes from an approval card do not apply to a seat, whose plans are answered in the terminal. KERNEL-1029.

**A closed Lead tab keeps its updates, and they go to the chat Lead for that work.** The queue of team updates for a terminal Lead tab is no longer dropped when the tab closes. A closed tab has no way back, so it is gone for good: its queued updates go at once to the tab `leadUpdateTarget` names for that work (another tab of the same Lead chat, else the newest open Lead chat) as a Team update that says it comes from a tab the user closed. If that chat can't take it yet, because it is mid-turn or paused, the updates stay on the closed tab's queue and the next flush tries again. A terminal Lead tab that is open gets them in its own queue, as before. If the project has no open chat tab at all they wait, and nothing is dropped. KERNEL-1029.

**Archiving a workspace keeps its terminal tabs' updates for the restore.** Restoring a workspace resumes the same session in the same tab, so its queue stays, the inbox row says the updates wait for the restore, and the restore raises the row again. The updates reach the terminal at its next prompt or `check_team`, as before. A workspace deleted from History has no tab to come back to, so its queue is rehomed like a closed tab's. KERNEL-1029.

**The `seat.updates`, `notifications.answer` and `Chat.seat` shapes did not change.** The renderer reads them as before. KERNEL-1029.

**The renderer reads the waiting count with `seat.pending`.** `seat.updates` only fires on a change, so a count that exists at launch needs a read. `seat.pending` takes no arguments and returns `Record<chatId, number>`, with only the terminal Lead tabs that have updates waiting. KERNEL-1029.
