**A workspace being made asks the remote before it reuses a recent fetch.** KERNEL-542 let any caller reuse a fetch that passed in the last minute, so a PR merged inside that minute was missing from a workspace created right after it. Now `createWorkspace` and `makeNow` pass `check` to `fetchOrigin` with the branch the base names (the default branch, or a branch picked in New chat). Inside the minute, `fetchOrigin` runs `git ls-remote <remote> refs/heads/<branch>`, which reads one sha and no objects, with a 10 second limit. When it matches the local `<remote>/<branch>`, the fetch is reused. When it differs, fails, or the remote has no such branch, it fetches now. Callers without `check`, such as New chat's prefetch on open, still reuse without asking, and Create still answers before the fetch. A fetch that fails also ends the reuse, so a caller after it doesn't take the remote as reached.

**A workspace that started from a stale base catches up once a fetch passes.** KERNEL-179 started a workspace from `<remote>/<default>` as last fetched when the fetch failed, and nothing moved it later. Now BaseWatch catches up each workspace with `fetchFailed` when a fetch of the room's remote passes: the fresh fetch after a merge, or the fetch of another workspace being made (`check` with `fetched: true`). It only touches a teammate workspace that is ready, on a worktree, not a review, and has no turn running or message queued in any of its chats. It reads that again after each git step.

With no commits of its own and no changed tracked files, `fastForward` moves it to its base, `fetchFailed` is cleared, and the chat gets a note that it now starts from the latest base. With work on the branch, or when git refuses the fast-forward, Kernel posts one message asking the teammate to rebase onto its base, and clears `fetchFailed` once the message went. A branch that is already level with its base just loses `fetchFailed`, with the same note. A workspace caught up in a check isn't also checked for conflicts in that check, so it gets one message.

A busy workspace waits. Its turn end already calls BaseWatch for that workspace (KERNEL-180), and while it has `fetchFailed` that check runs a normal fetch, reusing one that passed in the last minute. That fetch is the retry, so there is no timer. Chats with Kernel are left out: `syncLead` keeps Kernel's worktree on its base (KERNEL-181).

Amends KERNEL-542 (a recent fetch is reused by every caller) and KERNEL-179 (a workspace that started from a stale base stays there). KERNEL-653.
