**A room merges with its own method, else the app's when the repo allows it, else the first one the repo allows.** `[pr] merge_method` wins and Kernel doesn't check it. Someone typed it for this repo, and if the repo refuses it, GitHub's error says so in the merge's message. With no room method, Kernel asks the room's code host which methods the repo allows. On GitHub that is `gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed`, which anyone who can read the repo can see. The app's `pr.mergeMethod` is used when the repo allows it. Otherwise Kernel takes the first allowed method in the order squash, merge, rebase. A repo that allows only merge commits used to fail every merge on Kernel's default of squash. When the host can't say (gh failed, offline, or a host without `mergeMethods`), Kernel uses the app's method, as before. The answer is kept per room for 10 minutes and dropped when a merge fails, since a failed merge may mean an admin changed the repo's settings. A failed read isn't kept. The method a merge used goes on the workspace as `mergedWith`, so the merged toast says "Merged into" rather than the app's "Squashed into". KERNEL-468.

**Only Kernel's own Create PR text follows the repo's conventions.** When the text in force (the room's, else Settings, Pull requests) is Kernel's default, Create PR sends a version built from the workspace's checkout. It names the PR template (`pull_request_template.md` or `.txt`, any case, in `.github/`, the root or `docs/`, in that order, or a `PULL_REQUEST_TEMPLATE/` folder when there is no single one), the contributing guide from the same places, and the commitlint config (`.commitlintrc*` or `commitlint.config.*` at the top, or a `commitlint` key in `package.json`). Text the user or the room wrote goes out as written, because Kernel can't tell which of its lines they meant to keep. The template and the guide are named by path, not pasted in, so a long template doesn't fill the message and the agent reads the version on its branch. KERNEL-468.

**Kernel asks for Conventional Commits only when commitlint checks them.** The default used to say "Title it as a Conventional Commit" in every repo, which is wrong for most repos people add. Without commitlint the line asks for a title in the style of the repo's recent commits. That still gets Conventional Commits in a repo that uses them by habit, Kernel's own included, since the agent reads the log. With commitlint it asks for Conventional Commits in the title and the commits and names the config. The old default text joins `SAVED_BEFORE`: settings files from before KERNEL-225 saved it on every launch, so it reads as unset and those installs get the new text. KERNEL-468.
