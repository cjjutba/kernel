**A window that loads asks main for what it missed: which chats are working, their retries, and every workspace's script and terminal output.** Pushes only report changes, so a window that reloaded (a `git pull` under `pnpm dev`) or was reopened from the Dock showed every working agent as stopped until its turn ended, a running dev server as stopped and terminals blank. The engine was fine and Kernel said nothing was stuck, so the maintainer typed "continue" into the chats: 18 of the 25 such messages in one night interrupted a turn that was still running. `chats.live` answers with the chats whose turn runs and the retry each one counts down. `boot()` applies it so that a `chat.running` or `retry` push that arrived while the call was out wins, the rule `loadRoom` already uses for agent statuses, which needs nothing from the order IPC replies and pushes arrive in. Script and terminal output are streams, so main keeps them, trimmed by the window's own rules (`src/shared/scriptLog.ts`), and `scripts.replay` and `terminal.replay` send them back as pushes (`script.state`, and `terminal.data` with `replace`) on the same stream as live output. Whatever the window holds came before the replay and is in it, and whatever comes after is newer, so nothing shows twice or goes missing. Script events are kept in Kernel's push listener rather than in `runScript`, since `kernel.ts` pushes setup and archive lines of its own. The window asks once per workspace and per terminal, because from then on every line reaches its store, open or not. An archived workspace's record goes, the exits that arrive after the archive included. Main clears a script's exit code when it runs again, which the window only did for its own Run button. An open terminal redraws from the top when the replay lands, since `appended` only handles a buffer that grew or was trimmed. A dev window newer than its main (mid-pull) gets no answer from these channels and boots as before. KERNEL-340.

**Claude Code processes lead their own process group, and Kernel adds no signal handler.** Kernel started them in its own group, which under `pnpm dev` is the terminal's foreground group, so Ctrl+C or a closed tab reached every agent at once and ended its turn before Kernel's quit could keep it to carry on (KERNEL-215). A throwaway Electron 38 app showed the rest: SIGINT, SIGTERM and SIGHUP each fire `before-quit`, a `process.on` handler for them never runs, a quit held for 3 seconds keeps the main process and window up, and a child in the same group dies of the SIGINT at once while a detached one runs on. So the quit that follows a signal is the ordinary one. Electron can't say whether a quit came from a signal or from Cmd+Q, so it asks while agents work, and they keep working until the answer, then stop the way KERNEL-215 carries them on. A `pnpm dev` started while the old copy's dialog is still up hands over to it and exits, and nothing is lost: answer the dialog, then run it again. The installed app isn't started from a terminal, so only dev runs reached this. KERNEL-340.
