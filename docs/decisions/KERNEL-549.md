**Reviews come in kinds, code, security and UX, set in the shared `[review]` table and kept apart from agents.** Part of KERNEL-548. Before this, a PR got one reviewer, an agent, and a room with no reviewer agent got no review at all. Now each kind is a table in `.kernel/settings.toml`:

```toml
[review]
rounds = 2

[review.ux]
paths = ["src/renderer/**"]
agent = "lumi"
required = false
model = "claude-sonnet-5-5"
```

The code review runs on every PR and is required unless `[review.code]` says otherwise. Security and UX are off until a room adds their table, which turns the kind on unless it says `enabled = false`. `paths` are globs, or plain paths that name a file or a folder, and an empty list is every PR. `required` decides whether the kind's approval counts toward "require Reviewer approval". Its blockers hold a merge either way. `agent` runs the kind with that room agent's own prompt. Without one, Kernel's prompt for the kind runs, from `docs/lenses/<kind>.md`, under the reserved id `kernel-reviewer`. The code review's agent is otherwise the room's reviewer. Kernel's built-in Theo counts as no reviewer here, so a room without a reviewer file runs `code.md`, which starts from Theo's text and `BLOCKER_RULE`. KERNEL-553 can then take Theo out without touching reviews. `[team] reviewer = "none"` still means no automatic code review, unless `[review.code]` names an agent. `rounds` is read and written here and used by KERNEL-552. Only the shared file sets `[review]`: it is the team's policy, so the personal file can't loosen it. `settings.setReview` writes it the way `agents.setTeam` writes `[team]`, splicing each table into the text and refusing a change it can't make without touching the rest of the file. Each prompt in `docs/lenses` blocks only on its own kind of problem, using the KERNEL-377 list, and `reviewRule` tells a chat which other kinds run beside it. The prompts are bundled into the main process with `?raw` rather than read from `docs/` like the starter agents, because a review chat picks its prompt as its session starts, which is synchronous, and a bundled prompt can't go missing from a build.

The UI says "review" for all of this: "the security review", "Code and security approved", "Security found 2 blockers". Lens is the code's word. KERNEL-549.

**Kernel starts the reviews itself when a PR passes checks, one review workspace per PR with one chat per kind.** Before this, Rowan's prompt carried `LEAD_REVIEW_RULE` and each ready PR's Team update told it to call `create_workspace` with `review_of`. Rowan sometimes didn't, and the review depended on a Lead turn. Now the `pr` push for `ready` calls `Reviews.onReady`: while `pr.autoReview` is on, Kernel works out the kinds whose paths match the PR's changed files (`git diff --no-renames <base>...<head>`, so a file moved out of a path still counts) and starts a review workspace with a chat for each. All chats share one worktree and one setup run, and each brief waits until setup passes. A later ready on a new head adds a chat for a kind the workspace lacks and asks each chat without a verdict on that head to review again, once per commit. KERNEL-552 narrows that to the kinds that blocked. The Lead's own workspaces and reviews get none. `LEAD_REVIEW_RULE` and the "needs a review" To do line are gone. Rowan still passes blockers on. A blocker line from a kind no longer asks Rowan to request another review, since Kernel runs it again once the fix passes checks. A review Rowan starts with `review_of` because the user asked still works as before, and counts as the code review.

A review chat is read-only whatever its agent's file says. `toolPolicy` takes `readOnly` for any chat in a review workspace and drops Edit, Write, MultiEdit and NotebookEdit, a plan file included. Bash stays for git and gh. On Codex, Kernel declines every file change a review chat asks to make. An edit Codex makes inside its sandbox without asking is stopped only by the prompt and `reviewRule`. An agent never reviews its own PR with its own prompt: when a kind's agent wrote the PR, that kind runs Kernel's prompt.

A verdict carries its kind, and `optional` when the kind wasn't required. `submitReview` replaces an earlier verdict by review workspace and kind. `kindStates` in `src/shared/merge.ts` reads the verdicts kind by kind, and `headBlockers`, `mergeBlock` and `reviewPhrase` build on it. Verdicts of two kinds on the same head both count. Blockers on the head from any kind hold the merge. With "require Reviewer approval" on, every required kind that reviewed the PR has to approve its head. A kind still running holds nothing, as a PR nobody reviewed always merged. A verdict from before this has no kind and counts as the code review's. Amends KERNEL-115, KERNEL-130 and KERNEL-497. KERNEL-549.

**Kernel reads `[review]` and `[team]` for these decisions from the PR's base branch, never from the PR.** Otherwise a PR could turn its own review off, name its author as reviewer, or drop the paths that would have reviewed it. `policyFor` runs `git show <remote>/<base>:.kernel/settings.toml`, then the local base branch when the remote's copy isn't there. A base with no settings file, or none Kernel can resolve, runs on the defaults, so code review still happens. The main checkout's working file and the personal file don't count either, since neither is what the PR merges into. The decisions are fixed on the chat when the review starts (`Chat.lens`), so a change to `[review]` later applies to the next review, not to a running one. KERNEL-549.
