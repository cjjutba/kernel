**Codex runs through `codex app-server`, and Kernel's own tools reach it as dynamic tools.** Kernel needs approval requests, interrupt, resume, sign-in and rate limits from Codex. `codex exec` and the Codex TypeScript SDK give no approval requests or sign-in, so Kernel speaks app-server's JSON-RPC over stdio, one process per chat, the same shape as Claude's process per chat. The protocol types are generated from the pinned binary with `codex app-server generate-ts --experimental`. A spike on Codex 0.153.4 started an ephemeral thread on `gpt-5.6-luna` with one dynamic tool, `kernel_ping`, and asked for a ping. Codex sent `item/tool/call`, showed a `dynamicToolCall` item, took Kernel's answer and repeated it in its reply. So `Tools.toolsFor()` goes to Codex as dynamic tool specs, answered in process like the in-process MCP server Claude gets, and the HTTP MCP fallback with a per-chat token isn't built. The same run showed what the runner relies on: `account/read` names the ChatGPT email and plan, `account/rateLimits/read` and `account/rateLimits/updated` give a 300-minute and a 10080-minute window with `usedPercent` and `resetsAt` in epoch seconds, `model/list` gives each model's own efforts (up to `max`, and `ultra` on some), `collaborationMode/list` has `plan` and `default`, and `thread/tokenUsage/updated` carries the model's context window. Codex runs the user's own `~/.codex` hooks and MCP servers in a Kernel thread, as Claude reads `~/.claude`. Reasoning items come back empty unless a turn asks for a summary, so the runner asks for one. KERNEL-406.

**Codex commands with no Kernel rule run in Codex's sandbox without asking, except in Ask.** Codex threads run with approval policy `untrusted` and sandbox `workspace-write`, so Codex asks about nearly every command outside its own short list of safe reads. Claude leaves such commands to the user's own Claude Code allow list, which Codex has no counterpart for, and asking about each one in Accept edits would ask about most commands. So Kernel's order for a Codex command is: Never allow (and a push to a protected branch) declines, Network off declines a command that reaches the network, a room's Always allow rule accepts, Always ask asks the user, and then Bypass in worktrees and Accept edits accept while Ask asks. An accepted command still runs inside the sandbox. A request to run outside the sandbox, or for more permissions, always asks. File changes accept on their own in Accept edits and Bypass in worktrees, and ask in Ask, as Claude's edits do. A worktree's `.git` is a file pointing into the room's `.git/worktrees/<name>`, outside the workspace, so the runner adds the repo's git common dir to the sandbox's writable roots, or `git commit` would fail. The sandbox's network access follows Settings, Permissions. This differs from Claude on purpose. KERNEL-406.

**Spike: does a `claude setup-token` session still report usage?** A session runs on it, but the usage call answers with nothing. Run on the pinned CLI (2.1.292) with a 108-character `sk-ant-oat01-` token from CJ's account in `CLAUDE_CODE_OAUTH_TOKEN`, the shared `~/.claude`, and `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` removed:
- One Haiku turn answered. `init` said `apiKeySource: 'none'`, so the turn billed the plan, not an API key.
- The env var wins over the Keychain login. The same run with a made-up token failed with "401 OAuth access token is invalid".
- `rate_limit_event` arrived with `unifiedWindows`, giving the 5-hour and weekly utilization and reset times, as on the CLI's own login.
- The experimental usage call didn't throw, but gave `rate_limits_available: false`, `rate_limits: null` and `subscription_type: null`, whether asked before a turn, after one, or in a session that sent no prompt. On the CLI's own login the same call gave the plan (`max`) and every window. The token's `user:inference` scope doesn't reach `/api/oauth/usage`.
- `claude auth status` on the token said `loggedIn: true`, `authMethod: 'oauth_token'`, and gave no email and no plan.

So an account added this way keeps limits and meters from `rate_limit_event` during turns. It loses the usage call: idle refreshes, the early-lift check while a limit pauses the rooms, and model windows such as Fable's. Kernel also can't read its email or its plan, so the plan defaults (KERNEL-225) would treat a Pro account as unknown. CJ chooses between this token and a per-account `CLAUDE_CONFIG_DIR` before the Add account flow is built. The capture itself: `claude setup-token` wraps the token at the terminal's width and, in a narrow terminal, doesn't show it at all. A flow that reads it runs the CLI in a pty wide enough for one line, joins wrapped lines, and accepts only an `sk-ant-oat01-` token of about 108 characters. KERNEL-406.

**Sessions keep the orchestration, and a runner per provider speaks one CLI.** `Sessions` had grown to mix queues, pauses, limits, carry-on, the idle stop and hand-offs with the Agent SDK's messages and callbacks. The orchestration stays in `services/sessions.ts`. Each chat's process is a `Runner` (`services/providers/types.ts`) that reports back through a `RunnerHost`: `ClaudeRunner` holds the SDK code as it was, and `CodexRunner` holds the app-server code. Plan approval came out of `canUseTool` into one `requestPlan`, which ExitPlanMode and a Codex plan-mode turn both call, so the plan card, the saved plan file, leaving plan mode and the Lead's hand-off are the same on both. With every role on Claude nothing changed: the full suite passed on the seam before any Codex code landed, apart from one test that injected the old private `Live.query`. KERNEL-406.

**Settings, Models and effort sets a provider, model and effort per role, and an agent file's model line pins that agent.** One Claude model per role and one global effort became `models.roles`, each `{ provider, model, effort }`, and an old settings file moves over as Claude roles at its old effort. Only what the user chose moves: a model or effort they never set stays unset, so the plan's defaults (KERNEL-225) still reach it. The plan keys are now role paths: the Lead's and the reviewer's model and every role's effort, with the agent limit and auto review as before. `Team.pickFor` is the one place an agent's start is decided: the file's `model:` with its `provider:` (or the provider the id belongs to: `claude-*` and Claude's aliases are Claude, `gpt-*`, `o<n>` and `codex-*` are Codex), else the role. `inherit`, or a model Kernel can't place, follows the role as it always did. `effortByModel` keeps plain model ids as keys, since Claude's and Codex's can't collide. A chat keeps its provider for life: the conversation lives in one CLI's transcript. Picking the other provider's model in a started chat opens a new tab on it, and one that hasn't started moves over. Chats on Claude still save no `provider`, so their rows look as before. KERNEL-406.

**Kernel's tools keep their Claude names in its rules, and Codex reads them as `kernel_<tool>`.** `LEAD_RULE`, `TEAMMATE_RULE`, `SHARE_RULE`, the reviewer rule, `HANDOFF_NOW`, `HANDOFF_REMINDER` and tool results name `mcp__kernel__<tool>`. Writing each twice would let them drift, so `forProvider` rewrites the names for a Codex agent at the one place each leaves Kernel: the thread's developer instructions, the hand-off texts and the dynamic tools' answers. Codex rows still show the tool as `mcp__kernel__<tool>`, so the Lead's own reads of its transcript (`create_workspace` rows) work on both. On Claude the hand-off reaches the Lead as hook context inside its turn. Codex has no such hook, so an approved Codex plan is followed by `HANDOFF_NOW`, or "go ahead" for a teammate, as Kernel's own next turn, and a Lead turn that ends with nothing handed off gets `HANDOFF_REMINDER` once the same way. A Lead that asked with `request_plan_approval` gets no second card for the plan item its plan-mode turn ends with. KERNEL-406.

**Accounts share each CLI's config and swap only the credential, and switching is always a click.** CJ has several Claude and ChatGPT accounts and wants to keep MCP servers, plugins, skills and chat history across them. A Claude account Kernel adds is a `claude setup-token` token, kept encrypted with `safeStorage` in `claude-tokens.json` and passed as `CLAUDE_CODE_OAUTH_TOKEN`. Everything else stays in `~/.claude`, so a resumed chat finds its transcript on any account. Amends D-018: an added account's subscription token goes in `CLAUDE_CODE_OAUTH_TOKEN`, and `sessionEnv` still drops `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`, so no session bills an API key. A Codex account gets `<dataDir>/codex-homes/<id>/`, where only `auth.json` is its own and every other entry of `~/.codex` is a link, made again before each use so what `~/.codex` gains later is shared too. A thread started on one Codex account resumes on another, and dynamic tools stay with the thread. The CLI's own login is always the first account, and the one Kernel uses until the user picks another. A switch applies from the next turn: a running turn finishes on its account and idle processes end. Kernel never switches on its own, even at a limit: the banner offers "Switch to" another signed-in account with room. Neither provider has an API key option anywhere. KERNEL-406.

**Limits and sign-outs hold only their provider's chats.** A usage window now carries its provider and the account it was read on, and is kept by `limitKey`, which leaves a Claude window on the CLI login under its type, as every saved limit from before was. A rejection holds a chat only when it is its provider's, on the account that provider runs on now, so Codex agents keep working through a Claude limit, and a switch to an account with room lets the chats go. A room pauses for a limit only when every provider its agents run on is stopped. With every role on Claude that is the old rule. A sign-out holds only its provider's chats: Claude's under `auth`, as before, Codex's under `codex-auth`. Offline still holds everyone. Codex's windows come from `account/rateLimits/read` and `account/rateLimits/updated`, by length: the 300-minute window is the 5-hour one and the 10080-minute one the weekly one. Amends D-017 and D-069, which assumed one Claude account. KERNEL-406.

**Kernel bundles a pinned Codex, as it bundles Claude.** `@openai/codex` is pinned exactly in package.json, and its darwin binary is unpacked from app.asar (electron-builder.yml). Each provider runs the path in Settings, Providers, else its bundled copy, else the one on the PATH, and Use system skips the bundled copy. The status table and the account reads go through that same executable, never whatever `claude` is on the PATH, which fixes KERNEL-277. Only the protocol types Kernel uses are committed, from `scripts/codex-protocol.mjs`, so a Codex bump reads as a diff. Preflight checks Codex only while a role runs on it, and never blocks. KERNEL-406.
