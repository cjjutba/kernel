**The first switch of a shared chat to Build here makes its working copy by Workspace type.** A chat on the shared main folder (KERNEL-1050) can't edit it, since every Hand off chat reads that folder and Kernel fast-forwards it. Build here needs a folder that belongs to the chat, and Settings, Git and worktrees, Workspace type (`repo.workspace.mode ?? settings.workspace.mode`) is where the user already says what a working copy is, so the switch follows it instead of forcing a worktree. A new chat that starts in Build here follows it too, in place of the worktree KERNEL-405 forced. Hand off chats and reviews still get a worktree or the shared folder as before.

The switch waits until no turn runs in the chat, with its tabs held so a message sent meanwhile waits too, and reads the record again after each wait. Worktree: a branch from the "Chats with Kernel" pattern and the chat's title, cut from `<remote>/<default>` through the same spare claim, branch lock, fetch and KERNEL-653 check a new chat uses (`Workspaces.cutOwnWorktree`, then `makeWorktree`). Current branch: the main checkout, with the baseline per "Treat existing changes as the baseline", refused with a sentence when "One current-branch workspace per project" is on and another open workspace is on it. That rule now counts a chat with Kernel that builds on the checkout, not only teammates (`Workspaces.onCheckout`). Then ports, files.copy and setup run as for any workspace, and each session resumes by id in the new folder (KERNEL-348).

The chat keeps the working copy. Switching back to Hand off only changes the mode, and switching to Build here again reuses the folder with no cut and no setup. While the copy is made the workspace is `setup` with `worktreePending`. A failed cut puts the chat back in Hand off on the shared folder and posts a row saying why. A failed setup behaves as for a new chat: the chat stays in the new folder, failed, with Run again.
