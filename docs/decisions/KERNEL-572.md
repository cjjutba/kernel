**The renderer reads the mode a chat runs in from `chats.runMode` and `chat.runMode`, never from `Chat`.** The answer depends on the room, Settings, Permissions, what the provider can run, the agent file and the chat's live process, so a copy saved on `Chat` would go stale whenever one of those changed. It works like the queue's reason (KERNEL-271): main computes it, a call answers it and a push carries each change. `Sessions.pushModes` sends it again on the triggers that move live chats (`applyModes`), and also when the chat is configured, when its agent or its provider's account changes, and when its process ends. It covers every chat in a workspace that isn't archived, live or not, and leaves big terminals out. A chat gets a push only when its answer differs from the last one the renderer got. KERNEL-572.

**`why` is set exactly when the chat runs in another mode than the one picked, and the first step that moved it gives the reason.** The brief named four reasons. Two more keep that rule true. `plan` covers a chat that is planning. `noBypass` covers Claude Code's settings turning Bypass permissions off, or Kernel not having read them yet. Only in worktrees comes before policy, because Kernel only reads the policy for a workspace that can run Bypass permissions. So a current-branch chat under a policy that turns Bypass off says `worktreesOnly` until Only in worktrees is off, and `noBypass` after that. While Bypass permissions waits for a turn to end, the chat reports the mode Kernel last gave its process, with `turnRunning`. KERNEL-572.
