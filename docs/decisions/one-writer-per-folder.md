**Turns that can write take turns in a folder.** Two chats in one workspace (a tab added with "Previous worktree", see workspace-picker) or two workspace records that resolve to the same folder could run turns at once and edit the same files. Sessions now holds a message when another chat in the same folder is running a turn that can write. The reason is `folder` (`QueueReason`), computed with the other reasons and never saved. The composer says "Waiting for <chat title> to finish in this folder", and the title opens that chat. Folders are compared by real path, so a symlink and a trailing slash count as one folder. The hold does not read Git, only the chat's workspace path.

**First held, first served.** A chat also waits for another chat in its folder whose message was queued earlier and is free to go, so three tabs go in the order they waited and a later message cannot jump the line when the folder frees. A chat that waits on something else (offline, paused, the agent limit, a cut-off to carry on, a crash) does not hold a place, so it can never block the chats behind it for a reason that has nothing to do with the folder.

**Plan mode, review chats, terminals and steering are exempt.** A plan turn can't write, so it neither waits nor holds anyone up. A review chat (a chat with a lens) is read-only, and a review workspace runs its code and UX reviews side by side in one folder. A terminal is no agent turn. Steer goes into the running turn, which is already the folder's writer, so it is not held. Kernel's own turns (Team updates, reviews, carry-ons after a limit or a quit) follow the same rule: `post` refuses with `folder`, and a carry-on waits until the folder is free.

**Nothing waits for itself or for a chat that is gone.** A chat's own running turn stays the `running` reason. Stopping a chat, closing its tab or archiving its workspace drops its held messages and starts the chats behind it. Taking the last message out of a held chat's tray does the same. After a restart a held message goes first, since the crashed turn's carry-on is not queued and waits for the folder like any other message.

**Send now does not go past the folder hold.** It can start a chat over the agent limit, but never into a folder another chat is writing in, so the button is not offered for `folder`. A chat held for the folder takes no agent slot, since slots count running turns. When both hold, the reason says `capacity`, and the folder still holds once a slot frees.

**Left out, the sidebar.** Other holds (agent limit, offline, paused) show only in the composer, so the folder hold does too. The sidebar row keeps the chat's real status.
