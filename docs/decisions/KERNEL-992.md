**Replaced by KERNEL-1113:** Kernel no longer checks a go-ahead or hides tracker writes from the Lead. Kept for history.

**Build here asks for a go-ahead before it changes files, the same rule as Hand off.** With plan mode off, Kernel edited, committed and opened a PR as soon as the model read a message as a request, and "can we just fix this... Can we just remove those? or what?" produced a PR with a fix Kernel chose itself. Hand off already checked in code (KERNEL-678). Build here now does too. `start_build({ go_ahead })` takes the user's words from their latest message, checked by the same `goAheadOf` as `create_workspace` and `file_issue`, and records `Workspace.buildGoAhead` (`quote`, the time of the message it came from, and the branch). `GO_AHEAD_LINE` in `handoff.ts` is the one rule both modes share: a request for one clear change is a go-ahead even when phrased as a question, and a message that offers options, asks what to do, asks a question or only agrees is not one, so Kernel answers, recommends one approach and asks once. KERNEL-992.

**What is gated while it is closed.** Edit, Write, MultiEdit and NotebookEdit (a PreToolUse hook on Claude shaped like the reference-folder check, and `approveFiles` on Codex), and `git commit`, `git push` and `gh pr create` (`publishesWork`, checked in `guardVerdict` for both providers, so `&&` chains, `bash -c` and env prefixes count). Bypass permissions doesn't skip any of it. Reads, tests and `pnpm shots` still run, and so do plan files and `.kernel/shared` files, the same exemption Hand off has. Both runners read `RunnerHost.buildOpen()` at each call, so a go-ahead or a switch in the middle of a reply applies to the next step (KERNEL-770). KERNEL-992.

**Commits and pushes are the hard stop, not every write.** Bash can still write a file other ways, such as `sed -i` or a redirect, and gating all of them would mean guessing what each command does. What the user is protected from is work leaving the worktree: nothing is committed, pushed or opened as a PR without a go-ahead, and an uncommitted edit stays in a folder the user can discard. Gating every Bash write is out of scope. KERNEL-992.

**What needs no quote.** In a turn the user started, the gate is open when the go-ahead was recorded for their latest message (`buildGoAhead.at` is not older than it), or a plan was approved after it. A go-ahead from an earlier message doesn't open a new one, so "also, what about X?" can't start work. In a turn Kernel started, such as a Team update, it is open when `buildGoAhead.branch` is the chat's branch now, or the chat has an approved plan, since that is a follow-up on approved work. A merge moves the chat to a new branch, so the old go-ahead stops counting by itself. Plan mode keeps it closed. A plan approved in Build here records a go-ahead with the quote "plan approved", and a mode switch clears it. KERNEL-992.

**The state is saved on the workspace.** A restart in the middle of a build would otherwise close the gate on work the user had already approved and leave Kernel unable to commit. The workspace is JSON, so no migration. KERNEL-992.
