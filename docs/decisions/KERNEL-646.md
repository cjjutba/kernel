**Codex servers sign in through Codex's own MCP OAuth, `mcpServer/oauth/login` on `codex app-server` in the account's home.** Amends KERNEL-626, which said Kernel needed no Codex sign-in. CJ's Codex had linear, mobbin and supabase waiting on one, and the only way to sign them in was a terminal. Codex 0.153.4 answers the request with `authorizationUrl` and later sends `mcpServer/oauthLogin/completed` with `success` and an `error`. Kernel opens the page with `openExternal`, as it does for a Codex account's own sign-in, and waits up to 15 minutes. Codex stores the token itself, in the Keychain under `Codex MCP Credentials` with a key that doesn't depend on `CODEX_HOME` (KERNEL-626), so one sign-in covers every Codex account. Kernel never sees the token. After a sign-in the server reads as ready on every Codex account checked before it, until the next check. Sign in to all works the same way on Codex and skips a server another sign-in already covered. A server Codex can't sign in to, such as a stdio one, fails with Codex's words. KERNEL-646

**Codex's failure reasons come from an ephemeral thread.** `mcpServerStatus/list` has no reason field, and `runtimeStatus` is null outside a thread. When some server listed no tools and isn't waiting on a sign-in, Kernel starts a thread with `ephemeral: true` in the home folder and listens for `mcpServer/startupStatus/updated`. Each one carries Codex's error ("MCP client for `x` failed to start: ..."). No turn runs and nothing is saved. Kernel stops listening once every server that said `starting` has finished, or after 30 seconds. Codex never starts some servers on a thread. On CJ's Mac those were `code-review` and `codex_app`, the bundled plugins' servers. They read "Codex lists it from the code-review plugin but didn't start it." This replaces KERNEL-626's "Codex could not list its tools." Every reason is cut to one line of at most 160 characters. KERNEL-646

**A server `config.toml` switches off is `not-set-up` with a note, not left out.** CJ's `vapi` and `computer-use` have `enabled = false`, so KERNEL-626 dropped them and the page showed them with no state. They now read "Switched off in Codex's config.toml." on every Codex account. KERNEL-646

**`mcp.accounts` lists every server of a provider on each of its accounts, in one of five states, with a kind.** The states are `ready`, `needs-sign-in`, `failed`, `not-set-up` and `ignored`. `not-set-up` replaces `not-installed`. The kinds are `user`, `connector` and `plugin`, and `connector: boolean` stays for the screens built before. A claude.ai connector that is missing on an account carries `connectUrl`, claude.ai's connector settings, and the account carries its `email`, since only the account's owner can add a connector and they have to be signed in to claude.ai as that account first. KERNEL-646

**A plugin's server that a claude.ai connector covers is ready, matched by name.** `plugin:vercel:vercel` was missing on CJ's Max login and ready on Pro. Both logins had the plugin. Claude Code 2.1.292 drops a plugin's server that points where a claude.ai connector does ("Lazy dedup: suppressing plugin server(s) that duplicate claude.ai connectors"), and only Max had claude.ai Vercel. The probe doesn't list a dropped server or say what covers it, so Kernel matches by name: `plugin:<plugin>:<server>` against a ready `claude.ai <Name>` on the account, with case and punctuation ignored. A match reads ready with "Covered by claude.ai Vercel on this account." This can miss a connector named differently from the plugin's server, which then shows as not set up. KERNEL-646

**Plugins sync both ways, with a three-way merge like MCP servers.** The real sync gap was elsewhere. Claude Code writes `plugins/installed_plugins.json` and `plugins/known_marketplaces.json` through a temp file and a rename, which replaces the link `linkClaudeHome` made with a file of the account's own. CJ's Pro folder had its own copy that had updated vercel to 0.50.0 while `~/.claude` stayed on 0.43.0. `syncClaudePlugins` runs before each Claude process on an added login and with the periodic MCP sync. When an account has its own file, plugins it added, changed or removed since the last sync go to `~/.claude`, with `mergeServers` deciding (the CLI login wins when both changed one plugin). Paths into the account's folder become paths into `~/.claude`, which they already reach through the linked `cache`. Then the file is a link again, so a later change on the CLI login reaches the account at once. The last merged state sits in `kernel-plugins-base.json` in the account's folder. On a first sync with no base, the CLI login's version of a plugin both have wins. KERNEL-646

**Ignore is per account and per server, kept in `accounts.json`.** It lives with the account (`mcpIgnored`) rather than in Kernel's settings, so removing the account removes it. An ignored server reads `ignored` whatever its state would be. A server switched off in every open room (`[disabled] mcp` in the room's settings) carries `roomOff`, since no session would start it. Neither counts toward the account's row warning (`mcpSignIns`), the notice after adding an account or Sign in to all. With no room open, no server counts as off in every room. KERNEL-646
