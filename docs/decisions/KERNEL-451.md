**Kernel reads an agent file's frontmatter the way Claude Code 2.1.292 does, with a YAML parser.** The line reader from KERNEL-397 got most files right and some quietly wrong, and every new key Claude Code adds was one more case to write. Reads now go through the `yaml` package, set up to match `Bun.YAML`, which Claude Code uses: a repeated key keeps its last value, and `<<` merges. The rest copies Claude Code's own code from the bundled build. The frontmatter is everything from the first `---` line to the next `---`. When the YAML fails, Claude Code quotes each `key: value` line whose value holds `: `, `#` or another YAML syntax character, turns leading tabs into spaces, and tries once more, so `description: Use this agent when: ...` reads. Kernel does the same. The fields read as Claude Code reads them:
- `tools` and `disallowedTools` split at commas and at spaces outside parentheses, so `Read Grep` is two tools and `Bash(git status:*)` is one. `*` means every tool, and a key with no value means none.
- `mcpServers` gives the names it lists, a server defined in place under its own name.
- `permissionMode` must be one of Claude Code's six modes, and `manual` reads as `default`. Kernel only reads it here. KERNEL-447 applies it, and only to make a chat's mode stricter.
- A written `\n` in a description is a new line.
- `model: inherit` is no model, so Settings, Models decides, as it does with no model line.

Writes stay line-based (`rewriteAgentFile`), so comments and keys Kernel doesn't manage stay as written. Two leniencies from KERNEL-397 stay: a file with no `name:` takes its file name, and one with no description gets `no-description`. Claude Code skips both. One known difference is left: a top-level key indented with a tab reads in `Bun.YAML` and fails in `yaml`, even after the retry. Amends KERNEL-397. KERNEL-451.

**A file Kernel can't read stays on Team with what went wrong, and does nothing else.** `loadAgents` used to drop it without a word, so one bad quote made a teammate vanish. Now a file Kernel can't open, YAML that fails the retry, frontmatter with no `key: value` lines, or a name Claude Code refuses (not text, a leading dash, a colon, over 256 characters) comes back under the file's name with an `unreadable-file` warning. Its `detail` finishes Team's "Kernel couldn't read its file: ..." line, such as "line 4 isn't valid YAML. Missing closing "quote". A file removed while the folder was read is simply gone. An unreadable agent never leads, reviews or takes a task, and `[team]` can't name it. When it shares an id with a file that reads, the readable file keeps the id. A chat still running on it gets only Kernel's tools and the session's, never every tool. Saving its profile refuses to rewrite it, since a line rewrite would keep whatever broke it, and New agent refuses to create a file that wouldn't parse. KERNEL-451.

**An empty tools line means no tools, and disallowedTools holds, as they do in Claude Code.** Building on KERNEL-439's draft, Kernel keeps enforcing agent files itself, and `toolPolicy` stays the one reader of both lines on Claude and Codex. KERNEL-397 said an agent with no tools line is unrestricted. That still holds, but `tools:` with no value, or `tools: []`, now leaves the agent only the tools every agent keeps. Before, Kernel read them as unrestricted while also marking the agent a helper. disallowedTools takes away what it names, the way Claude Code's subagent resolver does:
- A tool's name or older alias takes it away.
- A rule takes the whole tool: `Bash(rm:*)` takes Bash, as it does in Claude Code.
- `mcp__github` or `mcp__github__*` takes the whole server, and `mcp__*` takes every MCP server.

In a tools line, `mcp__*` names nothing, since 2.1.292 treats it as an invalid entry. Kernel's `mcp__kernel__` tools and the session's tools (plan mode, questions, ToolSearch, Skill, the task list) stay whatever either line says, because they are how an agent works in Kernel at all. Plan mode can still write its plan file (D-023). On Claude, the built-ins, servers and MCP tools disallowedTools names go into the session's `disallowedTools`, so the model never sees them. `mcp__*` can't go there without hiding Kernel's own server too, so the PreToolUse gate refuses those calls instead. The gate's reason now says which line refused. `canOpenPr` counts disallowedTools, so an agent whose disallowedTools takes away Bash is a helper. Amends KERNEL-397. KERNEL-451.

**On Codex, the same policy decides which MCP servers and tools the thread starts with.** Codex has no agent option (KERNEL-439), so Kernel writes the file into the thread's config. Before `thread/start` and `thread/resume`, the runner asks `config/read` for the workspace folder's `mcp_servers`. A server the file doesn't reach gets `enabled = false`. One the tools line names tool by tool gets `enabled_tools`, narrowed to the user's own list when there is one. Tools disallowedTools takes away join the server's `disabled_tools`. Kernel only overrides servers `config/read` listed, because codex-cli 0.153.4 fails `thread/start` with "invalid transport" for an override that names a server it doesn't have. A local run against a stub MCP server, with no model turn, showed that, and that the three keys switch a server off, keep only the named tools, and drop the disallowed ones. A server name a dotted config key can't hold is left alone. When `config/read` fails, the chat starts anyway, and a note says the file doesn't limit Codex's servers in that chat. Kernel's own tools reach Codex as dynamic tools, not a server, and every agent keeps them, as on Claude. The tools line's built-ins (Bash, Edit, Write) aren't mapped onto Codex's shell and patch tools here: that means choosing a sandbox per agent, which is its own change. KERNEL-451.
