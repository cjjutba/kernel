**A chat with nothing to do loses its Claude Code process after 10 minutes, and its next message resumes the conversation.** On 2026-10-10 CJ's Mac had 28 `claude` processes under Kernel and only 3 or 4 were working. Each idle one held 140 to 320 MB, plus its own copy of every MCP server in the user's settings, about 300 MB per chat in all. On an 8 GB Mac an ordinary day of hand-offs ends in swap. A chat without a process already resumes from `chat.sessionId` on its next message, the same `resume:` path a restart takes, so stopping an idle one loses nothing. Model, effort and plan mode are read from the chat when the process starts, so they carry over.

The clock starts when a turn ends (`setRunning`, still the one place a turn starts and ends) and stops when one starts. A change to the chat's queue starts it over. When it runs out, Kernel looks again: a chat with messages waiting, a brief held for setup, a paused room or a hold on every room, a usage limit it waits out, or a background task keeps its process, and the clock starts again. Waiting another 10 minutes is simpler than wiring every one of those to the clock, and the cost is that a chat may keep its process up to 10 minutes longer than it needs to. Background tasks come from the SDK's `background_tasks_changed`, the level signal its `sdk.d.ts` recommends over pairing `task_started` with `task_notification`, because a missed end event would keep a process forever. Ambient tasks (housekeeping and live-update watchers) don't count, since the SDK says they aren't activity.

10 minutes is longer than a person takes to read a reply and answer, so a conversation in progress never pays the restart. A restart costs a few seconds before the first token while Claude Code and its MCP servers start. It isn't a setting yet because nobody has asked to change it, and one number is easier to reason about while KERNEL-215 builds on this. If it turns out wrong on small or large Macs, the next step is a setting in Settings, Models, not a different default.

The idle stop is its own path, not `stop()`. It changes no status, adds no transcript or log row, and doesn't call `onExit`, so the Lead gets no crash update and the Inbox gets nothing. Claude Code's SessionEnd hook still fires on the way out, but the hook server drops hooks from sessions Kernel started (`isManaged`), and Kernel's in-process hooks don't listen for SessionEnd. This doesn't break the rule that statuses come from real events, because the timer sets no status. The agent was idle before the stop and is idle after it.

What Kernel read from the process object while a chat sat idle (who started the last turn, which hook blocked it) moved to a per-chat record that outlives the process, so `turnFrom`, `kernelTurn` and a blocked status answer the same before and after a stop. Only `stop()` clears it (Close chat, archive, restart, quit). A crash keeps it, which leaves `turnFrom` naming the last turn's sender where it used to be empty. Nothing reads it before the next message replaces it. KERNEL-183.
