**Kernel runs git init in a user's folder but never commits there.** Amends D-028. New room's "Initialize git" used to run `git add -A` and commit, which could pull `.env` files or `node_modules` into history. Now `initGit` only runs `git init -b main`, and the room's clone step tells the user to make the first commit. Until they do, a new worktree workspace fails with a message that says the room has no commit, instead of a raw git error. Rowan stays on the checkout, as KERNEL-355 already did for a room with no commit. Kernel refuses the home folder as a room, through New room or `rooms.add`, and refuses to init a folder with more than 5,000 files (`.git` not counted). Both refusals happen before the room is saved. From scratch still commits, since that folder was empty and holds only the starter kit. KERNEL-231

**A new room's worktrees go in a folder named by its id.** Amends D-028. The folder used to be the slug of the room's name, so two rooms named "app", or two names that slug the same, shared one. New rooms save `worktreeDir`, which is their id. A room saved before this has no `worktreeDir` and keeps the slug of its name, so its new worktrees land where its old ones are. A workspace's own path never moves, since archive, restore and trash all read `ws.path`. KERNEL-231

**Picking a free branch and adding its worktree run one at a time per room.** A branch is free until `git worktree add -b` creates it, so two creates at once picked the same name and the second failed. Workspaces holds a per-room chain around `freeBranch` and `createWorktree`, for new workspaces, Rowan's and forks. Ports already had their own reservation (KERNEL-244). KERNEL-231

**A settings file that doesn't parse warns in its room and is never saved over.** `loadRepoSettings` still reads a broken `.kernel/settings.toml` or `settings.local.toml` as empty, so the room keeps running on the other file and the defaults. The first failed read emits `settingsError` on the bus, and the room gets a warning in its feed plus a toast, both with the line number. The same mistake doesn't warn again, a different one does, and a fixed file resets it. `saveRepoSettings` refuses to write a file that doesn't parse, or that it can't read, and says why. Before this, a save started from `{}` and erased the file. KERNEL-231

**A reply from Claude's API beats the DNS probe.** Amends D-044. Behind a proxy, the DNS lookup of api.anthropic.com can fail while every request goes through, and Kernel held every send. Sessions now report `onReached` on an assistant message with no error and on a turn that ends in success. That marks the network online. Once the API has answered while the probe was failing, or the probe fails within two minutes of a reply, failed probes stop counting until one passes. A session's own connection error (`api_retry` with a null status) makes the probe count again, so a real outage still holds sends. One case is left: at launch on a proxy-only network nothing has run yet, so the first probe still holds sends until a turn gets through. KERNEL-231
