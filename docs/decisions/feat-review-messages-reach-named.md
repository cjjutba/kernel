**In a review workspace with several kinds of review, message_agent goes to the kind the Lead names, and Kernel never opens a chat without a kind there.** Before, the message went to the first open tab, which was usually the code review, and with every tab closed Kernel opened a new chat with no kind. That chat's submit_review counted as the code review and replaced the real code verdict. Now the Lead passes `review`. Kernel reopens that kind's tab if the user closed it. With no `review`, or one the workspace doesn't run, nothing goes out and the result lists the kinds it does run. A single-kind workspace, or a review started with review_of, takes no `review`. The loop guard counts each kind's tab on its own, so three tries at the security review leave the code review's tries alone.

**A verdict from a turn the Lead started always wakes the Lead, with the reviewer's reply.** A verdict turn used to drop its text, and a code approval stayed quiet while another kind blocked. So when the Lead asked the wrong chat, the reviewer's answer saying so went nowhere, and the PR sat blocked with nobody told. The verdict now waits for that turn to end and carries what the reviewer wrote after the Lead's message. Turns Kernel started keep the quiet rules.

**A kind that blocked while checks were running is asked to review again once, when the same commit passes checks.** Kernel runs one review round per head, so a block saying only "checks are still running" stayed until a new push or an overrule. The reviewer rule now says to wait with `gh pr checks --watch` and never block only because a check runs. As a backstop, submit_review records `checksRunning` on a blocking verdict that came in while the PR read as checks. The ready on that commit sends the kind one "review again" and marks the verdict `checksRetried`, which carries over to its next verdict on the same commit, so a second block goes to the user through the Lead's update. Verdicts saved before this change have no record and are never retried.
