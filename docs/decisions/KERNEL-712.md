**A release can go to a share of installs, through `stagingPercentage` in `latest-mac.yml`.** `pnpm release --rollout <percent>` writes the field after `minimumSystemVersion` before upload, and `pnpm release:rollout <version> <percent>` changes it on a published release. electron-updater 6.8.9 reads the field (`isStagingMatch` in `AppUpdater.js`): each install keeps a random id, and the update is offered when that id falls under the percentage. So installed copies follow it with no app change, and an install inside the rollout stays inside it as the percentage grows. 0 pauses a bad release for everyone who hasn't downloaded it yet. It can't take back an update already installed. The default is 100 until 1.0. After 1.0 the plan is 10, then 50, then 100. KERNEL-712.

**A rollout change re-uploads only `latest-mac.yml`. Amends the rule in `/release` that a published release never changes.** Moving or deleting a tag or a release is still never allowed. The zip, the DMG and their blockmaps stay as uploaded, so the feed's sha512 for the zip keeps matching. The rollout script edits the one line and leaves the rest of the file byte for byte, and it refuses a version that isn't the one the live feed shows, because a rollout on an older release changes nothing installs read. KERNEL-712.

**The feed shows only the latest release, so a partial rollout also holds back the previous one.** Installs read `releases/latest/download/latest-mac.yml`. Once 0.6.0 is published at 10%, an install still on 0.4.0 outside that 10% sees 0.6.0, isn't picked, and gets nothing. It doesn't fall back to 0.5.0. Raise the percentage rather than leaving a release partial for long. The maintainer's own copy is one of those installs, so step 7 of `/release` runs at 100, or through the end-to-end update test (KERNEL-715) instead. KERNEL-712.

**Every publish and every rollout change checks the live feed against the zip.** After `gh release create`, and after each `release:rollout` upload, the script reads the live `latest-mac.yml`, checks its version and percentage, downloads the zip and compares its sha512 and size with the feed. A mismatch fails the script with the reason, because an install rejects an update whose zip doesn't match. GitHub can take a few seconds to move `latest` to a new release, so a wrong version or percentage is read again for about a minute before it fails. A sha512 mismatch fails at once. `pnpm release:rollout --check` runs the same check read-only. KERNEL-712.
