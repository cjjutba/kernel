**"Require Reviewer approval" holds a merge only on a PR a reviewer looked at.** With `pr.requireReviewer` on and at least one saved verdict on the PR, `mergePr` needs an approval of the PR's head commit and no blockers on that commit. A verdict saved before the latest push doesn't count: `submit_review` already records the review worktree's HEAD as `sha`, and the merge reads the head from GitHub before it judges, so a push since the last poll can't slip through. A PR with no verdict merges as it did before the setting did anything. A review workspace that is running but hasn't sent a verdict doesn't hold the merge either, since one whose setup failed or that was abandoned would block it with no way out short of archiving. The refusal names the reviewer whose verdict holds it: the one who found blockers on the head commit, else whoever reviewed last. KERNEL-115.

**`pr.autoReview` decides whether the Lead starts a review on its own when a PR passes checks.** It defaults to true for now. KERNEL-204's plan defaults turn it off for Pro, and no Settings page shows it yet. Off, a PR that passed checks with no review on it reaches the Lead as ready to merge, and the Lead tells the user. A review the user asked for is still followed up as before: an approval is reported, and a review of an earlier commit asks the same reviewer again. The merge gate needs a current approval on any PR a reviewer looked at, so letting that review go stale would leave the PR stuck. The automatic review line moved out of `LEAD_RULE` into `LEAD_REVIEW_RULE`, which the Lead's prompt gets only while auto review is on. `LEAD_RULE` keeps a line on how to start a review the user asks for. The starter `rowan.md` is one file for both settings, so it says to start a review when a team update or the user asks for one. KERNEL-115.
