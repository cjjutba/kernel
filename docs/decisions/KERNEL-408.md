**Dev builds keep their data in `Kernel Dev`, and move it there once.** The installed app and `pnpm dev` both used `~/Library/Application Support/Kernel`, because both are named Kernel. Main wrote data the installed 0.1.1 couldn't read, and 0.1.1 crashed at launch. Now an unpackaged run that isn't a fixture sets `userData` to `Kernel Dev` before it takes the single-instance lock, since that lock is per folder. Packaged builds keep `Kernel`. Fixture runs and the smoke test keep their temp folder and never move anything. The maintainer chose a move over a copy. A frozen copy left in place would let the installed app resume agents dev already finished and act on dev's worktrees. Dev's first launch copies the database with `vacuum into`, so rows still in the WAL come along, plus `settings.json`, `hook-token`, `trust.json`, `integrations.json`, `env.json`, `room-icons/`, `shared/` and `Local Storage/` (composer drafts and sidebar widths). Caches, logs, telemetry and `update.json` stay behind. Then it checkpoints the old database and renames it to `kernel.db.moved-to-dev`, so the backup opens on its own and the installed app starts at onboarding. The copy goes into `Kernel Dev.partial`, and each entry is renamed into `Kernel Dev` with `kernel.db` last. A crash before that last rename leaves no database in `Kernel Dev`, and the next launch starts over. Dev takes its own lock before the move, so Chromium has already made the folder. A failed copy shows a dialog and quits instead of opening empty, because an empty `Kernel Dev` would make its own database and block every later retry. A failed rename of the old file only logs, since the data is already in `Kernel Dev`. The hook port and token don't change. KERNEL-408.

**One Kernel at a time, installed or dev.** Both write their hook address into `~/.claude/settings.json`, so two running apps would take hooks from each other. Before it takes its own lock, each build reads the other folder's Chromium `SingletonLock` symlink (`<host>-<pid>`). The lock counts only when the host is this Mac and the process is alive, so one left by a crash doesn't block. When the other build is open, Kernel says "Kernel Dev is open. Quit it, then open Kernel again." (or the reverse) and quits before it opens any data. The move checks `Kernel`'s lock again right before it starts, so an installed app that opened in between stops it. Running both at once is out of scope. KERNEL-408.

**A Kernel that can't start still checks for updates.** The updater used to start only after `kernel.start()` succeeded, so a release that crashed at launch could never receive its fix. Now a packaged build whose start fails runs one check with the same `Updater` and waits for the download for 90 seconds at most (`BOOT_UPDATE_MS`), so a slow network can't hold the dialog. When an update is ready, "Kernel could not start" names the version and offers "Install and restart", which settles `QuitGuard` first, as Restart to update does. With no update, a failed check or no answer in time, the error box shows as before. KERNEL-408.
