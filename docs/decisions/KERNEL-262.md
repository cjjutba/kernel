**A teammate records its own wait with wait_for_merge, and the Lead hears about it once.** Every teammate that isn't reviewing gets a `kernel` MCP server with one tool, `wait_for_merge({ on, why? })`. A review workspace keeps `submit_review` and nothing else. `on` is one ref: `#164`, `KERNEL-197` or a workspace id. The tool resolves and refuses it with the Lead's rules from `services/waits.ts`. Only the wording changes, so a teammate isn't told to call list_workspaces, which it doesn't have. The new target is added to anything the workspace already waits for, because the teammate can't see a wait the Lead set, and replacing it would drop that wait without anyone noticing. A target that already merged records nothing, and the tool says to rebase and carry on. A teammate on the main checkout gets the tool but is refused, because it has no branch to rebase later.

The wait goes through `Kernel.setWait`, so release on merge is the same as for a wait the Lead set (KERNEL-259). The difference is that its `wait.started` isn't marked told, so it wakes the Lead. LeadUpdates holds that event until the teammate's chat stops running (`chat.running` going false), which covers a turn that ends, crashes or is stopped by an archive or a closed chat. Without the hold, a turn that ran on for more than the 5 second update delay after the call would wake the Lead twice, once for the wait and once for the turn. In that same block, `decide` leaves out "Read the reply" because the wait line already asks the Lead to act. The hold lives in memory. After a quit, the saved wait event goes out on its own.

Amends KERNEL-259: before this, every `wait.started` from `setWait` was told. KERNEL-262.
