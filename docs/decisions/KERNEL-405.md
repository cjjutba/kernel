**Each chat with Kernel is its own workspace, with its own worktree, branch, ports and setup.** A room had one Lead workspace (KERNEL-355) and every chat with Kernel was a group of tabs inside it (KERNEL-337, KERNEL-338). All chats shared one folder, one port and one Changes list, and the folder only followed main when every chat in the room was idle. KERNEL-355 picked one worktree per room because Ask Kernel opened a chat for every question. Since KERNEL-339 a question joins the chat you are in, so that reason is gone. Now a chat with Kernel is a workspace marked `lead` whose `threadId` is the chat it hosts. `isLeadChatWorkspace` and `leadChatWorkspaceOf` in `src/shared/leadWorkspace.ts` find it. The `Thread` stays the chat's title and identity, and `Thread.closedAt` now means archived.

⌘N (`lead.start`) fetches the room's remote and cuts a worktree on a new branch from `<remote>/<default>`, or from the target branch picked in New chat. Kernel never pulls in the main checkout. Kernel always gets a worktree, whatever "Default workspace type" says. A room with no commit keeps Kernel on the checkout with no setup, as before. The branch follows its own pattern, `{lead}/{slug}` by default (`workspace.leadBranchPattern`, per room too), and Kernel renames it from Claude Code's title for the chat (D-089) until the branch is pushed or has a PR. git sets a new branch's upstream to the base it came from, so a branch counts as pushed only when `<remote>/<branch>` exists or its upstream is something else. files.copy and setup run like a teammate's, through `Workspaces.setUpWorkspace`, with the trust hold, the failed state and Run again. The first message waits in the chat's queue until setup passes (`workspace.leadWaitForSetup`, on by default). A tab opened while it waits waits with it. Kernel's own sends never land in a held chat, so `Sessions.post` refuses one.

Archive is the only way to close a chat. The row's hover Archive and closing the chat's last tab both call `threads.archive`. It archives every open workspace the chat handed off, then its own, each with the archive script, unless `workspace.archiveChatWorkspaces` is off, when those stay in the sidebar at room level. The window archives in one click when `threads.archivePreview` says nothing would be lost. Otherwise ConfirmArchiveChat names, per workspace, a running agent, an open PR Kernel stops checking, uncommitted changes and commits not on GitHub yet. Kernel's branch goes when it has no commits of its own, whatever "Delete branch on archive" says. Otherwise the switch decides, with the unpushed guard (KERNEL-70). Auto-archive on merge never archives a chat. An archived chat sits in History under its title. Restore brings back the chat with its worktree, branch and tabs, on a new branch from the latest base when its branch was deleted. Delete removes the chat's thread row too. Fork into new workspace stays refused for Kernel, and Create PR works on Kernel's branch once it has changes (D-106).

`lead.open` returns the room's newest open chat's workspace, or null. It never starts a chat. A room with no open chat opens New chat with Kernel on the `leadNew` route, with no workspace and no right panel, since nothing exists before the first message. Ask Kernel from Home or Inbox joins the newest open chat as a new tab, and starts a chat only when none is open. Kernel's own sends (`leadChat`: a floor brief, an overlap, a comment on a shared file) do the same. A team update for work whose chat is archived goes to the newest open chat, named as a closed chat. With no chat open, Kernel starts one for it, with setup, and the update waits for it (`openUpdateTab` answers `opening`). Kernel never restores an archived chat by itself.

Each chat follows the latest main on its own (KERNEL-181): a fast-forward of its branch to the base it started from, while that chat is idle and ready, with no commits of its own and no tracked file changed. A turn that ends syncs only its chat. A merge fetches once, then syncs every chat.

At startup Kernel moves the chats out of the old shared record, once (meta `leadChatsMoved`), with no fetch. Each open chat gets a worktree from `<remote>/<default>` as last fetched, and every tab of it moves there, closed tabs too, with their sessions, which resume from the new folder (KERNEL-348). The plans in `.kernel/plans` are copied over, what waited in a tab's queue waits for setup, and setup runs with the chat held. `Setup.fresh` keeps `recoverSetups` and `recoverTrust` away from a setup that started in this run. Then the old record's big terminals close, it is archived without the archive script, and its checkpoints go. A record on the main checkout removes no files. Closed chats stay with it, and History never lists it. A move that fails leaves the record open and tries again at the next start.

**Setup hands variables to the workspace through `$KERNEL_ENV`.** Setup gets `KERNEL_ENV`, the path of `<dataDir>/setup-env/<workspaceId>.env`, emptied before each run, and writes `NAME=value` lines to it, like GitHub Actions' `$GITHUB_ENV`. Once setup passed and the room's scripts are trusted, `Env.envFor` reads the file into a layer after the room's variables and before Kernel's own, so `KERNEL_*` always wins. Names that aren't valid or are Kernel's own are dropped, and a file over 64 KB gives nothing. Sessions and terminals drop `ANTHROPIC_*` and `CLAUDE_CODE_*` from it as from any layer (KERNEL-247). The setup log gets one line naming what was set and what was skipped, never a value. The file stays through an archive and goes with Delete. Every process also gets `KERNEL_WORKSPACE_NAME`, `KERNEL_BRANCH`, `KERNEL_BASE_REF` and `KERNEL_DEFAULT_BRANCH`. A chat with Kernel reads the room's env files from its own worktree, where files.copy put them, not from the checkout. KERNEL-405.

**Restoring a worktree workspace sets it up again.** Restore made the worktree again and copied files, but never ran setup, so a workspace came back without its dependencies (KERNEL-77). Now restore puts the record in `setup`, holds every open chat tab, and runs files.copy and setup the way a new workspace does, with the trust hold, the failed state and Run again. It returns once the record says `setup`. A restored chat already had its first turn, so it takes no start-of-chat checkpoint (`setupDone`'s `checkpoint: false`, and Run again checks for a sent message). A current-branch workspace comes back ready, with no setup, as before. Amends KERNEL-209's note that restore skips the copy when the room isn't trusted: it now waits for trust. KERNEL-405.

**A worktree whose folder was deleted outside Kernel is flagged.** It used to open as ready and fail on the first turn (KERNEL-291). `Workspaces.checkFolder` sets `Workspace.folderGone` when a worktree's folder is missing and clears it when it is back, pushing only on a change. `countChanges` checks every live workspace at launch, and `workspaces.changes` checks first and reads no diff for a missing folder. Sessions refuse a turn there and say why. The window draws it like a failed setup, with a banner and Archive, and reopening at launch, ⌘[ and Back to app skip it. Archive clears the flag, and Restore from History makes the folder again and sets it up. A current-branch workspace is the room's own checkout, so it is never flagged. KERNEL-405.
