**The Lead asks for plan approval only while its chat is in plan mode.** In a Lead chat with plan mode off, CJ asked Rowan a question and got back a plan with Copy and Approve on a hatched composer, so it looked as if plan mode had turned itself on. Rowan never entered plan mode. It called `request_plan_approval`, which the prompts allowed at any time: the kernel MCP instructions said "in plan mode or with request_plan_approval", and so did `LEAD_RULE`. Now the chat's plan toggle decides. With plan mode on, Rowan plans and asks with ExitPlanMode or `request_plan_approval`, the same as before, and an approval still means "hand it off now". With plan mode off, `request_plan_approval` creates no approval and returns an error telling Rowan to answer in the chat and hand off what the user asked for with `create_workspace`. When something needs the user's OK first, Rowan asks in the chat or with `ask_user`. The tool reads the chat's saved plan flag on every call rather than the one the session started with, because the Plan mode chip and ⇧Tab change it mid-session. The instructions, the tool's description, `LEAD_RULE` and the starter `rowan.md` all say the same thing. Plan with Rowan from an issue still opens its chat in plan mode, so it still gets a plan. A pending plan keeps its hatched box and its Copy and Approve bar. Amends D-059, where an approval could come "in plan mode or through request_plan_approval", and D-092, whose task list from `request_plan_approval` now shows only in a chat that is in plan mode.
