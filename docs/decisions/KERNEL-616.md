**An added Claude login can't share the CLI login's MCP sign-ins, so Kernel copies them between logins, both ways, before each Claude process.** Read from Claude Code 2.1.292, the CLI the SDK pins, and checked against the maintainer's Keychain on 2026-10-12 and 2026-10-13.

- Claude Code keeps everything secret about a login in one generic password in the login Keychain: `Claude Code-credentials`, or `Claude Code-credentials-` plus the first 8 hex characters of the sha256 of the folder when CLAUDE_SECURESTORAGE_CONFIG_DIR, or else CLAUDE_CONFIG_DIR, names one (KERNEL-560). The secret is a JSON object. `claudeAiOauth` is the login. `mcpOAuth` holds each OAuth MCP server's tokens, keyed `<name>|<first 16 hex characters of the sha256 of its type, URL and headers>`. `mcpOAuthClientConfig` holds a client secret given with `claude mcp add --client-secret`.
- One setting picks the item, for the login and the MCP tokens alike. CLAUDE_SECURESTORAGE_CONFIG_DIR set to an empty string sends a process to the CLI login's item, and the process then runs on the CLI login, Max, not on the account it was started for. Nothing else moves the MCP tokens on their own, and the SDK has no call that hands a session tokens. So two logins can't read one set of MCP sign-ins.
- On the maintainer's Mac the CLI login's item held tokens for linear, mobbin, porkbun and posthog. The Pro login's item, `Claude Code-credentials-0175ce98`, the name `credentialsItem` gives its folder, held entries for the same four keys with an empty access token, which is what made each ask for a sign-in. The keys match because every login gets the same `mcpServers` (`copyClaudeConfig`).

`shareMcpSignIns` in `services/providers/claudeHome.ts` does the copy.

- It reads every Claude login's item: the CLI's own, and each added login whose folder still matches the path it signed in with. For each server the freshest sign-in wins. One with a token beats one without, and a later `expiresAt` beats an earlier one, since a refresh or a new sign-in always moves it later. On a tie the CLI's stays where it is, and nothing is written.
- It goes both ways because these servers swap refresh tokens on each refresh, and mobbin's and porkbun's access tokens last about an hour. Once one login refreshes, the other login's refresh token can be dead, so the new one has to reach every login, the CLI's own included, before that login refreshes.
- Only `mcpOAuth` entries that are behind change, plus a client secret a login lacks. The login and every other key stay. An item Kernel can't read whole is left alone, and Kernel never makes one. claude.ai connectors are skipped by name. They don't use `mcpOAuth` in 2.1.292 anyway.
- The Keychain has no compare-and-set. Claude Code saves a refreshed login token only when the stored refresh token is the one it sent, and Kernel can't do that. So Kernel reads an item again right before writing it and writes only what is still behind. A refresh of the CLI login that lands inside that one `security` call could be undone, and the CLI login would ask to sign in again. Kernel writes the CLI login's item only when another login holds a fresher sign-in, about once per token lifetime per server, so this is rare. Not copying back is worse: the CLI login would lose linear after every refresh on an added account.
- A server that got a sign-in leaves the login's `mcp-needs-auth-cache.json`. Claude Code skips a user server listed there for 15 minutes, and a plugin server or a connector for 4 hours, without trying its tokens.
- It runs in `Providers.claudeEnv`, right before the SDK starts a Claude process on any account, at most once every 2 seconds, and at once before an MCP check and after an MCP sign-in. The `security` calls are synchronous, about 7 ms each on the maintainer's Mac, because `claudeEnv` is synchronous and the process starts right after it. A locked Keychain gives up after 5 seconds.
- Writes go through `/usr/bin/security`, as Claude Code's own do, so each item keeps the access list the CLI gave it and no prompt shows. The secret goes in on stdin, or as an argument when it is too long for `security -i`, as the CLI does. Nothing read or written is logged. Tests pass an in-memory Keychain, and without one Kernel shares nothing.
- API key and legacy token accounts run without CLAUDE_CONFIG_DIR, so their processes already use the CLI login's item.
- Clearing a sign-in on one login with `/mcp` revokes its tokens at the server, so the other logins' copies stop working too, and the next sign-in anywhere reaches all of them. A clear that doesn't revoke is undone by the next share.

**claude.ai connectors stay with their account, and Kernel says which servers need a sign-in on each Claude login.** A connector such as Google Drive comes from the claude.ai account, so a Pro account has only the connectors set up on it. `accounts.checkMcp` shares the sign-ins, then starts Claude Code on the login in the home folder with the account's environment, lists its MCP servers and stops without sending a message. The servers it reads as `needs-auth` land on the account's row as `mcpSignIns`, a connector marked as one. What is left is a connector, or a server no login has signed in to. `accounts.mcpSignIn` runs `claude mcp login <server>` in a pty in the login's folder. The CLI needs a terminal for it. It aborts when stdin isn't one. For a user server the sign-in lands in that login's item and the next share copies it everywhere. For a connector, 2.1.292's `mcp login` opens claude.ai's page and exits, the user finishes there, and the connector loads from the account's next session. The browser has to be signed in to claude.ai as that account. `mcp login` revokes a server's stored tokens before it signs in. That is safe here, since the share ran first: a server that still needs a sign-in has no working token on any login. KERNEL-616.

**Adding a login Kernel already has is refused with "That account is already in Kernel."** On Claude a login is the same account when its email matches, ignoring case, and its claude.ai organization matches too when both are known. One email can hold a personal plan and a Team seat, and those are two accounts with their own limits. `claude auth status` gives `orgId`, and Kernel keeps it on each added login. The CLI's own login counts while it reads signed in. The refused login signs out of its new folder, which removes that folder's Keychain item, and the folder goes. The account's other login stays signed in. On Codex the email alone decides, since Codex's account read has no workspace id, so one email with two ChatGPT workspaces counts as one account. The refused home goes. Sign in again on a row doesn't check this yet. KERNEL-616.

**A switch checks the models agents start on against the models the new account offers.** The account's models come from Claude Code's initialize answer on that login, which sends no message, or from Codex's `model/list` in its home, read once per login and again when its email or plan changes. On 2026-10-13 the maintainer's Max and Pro logins both listed the same 12 models, so today the check fires for an organization that limits its models or a plan that drops one. The models agents start on are each agent's pick in the open rooms Kernel has read (`Team.pickFor`, KERNEL-550's check): its file's pin, else its role's default in Settings, Models and effort. Before any room is read, the roles' defaults stand in. After a switch, by click or at a limit, the account's row carries `missingModels` with the agents on each model, and the Inbox says so once a day per account and set of models. The plan defaults (KERNEL-225) follow the switch first, so on Pro, Kernel's own Sonnet default for the Lead is what gets checked, and only a model the user set or a file pins can be missing. At a limit, Kernel prefers an account with room that offers every one of those models (`spareFor`), and moves to one that lacks some only when no other has room. An account whose models can't be read counts as offering them. The reads run only on a Kernel built with `checkPins`, which the app passes and tests leave out. KERNEL-616.
