**A failed write of Claude Code's settings file names its one fix, and a link into a folder Kernel can't write is never written through.** `writeAtomic` in `services/hooksInstaller.ts` takes the first backup itself and turns three failures into a `HooksFileError`. EACCES names the folder the write needed and gives `sudo chown -R "$USER" <folder>`. EROFS finds the disk's mount point by walking up while `stat().dev` stays the same, and gives `sudo mount -uw <mount point>`. A settings file that is a link, whose target sits in a folder `access(W_OK)` refuses, throws before Kernel writes anything, backup included, and gives `rm <link> && cp <target> <link>`. A link into a folder Kernel can write, like a stow checkout, is still written through. Only the file itself counts as the link: a linked `~/.claude` folder gets the EACCES or EROFS card for the folder it resolves to. Other codes stay as they were, EPERM included. A read-only file in a folder Kernel can write is still replaced, as before. Commands use `~` for home and quote a path only when it needs quotes. KERNEL-461.

**A settings file Kernel writes keeps the owner's write access.** Kernel used to keep the old file's owner bits, so a 0444 file came back as 0400. It now adds 0600. The symlink fix copies a store file that is 0444, and Claude Code has to be able to write the copy afterwards. Group and others still lose read access (KERNEL-206). KERNEL-461.

**Check hooks shows one reason at a time: managed policy, then the last failed write, then the user's own disableAllHooks.** Managed policy comes first because nothing on this Mac changes it, and Kernel never edits managed settings. `services/claudeSettings.ts` reads it with `resolveSettings({ settingSources: ['user'] })`. `allowManagedHooksOnly` counts only from managed sources, as Claude Code reads it. `disableAllHooks` from managed settings uses the Managed card with the title "Your organization turns hooks off", the fix line "Ask whoever manages this Mac to turn hooks back on" and no button, since adding Kernel's hooks there wouldn't run them. The user's own `disableAllHooks` counts only while the merged settings still hold it. Kernel's hooks in managed settings count as installed, and they clear both `allowManagedHooksOnly` and the user's own switch, because managed hooks run under both. So Check again finds them once the admin pastes the block that Copy hooks for your admin copied. KERNEL-461.

**The hooks feature remembers a failed write until a write works.** Install, the start-up rewrite and Turn hooks on keep a `HooksFileError`'s problem, and any write that works clears it. Remove in Settings, Hooks doesn't, because a failed removal leaves the hooks installed, and the card would say they aren't. Its error message still names the fix. Turn hooks on only removes `disableAllHooks`, after the first backup. It doesn't install, so the event list shows next and says whether the hooks are there. KERNEL-461.
