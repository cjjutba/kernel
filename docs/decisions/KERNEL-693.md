**A wait across base branches is refused, and "Your branch now starts from it" needs the merge in HEAD.** A PR that merges into release/1.2 never reaches a branch that starts from main, so a wait on it could only end in a false note. `waitRefusal` compares the target's base with the waiter's, or for a hand-off with the base create_workspace would use, after stripping the room's remote, so `origin/main` and `main` count as one base. The Lead's create_workspace and wait_for_merge, a teammate's own wait_for_merge and the waits Kernel sets from a tracker's blockers all go through it. At release, a fast-forward that git calls "already up to date" still returns true, so Kernel also checks that HEAD contains `<remote>/<base>` for the base each target merged into. The brief asked for the waiter's own base there, but right after a fast-forward onto that ref the check always passes, so it can't catch a merge into another branch. A wait set before this change that spans two bases gets the rebase message instead of the note (KERNEL-693).
