**The PR poll reads each room's PRs in one GraphQL query, and reads a PR in full only when that query says it changed.** `gh.prs` asks GitHub for every open PR of a room by number, using aliases. Each PR comes back with its state, mergeability, `mergeStateStatus`, review decision, head, `updatedAt` and its head commit's checks, each with `isRequired`. The query also returns the rate limit. On cjjutba/kernel, eight PRs cost 1 point and 1.5 seconds. Kernel keeps a fingerprint of each PR's last full read (`fingerprintOf`: state, head, `updatedAt`, review decision, GitHub's block, and each check's name, state and whether it is optional). A PR gets the full read (review comments, conflicting files) only when its batch read's fingerprint differs, or when the batch read would move its state past the holds in `refreshPr`. A new review comment moves `updatedAt`, so it counts as a change. A workspace with no PR number yet, a PR the batch didn't return, and a test stub with no `prs` are read one at a time on KERNEL-216's schedule. A full read is two calls: `gh pr view --json number` for the branch, then one GraphQL query with the review comments. Amends D-006, where every read was `gh pr view`. KERNEL-388.

**The poll runs every 10 seconds while a PR is moving and every 30 seconds when every PR waits on someone.** A PR is moving while it is creating, has checks running, is being merged or resolved, or GitHub is still checking it for conflicts, and for 20 seconds after any PR's state changed. The poll is one `setTimeout` loop that reschedules after each poll, so two polls never overlap. Its first poll comes 30 seconds after start. Focusing Kernel's window, waking the Mac and a merge Kernel ran each ask for a poll within a second. Two asks are never closer than 5 seconds, and a Kernel that hasn't started never polls. Amends D-034 and KERNEL-216, where a 45 second interval drove the poll. The KERNEL-283 quick re-check stays as it was. KERNEL-388.

**Held Lead updates go out and waits retry every 45 seconds, never at launch.** The faster poll doesn't flush `leadUpdates` or run `retryWaits` on every pass, only when 45 seconds have passed since start and since the last time. So the Lead still hears nothing the moment Kernel opens (`leadUpdates.load`). Calling `pollPrs()` directly still does both, as before. KERNEL-388.

**Kernel's reads stay inside GitHub's rate limit.** Kernel's polling and every agent's `gh` calls share the token's 5,000 GraphQL points an hour. `PrCadence` reads what each batch says is left. Below a fifth of the limit, the poll runs once a minute even while a PR moves. Below a twentieth, it reads nothing until the reset, at most an hour. A read that GitHub refuses for its rate limit pauses the poll until the later of the batch's reset and the one `gh api rate_limit` reports, since the two can disagree. GitHub's "slow down" limit backs off from a minute, doubling up to 15 minutes. While the poll is paused, reads you start still run: opening a workspace, Fix checks, Merge PR. A merge that can't read says when the limit resets. The pause shows nowhere in the window yet. KERNEL-388.

**A read that fails changes no PR's state.** `GitHub.info` resolves null only when there is no PR: gh found none on the branch, GitHub can't find the number, or the folder has no GitHub repo or no gh. Any other failure rejects with `GhReadError`, which tells GitHub's rate limits apart. `refreshPr` keeps the workspace as it was and counts the failure toward KERNEL-216's backoff. Before this, any failure read as "no PR", so a network blip or a rate limit turned Creating back into Create PR. A Creating PR whose turn is over still goes back to Create PR once three reads in a row have failed, so its spinner can't stay forever. Amends D-034. KERNEL-388.

**Only the checks a repo requires decide its PRs.** When any of a PR's checks has `isRequired`, the rest are optional (`PrCheck.optional`). They don't make the PR "Checks failed" or "Checks running", don't hold `requireGreen` in `mergeBlock`, and aren't listed in `fix-checks.md` or the "failed on the PR" note. A repo that requires no checks keeps every check deciding, as before. The exceptions are the ones its room lists in `[pr] optional_checks` in `.kernel/settings.toml` or `settings.local.toml`: names that match whole and without case, with `*` for any run of characters. A check GitHub requires always counts, whatever the room lists. Optional checks still show in the Checks tab with "optional", and a failed one shows the muted warning icon instead of the red x. The key has no control in Settings yet. A required check that hasn't reported yet can't be told apart, so until it shows up, every reported check decides. Amends D-034, where "require green" counted every check. KERNEL-388.

**A ready PR that GitHub won't merge stays ready and says why.** `mergeStateStatus` BLOCKED with a required review, BEHIND under the "up to date" rule, or BLOCKED for any other rule, on a PR whose deciding checks passed, sets `PrInfo.blocked` and `Workspace.prBlocked` (review, behind, rules). The state stays `ready`, so the Lead's review flow (KERNEL-121) goes on. The header reads Open with Merge PR, as `design/redesign/PrOpen.png` draws a blocked PR. `mergeBlock` refuses with GitHub's reason, from the fresh read or, when the merge read nothing, the last poll's. The Lead's "ready to merge" lines and `list_workspaces` say what GitHub needs. DIRTY reads as a conflict, and UNKNOWN reads as checks (KERNEL-283). The Lead hears nothing new when a ready PR becomes blocked or unblocked. Amends KERNEL-115. KERNEL-388.

**Opening a workspace reads its PR through `refreshPr`.** `pr.get` used to read GitHub for the Checks tab and leave the header alone, so the two could disagree. It now refreshes the PR, which moves the header with what the tab shows. It reuses a full read from the last 10 seconds. An archived workspace, opened from History, is only read and keeps its state. KERNEL-388.
