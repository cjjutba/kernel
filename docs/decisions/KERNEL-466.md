**A hire, an edit, a retire or a restore is either for the user on this Mac or for the team, and it starts on "Just for me".** `agents.create`, `agents.save`, `agents.retire`, `agents.restore` and `hire_agent` take a `scope` of `me` or `team`, and leaving it out means `me`, as D13's notes say. Kernel no longer writes, changes or moves an agent file in the room's own checkout, so the checkout never holds an agent file nobody committed. Before this, New agent, hire_agent, Save changes, Retire and Restore all wrote there and left the user to commit or clean up. On the hire card, the Lead proposes a scope only when the user said which, the card shows the path that scope writes, and the user's pick comes back as the `allow` decision's `scope` and wins. KERNEL-466.

**A change for the team is one commit in a workspace of its own and a pull request through the room's code host.** Kernel cuts a workspace on the Lead from the room's base, with a branch named by the room's pattern, as a task's would be. It writes the change in that worktree, commits it with the user's git identity and hooks, and opens the PR through `hostFor(room).create` (KERNEL-453). Nobody works in the workspace, so the room's setup doesn't run, files.copy isn't copied and no brief waits. The PR poll, Merge and archive then handle it like any other workspace. If the change can't be written or committed, for example because the file isn't on the base or a hook refuses the commit, Kernel removes the workspace, worktree and branch, and the error says why. If only the PR fails to open, the commit stays in the workspace, and Create PR there finishes the job. An edit for the team carries only the fields this save changed from what the user saw, never the user's own edits. A file the repo hasn't committed isn't the team's, so an edit, retire or restore for the team refuses it before it makes a workspace. A room whose host can't open pull requests, which today means a local room, takes changes for the user only. KERNEL-466.

**A new agent for the user goes to ~/.claude/agents, and the user's edit of a repo agent goes to Kernel's data folder.** New agent and hire_agent write `~/.claude/agents/<id>.md`, which Claude Code runs in every folder and Kernel reads for every room (KERNEL-463). The name has to be free in the room's `.claude/agents` too, because a repo file with the same name wins. An edit of the user's own agent rewrites its file in `~/.claude/agents`, which KERNEL-463 refused and left for this ticket. An edit of a repo agent can't live in `~/.claude/agents`, because the repo file would win there in Claude Code and in Kernel. Kernel keeps the fields the user changed in `agent-overrides.json` in its data folder, by room and agent, and lays them over the file every time it reads the team. A field set back to what the file says follows the file again. It isn't kept in `.kernel/settings.local.toml`, because that file sits in the checkout, ignored but present, and P0 owns its keys. This is the one place Kernel and Claude Code read an agent differently: `claude` in a terminal runs the repo's file as written, while Kernel runs the user's version. The user chose that for themselves. A plugin agent still takes no edits, and a change for the team refuses personal and plugin agents, since the team's repo doesn't have them. Amends KERNEL-463. KERNEL-466.

**Retiring for the user hides the agent in this room on this Mac. Retiring for the team does the same and moves the file in a pull request. Amends D-003.** D-003 moved a retired agent's file to `.claude/retired-agents` in the checkout. For the user, the file now stays where it is, and Kernel records the retire in `agent-overrides.json`. Team lists the agent with the retired ones, and Restore clears the record. That goes for personal and plugin agents too, which KERNEL-463 refused to retire: retired for the user, one leaves this room and its file stays where Claude Code reads it. For the team, a PR moves the file to `.claude/retired-agents`, D-003's folder for D-003's reason, and the agent also leaves the user's team at once. So its open workspaces go to the Lead or the agent picked now, as the retire dialog says. A team retire whose PR closes without merging leaves the agent retired for the user until they restore it. A hire or an edit for the team changes nothing locally before it merges, because nothing has to be handed off. Restore clears the user's own retire first. A file in `.claude/retired-agents` comes back to `~/.claude/agents` for the user, or in a PR that moves it back for the team. KERNEL-466.

**An agent hired or brought back for the user joins their team in this room even when `[team] roster` leaves it out. Amends KERNEL-465.** KERNEL-465 put a hire and a restore on the room's roster, so they wouldn't land off the team. Writing the shared `.kernel/settings.toml` for an agent only this user has would change the checkout and put a name on the team's roster that nobody else can resolve. So Kernel marks the agent as joined in `agent-overrides.json` and adds it to the roster when it reads the room's saved `[team]`. A choice `setTeam` weighs is read exactly as passed. A roster the user then picks in Settings or Room setup is the team they want, so it clears those marks. A hire or a restore for the team adds the agent to the roster in the same commit as its file, when the base has a roster. KERNEL-466.

**Seeding a starter team, adding a starter agent and Customize still write into the checkout.** D13 drew the choice for hire, edit and retire only. For the user, a starter team in `~/.claude/agents` would join every room on the Mac. For the team, an empty room would wait on a merge before it could work. Customize also writes `[team]` in the shared settings file. Each needs a choice of its own, so they are left as they were. KERNEL-466.
