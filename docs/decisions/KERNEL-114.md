**Archive on merge in Settings, Git archives a workspace once its PR merges, and the same switch covers review cleanup.** The switch defaulted to on but nothing read it, so merged workspaces piled up, each with a session that could keep a Claude process running. Of the three options in KERNEL-114 (make it work, keep an on-screen workspace until the user leaves it, remove the toggle), KERNEL-204 chose the first. The room's own `[workspace] archive_on_merge` wins over the app-wide value. Off means nothing archives on its own, including the reviews KERNEL-131 archived before. A PR closed without merging keeps its workspace, because its author may reopen it. Its reviews still go. Only a worktree workspace goes. Kernel can't check uncommitted changes in a workspace on the room's own checkout, and the Lead's workspace is one of those. That rule holds before Kernel has read the team, so it doesn't depend on knowing which agent is the Lead.

Kernel checks the same things archive_workspace does (`archiveGuard.ts`): a running agent, uncommitted changes, a git status it can't read. Merged work is also kept when its branch has commits GitHub doesn't, because the sidebar is where the user would find that unfinished work. "GitHub has it" counts the PR's head commit as well as the remote branch and the base. A squash merge leaves the commits off the base, and GitHub often deletes the branch, so without the head every squash-merged workspace would look unpushed. A workspace whose agent is working goes when the turn ends, through the same saved set as reviews. That set keeps its old name and meta key, `reviewsToArchive`, so a review marked before an update still goes. A kept workspace gets a note in the log and Kernel doesn't try again.

On a merge, Kernel archives the reviews and releases the workspaces waiting on that merge (KERNEL-259) at the same time, then archives the work once both are done. Just before it archives, it checks the PR state again: work that moved to a fresh branch is no longer the merged work. Releasing a wait and the Lead's merged update read only the saved PR state and `mergedAt`, so archiving the work afterwards breaks neither.

Work that merged before this shipped gets no PR event, so the first start archives it, with the same checks. That sweep runs once (meta key `mergedSwept`). On every start it would archive again a merged workspace the user restored from History, and it would repeat the note for a kept one. Turning the switch on later archives the next merges, not the old ones.

A workspace Kernel archives while it is on screen opens the Lead's chat with a toast, as KERNEL-132 does for reviews, instead of jumping to History. That needed `afterArchive` in the renderer to cover a merged workspace as well as a review. KERNEL-114
