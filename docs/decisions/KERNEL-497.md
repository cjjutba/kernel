**Blockers on a PR's latest commit hold the merge whatever the reviewer rule says, and only a person can merge past them.** Amends KERNEL-115 and KERNEL-376. Under KERNEL-115, `mergeBlock` read the verdicts only with "Wait for the reviewer's approval to merge, when a review ran" (Settings, Pull requests) on. With it off, KERNEL-490's PR showed a green Merge and counted toward "1 ready to merge" while its row read "Theo found 1 blocker". With it on, the only way past a blocker was to turn the setting off.

Now `headBlockers` in `src/shared/merge.ts` finds the latest review with blockers on the head commit, the one GitHub reports when the merge read it. `mergeBlock` refuses on it with the rule on or off: "Theo found 1 blocker on the latest commit. Merge anyway to go ahead." The rule still decides the other half. With it on, a PR a reviewer looked at waits until someone approves its head commit. With it off, it doesn't wait. Since blockers count either way, `mergeNeedsPr` needs GitHub's read for any PR with a review, so a failed read refuses the merge rather than judging blockers against a stale head.

`mergeBlock(..., { override: true })` is Merge anyway. It skips the review and nothing else. A PR that isn't ready or open, red checks, conflicts, a PR GitHub is still checking for conflicts and GitHub's own branch rules all still refuse. Only `pr.merge` carries `override`, and only a person's click sends it. `mergeAll` never passes it, so Merge all stops at a PR with blockers and gives the reason. Kernel's merge_workspace never passes it either. It skips such a PR before trying, with "Skipped #N: Theo found 1 blocker. Merge it from its Merge anyway button if you want it in." Blockers are a reviewer telling the team the work is wrong. Merging past them is a call the user makes with the PR in front of them, not one the Lead or a batch makes for them. KERNEL-497.
