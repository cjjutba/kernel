**An added Claude account is a full `claude auth login` in a folder of its own, not a `claude setup-token` token.** Amends KERNEL-406, as KERNEL-560's spike recommended. Each new Claude subscription account gets `<dataDir>/claude-homes/<id>/` as its `CLAUDE_CONFIG_DIR`, and the login's Keychain item is named after that exact path string, so Kernel builds it one way, keeps it on the account as `home`, and passes the same string to the login, every process and the logout. KERNEL-406 chose a token because the token left the CLI's own login alone. The folder does too: logging in, switching, renaming, signing out and removing an added account never touch the CLI's own Keychain item, and every `auth logout` Kernel runs for an added account carries its folder.

- Everything in `~/.claude` but the login's own files is linked into the folder (`linkClaudeHome`), right after the login and again before each Claude process: settings and Kernel's hooks, chats, plans, history. `skills` and `plugins` are real folders whose entries are links, all but `synced`, where claude.ai syncs each org's own content. An empty folder the CLI made where a link goes gives way to the link. One with something in it stays.
- Before each process, `mcpServers` and `projects` come over from `~/.claude.json` in place of the folder's own, so MCP servers added in a Kernel terminal reach every account. Every other key describes the login and stays. A file that can't be read whole, as when the CLI is writing it, changes nothing.
- Removing an account signs it out, then deletes its folder entry by entry with `lstat`, so a link goes as a link and nothing in `~/.claude` is touched.
- A folder whose stored path no longer matches, because the data folder moved, reads as signed out. Sign in again logs in at the new path and signs out the old one. Remove signs out both.
- Sessions get `CLAUDE_CONFIG_DIR` and no `CLAUDE_CODE_OAUTH_TOKEN` from the Mac, so the folder's login is what pays (D-018). An API key account is as KERNEL-523 left it.

**Add account asks for nothing but the browser sign-in.** The Name and Plan fields go. The login's own `auth status` gives the email and the plan, the email names the account until the user renames it, and the plan defaults follow the plan Claude Code reports, so an upgrade or a downgrade on claude.ai carries over at the next read (KERNEL-225). Codex keeps its email as the name. The code field shows at once, since `claude auth login` shows its prompt from the start.

**Every account can be renamed, the CLI's own login included.** The nickname is kept in `accounts.json`, the CLI login's under the provider's `cli`. An empty name goes back to the email, or keeps the name it had when there is no email to go back to. A name that was the email follows a new email after a sign-in.

**Kernel reads every subscription account's usage and sign-in, not only the active one's.** A live process on the account answers. Without one, a Claude account gets a short session in its folder after `auth status` says it is signed in, and a Codex account gets one `account/read` in its home. The reads run at launch and when the account menu or Settings, Providers opens (`usage.get`, which answers with the windows Kernel has at once and pushes what the reads find, since the window waits on it at launch), every 10 minutes while any agent works, and at once when the account in use nears or hits a limit and the provider has another account to read. An account read in the last minute isn't read again unless the limit asks. Holds, the room pause and `nearLimit` still go by the account in use alone. Legacy token accounts can't read the usage call, so their meters stay as of their last turn, and API key accounts have no windows.

**A login going from signed in to signed out tells every window and saves one Inbox notice.** The last sign-in read is kept on the account in `accounts.json`, so a restart never announces a sign-out it already did, and an account never read before never does. The user's own Sign out says nothing. At most one notice per account per day, since a session the server refuses while `auth status` still reads signed in goes round the 10-second check.

**Legacy token accounts keep running until the user signs in again.** They are flagged `legacyToken` for the row. Sign in again on one runs the full login into its folder, keeps its id and nickname, reads its email and plan, and drops the token. No new account uses `setup-token`, so Kernel no longer runs it.
