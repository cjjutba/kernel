**A new chat with Kernel answers before its fetch and worktree, and its first message waits for the worktree.** KERNEL-405 had ⌘N (`lead.start`) fetch the room's remote, make the worktree, link node_modules and send the first message before it answered, so Create showed "Sending" for as long as the network took. Now `newLeadChat` answers once the chat, its first tab and its workspace are saved and pushed. The workspace already has the branch and folder it will use, and `Workspace.worktreePending` says git hasn't made them yet. `Lead.buildChat` does the rest in the background: `Workspaces.makeWorktree` fetches, reads the base again, makes the worktree and links node_modules, then setup runs through `setUpWorkspace` as before.

The first message waits in the tab's queue (`Sessions.hold`) until the worktree exists. Then KERNEL-490's rule decides: it goes while setup runs, or, with Wait for setup on and a setup script that runs on create, it waits for setup. `Sessions` also keeps any other message to a chat with no worktree in its queue, and `post` refuses one, so nothing starts a turn in a folder that isn't there.

The checks that need no network still run before anything is saved, so New chat shows them: no Lead, a picked base that isn't here and isn't on the remote, and a branch name git won't take. A picked base on the remote waits for the fetch, which may bring it, and a strict read after the fetch fails the workspace when it doesn't. The branch and folder are picked inside the room's branch lock with the record saved in the same step, and every other pick (`freeBranch`, `freeWorktreePath` with `pendingNames`) treats the names a pending chat holds as taken. A name someone takes meanwhile gets a suffix when git makes the worktree.

When git won't make the worktree, the workspace is `failed`, `worktreePending.error` holds git's `fatal:` line, the setup log says it, and the message stays queued. Run again (`scripts.run` with `setup`) makes the worktree, then sets up. Send anyway does nothing there, since there is nowhere to send to. A quit in the middle leaves the workspace in `setup`, and `recoverSetups` fails it at the next start with "Kernel quit before it made the worktree." A worktree git made before the quit is taken as it is. An archive waits for a worktree being made, then removes it, and nothing starts in it meanwhile.

Everything that reads `ws.path` skips a workspace with `worktreePending`: the right panel's reads answer empty, `checkFolder` never flags it as gone, git status, checkpoints, PR reads and the branch sync leave it alone, `syncLead` and `moveNow` skip it, the shell starts on the first keystroke after the worktree exists, and scripts, file reads, commits, discard and Open in refuse with "This chat's worktree isn't made yet."

`fetchOrigin` reuses a fetch that passed in the last minute. `lead.prefetch` starts one without waiting, so New chat can fetch when it opens and Create finds it done. A `fresh` fetch, as `syncLead`, Continue, waits and the base watch ask for after a merge, always fetches. A room with no commit keeps Kernel on the checkout with nothing in the background, as before.

Amends KERNEL-405 (⌘N fetches and makes the worktree before it answers) and KERNEL-490 (the first message goes at once when nothing waits for setup). KERNEL-542.
