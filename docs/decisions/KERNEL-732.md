**An overrule of a review's blockers belongs to one head commit, and only a merge a person starts goes past it.** Amends KERNEL-497. Under KERNEL-497 the only way past blockers was Merge anyway, which asked every time and left no record. On cjjutba/kernel#688 the PR header kept reading "Blockers found" after the maintainer overruled both blockers in chat.

Now `Workspace.overruled` holds the head commit, the kinds of review overruled, who did it (`user`, or `lead` on the user's words) and an optional note. `kindStates` in `src/shared/merge.ts` drops an overruled kind from `blocking` and from `waiting` while `overruled.head` is the head it reads, and lists it under `overruled`. `headBlockers`, `mergeBlock`, the Lead's merge_workspace and the Team update all read through it, so none needs its own check. The head is GitHub's when there is a fresh read. A new commit matches no overrule, so whatever its reviews find holds the merge again. Kernel doesn't delete the old record. It just stops matching. An overrule of the code review leaves the security review's blockers in place, and a kind that finds blockers later on the same head needs a second overrule, which adds it.

An overruled kind is not an approval. Auto-merge never weighs a PR with one, and `autoMergeBlock` refuses it with its own reason, because an optional kind's blockers were all that kept some PRs from merging by themselves. The overrule only clears the way for a Merge someone clicks, or a merge_workspace the user asked for.

`reviews.overrule` refuses when nothing blocks the head or Kernel doesn't know it, so it never records an empty overrule. `clear` takes it back. The Lead's overrule_blockers checks the user's quoted words against their latest message, as create_workspace's go_ahead does (KERNEL-678), and only in a turn the user started, as merge_workspace does (KERNEL-352). A review's id resolves to the PR it reviewed. KERNEL-732.
