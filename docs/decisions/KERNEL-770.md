**Each chat with Kernel has a mode, Hand off or Build here, and only the user switches it.** Hand off is how every chat worked before: Kernel plans, hands tasks to teammates and edits nothing. Build here has Kernel make the change itself in the chat's own worktree, test it as the repo's AGENTS.md or CLAUDE.md says, open the PR and fix it. The mode lives on the chat's workspace as `Workspace.leadMode`, and unset is Hand off, so chats from before keep working as they did. A new chat takes the room's `[agents] lead_mode`, else `team.leadMode` in the app's settings, else Hand off (`newChatLeadMode` in `@shared/leadMode`). Only a new chat reads the defaults, so changing one leaves open chats alone. `lead.setMode` switches a chat, leaves a `leadMode` divider in each tab, and ends the chat's idle processes with `Sessions.restartIdle`. The next turn starts with the new prompt and tools, and a running turn finishes in the mode it started in. There is no mixed mode. When Build here work spans lanes or is bigger than one PR, Kernel stops and calls `suggest_hand_off` with its reason. That puts a `modeSuggestion` item in the chat, which the app draws as a "Switch to Hand off" button that calls `lead.setMode`. Kernel never hands off or switches on its own. Amends the plan-only Lead role in KERNEL-67 and KERNEL-129. KERNEL-770.

**The Lead's rule splits into shared lines, Hand off's lines and Build here's lines.** `LEAD_RULE` keeps its text for Hand off. `LEAD_BUILD_RULE` drops the hand-off lines ("Never build a task yourself", approval means hand it off now, go-ahead quotes, branch and wait_for advice) and adds its own. The lines about Team updates, teammates' questions, reviews, writing style, other chats and read_plans stay in both, because teammates a chat handed work to before a switch carry on. Both go through `forProvider` for Codex. In Build here an approved plan gets "Plan approved." with no hand-off instruction, and the Stop hook doesn't remind the Lead to hand off. KERNEL-770.

**In Hand off, Kernel can't edit a file whatever its tools line says. In Build here, it can whatever the tools line says.** On Claude, `toolPolicy` takes the mode. Hand off refuses Edit, Write, MultiEdit and NotebookEdit with a reason that names the mode, and hides NotebookEdit. Write and Edit still reach a `.md` file in `~/.claude/plans` (D-023). Bash stays, for git and gh. Build here counts Edit, Write and MultiEdit as listed even when the tools line leaves them out. `disallowedTools` still takes them away, since that line is an explicit "never" in the file. Amends KERNEL-397, which said a tools line always holds. KERNEL-770.

**On Codex, Hand off runs every turn in the read-only sandbox and declines every file change outside `.kernel/shared`.** Codex 0.153.4 has no turn setting that keeps the workspace writable for git but closes it to `apply_patch`. Permission profiles exist only as config file entries. Under `workspace-write`, a patch inside the workspace never reaches Kernel, so declining it isn't enough (KERNEL-549 hit the same limit). The read-only sandbox makes every patch ask, and `approveFiles` accepts only changes whose every path is under the workspace's `.kernel/shared`, where share_file's files go. Those then follow the permission mode as before. Git commands that only read run in the sandbox. One that writes, such as a commit or a fetch, asks to leave it, as any command does on Codex (KERNEL-447). Build here runs `workspace-write`, the same as a teammate. KERNEL-770.

**create_workspace refuses a task in Build here, and a hand-off from a chat with uncommitted changes says so.** In Build here, create_workspace answers "Switch this chat to Hand off to give tasks to teammates." for anything but `review_of`, which still starts a review. In Hand off, when the chat's own worktree has uncommitted changes, create_workspace's result and the plan card carry a line saying teammates start from the base and won't see them. It doesn't block, and the edits stay in the worktree. The tools read the mode once, when the session starts, matching the prompt. KERNEL-770.

**A switch updates a tab's divider in place when it is the tab's last item, so switching back and forth leaves one.** Anything after the divider, a reply or a note, keeps it, and the next switch adds its own. Each tab goes by its own last item. The Bypass permissions note works the same way within a turn: turning Bypass on again updates it, and turning it off before the turn ends rewrites it to say so. KERNEL-809.
