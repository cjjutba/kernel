**A merge reads the PR from GitHub first, every time.** `mergePr` reads GitHub for any PR whose saved state is ready or open, whatever Settings, Pull requests asks for. The saved state is only as fresh as the last poll, and a merge into the base sends GitHub back to working out whether every other PR conflicts. That is when Kernel merges several PRs in a row (KERNEL-352). A merge is rare and the user or Kernel starts it, so one more `gh` read costs little. `mergeNeedsPr` now only decides whether a failed read stops the merge: with green checks required, or a reviewer's verdict on the PR, Kernel refuses with "Could not read the pull request from GitHub." Otherwise the merge goes ahead on the last poll and GitHub's own merge has the last word, as before. Amends KERNEL-115, where `mergePr` read GitHub only when `mergeNeedsPr` said the rule needed it. KERNEL-376.

**`mergeBlock` refuses a fresh read that isn't settled and mergeable.** When the merge has GitHub's read, the PR must read ready or open on it too, with `conflictsUnknown` unset. Anything else refuses with "This pull request is not ready to merge.", the same message the saved state gets, and nothing merges. The rule lives in `mergeBlock`, so every caller of it follows it. The check runs after the green checks rule, so a PR that GitHub reads as `checks` or `cifail` because of its checks still gets the message that names checks. Amends KERNEL-283, which kept `mergeBlock` on the saved state and left a PR GitHub was still checking for conflicts to GitHub's own merge. KERNEL-376.
