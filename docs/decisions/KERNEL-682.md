**A new room's settings.toml sets no script, and Kernel suggests scripts instead of writing them.** Kernel used to guess the stack from the lockfiles and write `setup = "pnpm install"` into the `.kernel/settings.toml` of a new room. The guess was often wrong for a repo that already had a setup script in another tool, and the user found out when a workspace's setup failed or installed twice. Now `defaultRepoSettings` writes every script as a comment. The stack still picks the examples, so a pnpm repo reads `# setup = "pnpm install"`. The only live value is the default copy list. An existing settings.toml is never rewritten, so rooms made before this keep the setup line they have.

Amends D-078: Kernel no longer writes its install command as the room's setup script. Room setup's one-time "Install dependencies" step, in the main checkout, stays as it is.

Amends KERNEL-209: the second writer that counted as trusted without asking, the settings.toml Kernel writes for a new room, is gone. That file has nothing to trust, so room setup no longer calls `trustCurrent`. It still runs the trust check (`untrusted`) after writing the file, so the room knows where it stands on what the repo brought: a committed `settings.local.toml`, or a `package.json` with install scripts. A Settings save is still the one writer that can count as trusted. The only other trust change is the Install step's command, below.

Amends KERNEL-444: an install that runs the repo's own code always waits for trust in room setup, and is no longer skipped when the room has nothing else to trust.

The Install step still asks before it runs repo code. For a new room whose install runs the repo's own code, such as `bundle install`, `uv sync`, `composer install` or `cargo fetch` (KERNEL-444), the written `setup = "bundle install"` used to be the text the user was asked to trust. The file no longer has that line, so the Install step's command is now part of what the room trusts, as `ScriptTrust.install`, for as long as the step waits (`heldInstalls`). The trust dialog shows it as "Install dependencies". Trusting it runs the install once in the main checkout and releases held workspaces, as before. The command leaves the subject once the install has run. Trusting also saves the hash of the room's text without it, so the room doesn't ask again afterwards, the way KERNEL-260 handles package.json's install scripts. This replaces KERNEL-444's skip ("run it yourself if you trust it"). That rule covered a repo whose settings had nothing to trust, where nothing would ever ask. Now the command itself is something to ask about, so that repo asks too. The trust covers the Install step's command and nothing else. It sets no setup script, and workspaces run only the scripts the room's settings set. A JavaScript repo with install scripts asks the way it did before (KERNEL-260).

`scripts.suggest({ roomId })` returns what the room could take, in this order: Conductor's scripts, Superset's, then the install the lockfiles point to (`services/scriptImport.ts`). It only reads. The renderer saves a suggestion's patch through `settings.setRoom`, so an imported script goes through the same save and the same trust rules as one the user typed. A suggestion that asks for what the room already runs is left out.

Conductor: `.conductor/settings.local.toml` over `.conductor/settings.toml`, key by key and run script by run script. `conductor.json` is read only when neither TOML file exists. A `[scripts.run.<id>]` table becomes a named run script. The one marked `default`, or the only one, becomes the room's Run. Kernel skips an entry that is hidden or not available locally, and a name Kernel can't use gets a note. `run_mode` maps to the room's run mode, and `file_include_globs` becomes a note pointing at Files to copy, since a suggestion carries scripts only. Superset: `.superset/config.json`, then the user's override at `~/.superset/projects/<repo path>/config.json`, then `.superset/config.local.json`, whose list replaces a key or wraps it with `before` and `after`. Commands join with `&&`, and teardown becomes the archive script. With no config, `.superset/setup.sh`, `run.sh` and `teardown.sh` become `bash .superset/<name>.sh`. Detected: the lockfiles' install as the setup script, with no guess at a run script.

`convertScriptVariables` rewrites the other tools' variables to Kernel's, such as `$CONDUCTOR_PORT` to `$KERNEL_PORT`. It matches whole names only, in `$X`, `${X}` and inside `$(( ))`, so `$CONDUCTOR_PORTAL` is left alone. A `CONDUCTOR_*` or `SUPERSET_*` name Kernel has no match for stays as written and adds a note to the suggestion. The function is exported for KERNEL-683.

The repo may be a clone of someone else's, so every file is read the way files.copy resolves one (KERNEL-209): a regular file whose real path stays inside the repo, at most 256 KB. A link that leaves the repo, a bigger file, or TOML or JSON that doesn't parse gives no suggestion from that source and no error. Superset's user override is the one file read outside the repo, and the same check keeps it inside `~/.superset`. Reading these files runs nothing. The text only runs after the user saves it and the room's trust rules pass. KERNEL-682.
