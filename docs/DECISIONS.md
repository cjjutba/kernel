# Decisions

> This is a record of how Kernel was built, kept as written. "CJ" is the maintainer.

Add an entry when you make a choice someone might later "fix". Newest at the bottom.

**D-001 Sessions run on the Claude Agent SDK, not a wrapped terminal.** Structured messages give a real transcript, `canUseTool` gives approvals, `rate_limit_event` gives usage. The big terminal (KERNEL-12) is the exception, for people who want the TUI.

**D-002 The Lead orchestrates through Kernel's own MCP tools, not the experimental agent teams flag.** Kernel owns worktrees, branches and approvals, and the flow works on any Claude Code version that runs the SDK. Agent teams hooks (TaskCreated, TeammateIdle) are still consumed when present. KERNEL-27 decides whether the agent teams check on first run stays a requirement.

**D-003 Retired agents move to `.claude/retired-agents/`, not `.claude/agents/retired/`.** A subfolder inside `.claude/agents` might still be loaded by Claude Code; moving it out guarantees the agent stops loading.

**D-004 Current-branch workspaces baseline with `git stash create`.** It records pre-existing changes without touching the working tree, so diffs and checkpoints show only the agent's work.

**D-005 SQLite with JSON columns for v1, Drizzle later.** Shapes are still moving. Swap to Drizzle with drizzle-kit migrations once the contracts settle after v1.

**D-006 GitHub through the `gh` CLI.** It already holds CJ's auth and handles PRs, checks and review comments.

**D-007 One approvals queue for everything.** Tool permissions (SDK and hooks), plans and questions share one model, so the Inbox, floor cards and inline chat cards stay in sync.

**D-008 PR actions are delegated to the agent with instruction files.** Create, fix checks, address review and resolve conflicts are messages to the agent, editable in Settings > PRs. Kernel only reads state and merges.

**D-009 Scripts run in the user's login shell, falling back to /bin/sh.** So nvm, pnpm and PATH tweaks apply.

**D-010 Linear holds the work, the repo holds the knowledge.** Issues and status live in Linear (team Kernel). Docs, design PNGs and decisions live in git so every session reads them locally.

**D-011 Contracts first, then parallel lanes.** KERNEL-8 and KERNEL-9 define every shared channel, type, route and component before the Build lanes start, so lanes rarely edit shared files.

**D-012 v1 includes the light theme, code signing, notarization and auto-update.** CJ's call, October 7, 2026. CJ has an active Apple Developer Program membership, so KERNEL-30 signs and notarizes for real.

**D-013 Tests run on Electron's Node.** postinstall builds better-sqlite3 for Electron's ABI, so `pnpm test` runs vitest with `ELECTRON_RUN_AS_NODE=1 electron`. Plain `pnpm exec vitest` fails with `NODE_MODULE_VERSION`. Run one file with `pnpm test test/kernel.test.ts`. The script calls `node_modules/vitest/vitest.mjs` directly, which pnpm links at the top level because vitest is a direct dependency. KERNEL-5, KERNEL-110.

**D-014 Dependency install scripts are allowlisted in `pnpm-workspace.yaml`.** `allowBuilds` approves electron, better-sqlite3 and node-pty, pinned to their versions, and denies esbuild, fsevents and electron-winstaller, which the app doesn't need on macOS. pnpm fails the install on any other package with an install script (`strictDepBuilds`, on by default), so nothing runs unreviewed. After bumping a pinned package, change its version in `allowBuilds`, or the install fails with `ERR_PNPM_IGNORED_BUILDS`. A new native module needs an entry too. This used to be npm's `allowScripts` in `package.json` (D-110). KERNEL-5, KERNEL-110.

**D-015 The window opens before the kernel finishes booting.** IPC handlers wait for `kernel.start()`, so the renderer can show a loading state (KERNEL-27). A failed boot shows a native error box and quits. Keep `createWindow()` ahead of `start()`. KERNEL-5.

**D-016 Kernel only steps in for risky Bash.** Sessions load CJ's user settings, and his allow list covers every Bash command, so `canUseTool` never sees Bash on his machine. An in-process PreToolUse hook applies Kernel's lists on top: Never allow returns `deny`, Always ask returns `ask` (which reaches `canUseTool` and the Inbox even past an allow rule or another hook's allow), and everything else is left to CJ's own settings. "Always allow in this room" saves the command, or Claude Code's suggestion when it is a single `prefix:*` Bash rule it allows saving, on the room (`Room.allow`). A room rule beats Always ask, but a prefix rule never covers a chained command (`&&`, `;`, `|`, a newline, `$(`), so `npm run build:*` can't wave through `npm run build && pnpm db:reset`. Other hooks can rewrite the command before `canUseTool` sees it (rtk adds a prefix), so rules and the Inbox use the command the PreToolUse hook saw, keyed by tool use id. CJ's call, KERNEL-6.

**D-017 Usage comes from the experimental usage call, on demand, with rate_limit_event as the fallback.** `rate_limit_event` arrives once per session start and when limits change. Besides the named window it carries `unifiedWindows` (not in `sdk.d.ts`) with the 5-hour and weekly numbers as 0 to 1 and epoch seconds. `usage.get` asks a live session's `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({ skipBehaviors: true })`, which reports 0 to 100 and ISO times, converts it to the event units, and keeps the event data when no session is live or the call fails. Nothing polls. Recheck the method name when the SDK pin moves. KERNEL-6.

**D-018 Sessions never get an API key.** The session env drops `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`, so Claude Code bills the Claude plan through its own login. If the init message still reports an `apiKeySource` other than `none` (an `apiKeyHelper` in settings, say), the chat gets a note and the room log a line. Verified live: `none` on CJ's Max plan. KERNEL-6.

**D-019 What the real transcript looks like.** Thinking comes back with empty text unless the session asks for `thinking: { type: 'adaptive', display: 'summarized' }`, so Kernel always does. Checked on Sonnet 5.5 and Haiku 4.5. The CLI sends a `system/init` at the start of every turn, and Kernel marks the chat running from it. An interrupt ends the turn with a `result` of `error_during_execution`, which Kernel hides behind the interrupted row. A follow-up sent mid-turn can join the running turn or run right after it. New chats pass their own `sessionId`, so Kernel knows the id before the first hook fires. KERNEL-6.

**D-020 Outside sessions start on their first hook.** Claude Code skips http hooks for SessionStart ("HTTP hooks are not supported for SessionStart", CLI 2.1.292). The hook server logs `session.start` when it first hears from a session id, and forgets the id on SessionEnd. The installer still writes a SessionStart entry, which does nothing. KERNEL-6.

**D-021 Fixture mode replaces the kernel, not the data.** With `KERNEL_FIXTURES=<Screen>` set, `src/main/index.ts` never constructs `Kernel`. `fixtureHandlers` answers every channel from an in-memory fixture, typed as the same `Handlers` map, so a new channel fails typecheck until fixtures answer it. Writes return a value and change nothing, so a shot is the same every run. userData moves to a temp folder, so Electron's cache never touches the real profile and a fixture run can sit beside a running Kernel. The harness makes one folder per launch and deletes it after the app exits; Kernel can't delete its own, because Chromium writes to it until the process ends. Manual `KERNEL_FIXTURES` runs reuse one `kernel-fixtures` temp folder. The harness launches Electron once per screen with `--force-device-scale-factor=1`, which matches the 1x canvas PNGs and keeps states from leaking between shots. A fixture exists only for a screen today's UI can show; the issue that builds a screen adds its fixture. KERNEL-7.

**D-022 useStore keeps shallow-equal results.** Selectors like `s.agents[roomId] ?? []` and `.filter(...)` return a new array on every read, and useSyncExternalStore re-renders whenever the snapshot changes identity, so every screen with data looped until React error #185. `useStore` now returns the previous result while the new one is shallow-equal. Found by the first fixture shots. KERNEL-7.

**D-023 Autopilot guardrails live in a hook as well as permission rules.** `.claude/hooks/guard.mjs` denies edits outside the repo, force pushes, pushes to `main`, `rm -r` outside the repo and the live test. Permission rules can't express "outside this repo", and the hook still applies when a session runs with permissions bypassed. Temp files go under `shots/`. See docs/AUTOPILOT.md. One write outside the repo is allowed: a `.md` file directly in `~/.claude/plans`, where plan mode writes its plan. Without it the plan approval prompt came up empty. The guard walks every path part by part like the OS does, following each symlink (dangling ones too) before it applies the next `..`, and denies a symlink loop. That applies to the repo check as well. So `plans-evil/`, a subfolder, a `.md` link to `settings.json` or to a file that doesn't exist yet, and `plans/d/../x.md` with `d` a link are all denied. The plans folder itself must be a real folder. If it were a link to `~/.claude`, `CLAUDE.md` would pass as a plan. KERNEL-63.

**D-024 Contracts are written down before the screens exist.** `src/shared/ipc.ts` lists every channel the 119 screens call. A channel no lane has built rejects with `NotImplemented` naming its issue, from the `UNBUILT` map in `src/main/kernel.ts`; the lane that builds it deletes its line and adds the handler. Fixture mode answers every channel anyway, from optional `Fixture` fields or defaults. The store stays flat, one top-level key per domain plus `ui` (route, modal, menu, toasts, banner, theme, stage, workspace panes), and every write goes through the typed groups in `actions`. Flat keys keep today's selectors (`s.items[chatId]`) working; nested slices would have meant rewriting every screen for no gain. `Route` has one entry per screen family, and onboarding and settings render without the sidebar like their PNGs. Each family's component sits in `screens/<family>/`, named in the Component column of `docs/SCREENS.md`. Families with a prototype re-export it until their lane replaces the file. `AppSettings` and `RoomSettings` moved to `src/shared/types.ts` so Settings screens can read them. KERNEL-8.

**D-025 Themes are scoped attributes, and the component gallery is a dev route.** Tokens in `tokens.css` are defined under `:root, [data-theme='dark']` and `[data-theme='light']`, so any subtree can opt into a theme (the gallery shows both side by side) and `ui/theme.ts` sets `data-theme` on `<html>` for the app, resolving "system" from `prefers-color-scheme`. Light values are the `LMAP` from `design/canvas/source/build.py`, with `--muted` darkened to `#62666d` so text keeps 4.5:1 on every light surface (4.6 on hover, the lowest); KERNEL-29 may adjust them. The gallery (`ui/DevUi.tsx`) is the `{ name: 'devUi', page }` route. In dev, `#/dev/ui/<page>` opens it and the gallery links its four pages. Production has no way to reach it, except that the `DevUi`, `DevUiDisplay`, `DevUiOverlays` and `DevUiDialogs` fixtures force the route for `pnpm shots` (the harness runs a production build). Those fixtures have no PNG and are exempt from the PNG-name test. KERNEL-9.

**D-026 Meter colors follow the issue, not SettingsAccount.png.** The canvas meter in `SettingsAccount.png` has its colors inverted. KERNEL-9 asks for a bar that turns white at 85%, so `Meter` is grey below 85% and the ink color from 85%: it gets brighter as you near the limit. Size follows the canvas (6px, radius 3, `--line-2` track). KERNEL-9.

**D-027 Agent teams stays a first-run check, but only for Kernel's own sessions.** Kernel orchestrates through its own MCP tools, so agent teams are not strictly needed to run a Lead. The canvas (`SetupTeamsOff.png`) still shows the check, and the sessions that Kernel starts use it for TaskCreated, TaskCompleted and TeammateIdle hooks, which feed the Board. The check reads `models.agentTeams` in Kernel's settings, and "Turn on for Kernel" sets it through `setSettings` like the Models page toggle. `sessionEnv` sets `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` for the SDK sessions and the big terminals Kernel starts when the setting is on, and removes it when it is off, whatever the user's shell exports. A change applies to each agent's next session. Kernel never writes the variable into the user's shell or `~/.claude`. It blocks Continue like every other failing check, and one click clears it. Until KERNEL-73 nothing set the variable, so the setting did nothing. KERNEL-27, KERNEL-73.

**D-028 Rooms are created in two steps, and removing one forgets it.** `rooms.create` saves the room and returns at once; clone, worktree folder (plus `.kernel/settings.toml` when missing), install, local files, hooks check and agent seating run behind it and report as `room.setup` events, so RoomSetup can be left. A failed step shows its error and the later steps still run, except when there is no checkout. Hooks are only checked, never written to `~/.claude` from here. Connect a repo and Open a folder fill a draft and hand back to New room, which is the only place a room is created. `NewRoomRequest` gained `cloneTo` and `initGit`, and the `newRoom` modal takes a `prefill`. Removing a room archives each open workspace for real, as the PNG says: sessions and scripts stop, its archive script runs, and its branch is kept when it has unpushed commits (D-064). Then Kernel deletes its record of the room (room, workspaces, chats, approvals, activity), because a workspace without its room would break History. Worktree folders go only when "Also delete the worktrees" is ticked; otherwise the archive leaves them, with their branches. If any workspace fails to archive, the error names it and the room stays. The folder, its history and `.claude/agents` are never touched. Until KERNEL-75 the confirm said "removes", and removal skipped the archive script and left setup scripts running. Hide sets `hidden`; the room stays on All rooms with a "Show in sidebar" link. KERNEL-20.

**D-029 Workspace transcript folds finished turns; focus mode is Cmd+backslash.** A turn with an ok result folds its thinking, tool calls and earlier messages into one "N tool calls, M messages" row, and shows the reply, the Changed chips and the duration. A turn still running, stopped or failed shows every item, so nothing is hidden while it matters. The expanded list reads each Edit or Write count from the changed files. Focus mode (sidebar swapped for the 64px rail, panels hidden) toggles with Cmd+backslash, because the canvas shows the rail but no shortcut. `workspaces.tree` lists tracked and unignored untracked files; `workspaces.readFile` refuses paths outside the worktree (symlinks included), files over 1 MB and binaries. Composer, ChatTabs and PrHeader exist as thin files so the screen renders; KERNEL-11, 12 and 15 replace them. KERNEL-10.

**D-030 Follow-ups wait in Kernel's queue, not in the running turn.** While a chat runs, `chats.send` holds the message in a per-chat queue (memory only) and pushes `chat.queue`. The composer shows each held message with Send now and remove, and clicking its text pulls it back into the box. When the turn's result arrives, the oldest one is sent; the next goes when that turn ends. Send now moves a message first and interrupts the turn. This replaces D-019's note that a mid-turn follow-up joins the running turn: it could not be edited or removed once sent. Stopping a chat clears its queue. A skill chip is sent as a `/name` text block with the text after it in the same block, because Claude Code only reads a slash command at the start of a block. Diff hunks sent to the agent become a file chip named `file:first-last` with the hunk inlined. Hunks split `git diff` per hunk; `mine` ones are HEAD to the baseline snapshot, `agent` ones everything since. Committing picked hunks resets the index, applies each patch with `git apply --cached` and commits. KERNEL-11.

**D-031 Approval cards read the Approval, and Edit file on a hire sends a note back.** A card in the chat is drawn from the `Approval` in the store, so answering in the chat, the Inbox or on the floor goes through `approvals.decide` and the others update from the push event. A pending approval for the workspace shows at the end of the chat even before the engine places an `approval` item. `Decision` has no field for edited file text, so Edit file on the hire card denies with a note for Rowan to revise the file instead of editing it in place. A failed turn shows an error card with Open terminal, Retry and Ask the agent to fix; a stopped turn shows the Interrupted marker and its time.

**D-032 The new workspace modal reads Linear from `LINEAR_API_KEY` until Settings > Integrations stores a token.** `services/linear.ts` takes the token from the environment, and the Issues tab says to connect Linear when there is none. KERNEL-26 replaces `linearToken()` with the stored one. The modal defaults to the engineers model, as NewWorkspace.png shows. Its plan mode starts from "Start new workspaces in plan mode" (D-073), not the Lead's setting. A picked PR or branch becomes the base the new branch is cut from, and a Linear issue puts its id in the branch name (`feat/{task}-{slug}`).

**D-033 The Inbox lists notifications, and pending approvals fill in until main's row arrives.** `services/notifications.ts` turns approval events and PR state changes (ready, cifail, changes) into stored `Notification` rows, one per approval (`n-approval-<id>`), and settles them on a decision, merge or close. `notifications.list` and `.read` are built on it. The renderer's inbox model (`screens/inbox/model.ts`) adds any pending approval that has no row yet, so the sidebar count, Home and the Inbox agree at once and never lag an approval. An approval row follows its live `Approval` for "needs you". macOS banners show only while no Kernel window has focus, and only for kinds switched on in Settings > Notifications, outside quiet hours; every item still lands in the Inbox. Updates is every item that does not need CJ. `mergedAt` is now set when a PR is first seen merged, for Home's Shipped recently. KERNEL-17.

**D-034 Kernel holds a PR state only while its own work runs, and reads GitHub for the rest.** Create PR sends `create-pr.md` and shows Creating. Fix checks, Address review and Resolve conflicts send their file and show Resolving. Both hold until the agent's chat has no turn running and nothing queued, so a poll can't flash the old state mid-turn. A turn that ends without a PR goes back to Create PR, and the renderer toasts it. Merging holds while `gh pr merge` runs. A workspace with no PR adopts only an open one, never an old merged or closed PR that reused the branch name. Every agent turn refreshes the PR, and the 45s poll covers open ones. `address-review.md` and `fix-checks.md` carry the unresolved review comments and the failing checks that GitHub reports. Review comments come from one `gh api graphql` call: one per review thread, plus the text of each reviewer's latest "changes requested" review. Merge refuses when "require green checks" is on and any check is not passed or skipped. A PR with no checks counts as green. Continue cuts a fresh branch from the base in the same worktree and keeps the chat (`feat/x` becomes `feat/x-2`, then `feat/x-3`). It refuses on current-branch workspaces, because it would switch the branch of CJ's own checkout. Notes the engine writes after a turn ended (merged, closed, checks failed) sit below that turn's duration line. Toasts are timed by the Toast component, which pauses on hover, so `actions.ui.toast` no longer sets a timer. KERNEL-15.

**D-035 The floor derives everything from the store, and a card's story comes from the newest activity event.** Tags, people and the header counts read `status` (agent.status events) and pending approvals only, never timers. A blocked or offline agent gets a floor card in Logs; its text comes from the agent's newest `agent.status`, `tool.failed`, `session.end` or `note` event: `data.detail` is the sentence under the title and `data.output` is the code box. Without them the card falls back to the agent's `saying` line. Seats follow `room.desks` when set (agents it does not list sit in the overflow strip), otherwise file order, with the lead always on the lead desk. The selected agent defaults to the first one that needs you, is blocked or is offline, then the lead. Tags draw no ring for planning or walking, as on the canvas (KERNEL-83).

**D-036 The briefing sequence is a stage read from events, and the Lead walks it.** `screens/floor/sequence.ts` derives the stage from the store in this order: a pending plan approval from the Lead is plan; the newest plan approved while the Lead is still running is handoff, until every plan step that names an agent has a workspace and the Lead has logged something other than a line it said since the last `workspace.created` (plan-mode plans have no such steps and end with the Lead's turn); a `brief` event (now logged by `rooms.brief`) that the Lead is running on is sent, then planning once the Lead acts on it in plan mode (a plan sent back or expired reopens that round, and it ends when the Lead finishes its turn); any pending approval or needs status is needs; a room workspace with PR state `ready` is review; anyone busy is working. `ui.stage` (fixtures) replaces the stage, and the stage names are the canvas `%%STAGE%%` values. The Lead walks along the `wp()` waypoints: to the task wall while planning, to each assignee's desk in the order `create_workspace` ran (the `workspace.created` events the Lead logs), and back to the desk otherwise. Moves queue one waypoint per 950 ms, each event walks once, and nobody teleports. Reduced motion (system or Settings > Appearance) and Settings > Experimental walking off make each move a jump, and the walk jumps to its end when the window comes back after a second or more away. Someone away from the desk reads "walking" on the tag, the card and the header count. The speech bubble is the newest `agent.say` from any agent, not only the Lead, since the stage began, shown in sent, planning, handoff and review, and those lines stay out of Logs. Request changes on a plan sends "Please revise the plan." when the note is empty, and Deny on a permission sends "Denied in Kernel." Extending D-035, when nobody was clicked and nobody is loud, the card follows the hand-off: the agent just handed work during handoff, the first assignee while working. The review card names the reviewer only when the plan gave a reviewer agent a task under the same parent, since a ready PR alone says nothing about who reviewed it. D-040 adds talks and hires to the walks. KERNEL-23. Updated in KERNEL-83.

**D-037 Restore recreates the worktree from the branch, and a deleted branch cannot come back.** `workspaces.restore` runs `git worktree add` on the saved branch at the saved path, falling back to `origin/<branch>`, then copies local files and marks the workspace ready. Chats were never deleted, so they reopen with it. If archive deleted the branch and no remote copy exists, restore fails with a plain message and the workspace stays in History. Sign out and Switch account both sign out through the CLI and open the checks screen, where signing in lives (KERNEL-28 builds the sign in button).

**D-038 On the board, a pending approval is Needs you, and Blocked is only for failures.** KERNEL-18 words a pending approval as blocked, but Board.png tags it Needs you and keeps Blocked for failures. A task is Blocked on a failed setup, failing checks, a merge conflict or requested changes. Outside-session tasks are keyed by `team_name` or `session_id` plus the hook's `task_id`, because Claude Code numbers tasks per task list.

**D-039 The Team lane writes agent files itself, and a draft is a template, not a model call.** Describe builds the file from the description (`draftAgent`): the role guessed from keywords picks tools, the model comes from the picker, and the review step is an editable text box, so New agent works offline and the same way every time. "Refine it in a chat with Rowan" sends the draft to the Lead, who proposes the final file with `hire_agent`. Saving a profile rewrites only the managed lines (`name`, `description`, `model`, `effort`, `tools`, `role`, `skills`) of the existing frontmatter and leaves every other line, such as a `hooks:` block, `color` or comments, as written; values with `: ` or `#` are quoted. The profile's model and effort apply to the chats a new workspace starts with (`modelFor` maps the `sonnet`, `opus`, `haiku` and `fable` aliases). The display name is the file stem, so it cannot be edited. Create joins the end of `room.desks` when the room sets one. Retire refuses the Lead, hands open workspaces to the Lead (or `handoffTo`), removes the desk and moves the file to `.claude/retired-agents` (D-003); a retired file replaces an older one with the same name, and Restore refuses when the name is taken. A debounced `fs.watch` on `.claude/agents` (armed on `.claude` until the folder exists) reloads the team and pushes `agents` when files change outside Kernel. The dialog says "retired-agents" where the PNG says "agents/retired", and the confirm button is ink, as drawn. KERNEL-19.

**D-040 Floor moments are read from events, and an overlap is a record the engine keeps.** `services/overlap.ts` compares each open workspace's changed files and line ranges after every turn and on merge or archive, raises one `Overlap` per shared file, and clears it when a workspace merges or archives or the agents stop sharing the file. "Let Rowan sort it" sends the Lead both sides and takes the card off the floor until the overlap clears; it logs a note, not a brief, so the briefing sequence does not restart. A talk is an `agent.talk` event (`message_agent`, Task delegation): the speaker stands at the listener's desk while the listener works and walks home on their next `turn.done`. A chat bubble needs CJ's `prompt` on a working agent with no newer brief. A hire walks in from the door only for 20 seconds after `agent.joined`, which the engine logs for any new agent file. The overlap log line carries links to both workspaces (acceptance criteria), which the PNG does not draw. The hire bubble says "Hi, I'm <name>, the <role>" because agent files have no first-person intro. KERNEL-24.

**D-041 One pty channel pair serves the big terminal and the bottom shell, and the first resize starts the process.** `terminal.write` and `terminal.resize` take a terminal chat id, or `shell:<workspaceId>` for the plain shell, so no channel was added. A big terminal opens the login shell in the worktree with `KERNEL_PORT` set and types `claude`, as Big terminal shows. Its hooks reach the floor through the installed http hooks, matched by cwd. Closing the tab, archiving the workspace or quitting kills the process. Cmd+W is taken from the default menu in the main process and handed to the page, so it closes the open tab instead of the window.

**D-042 A fork ends at an assistant message, and a fork of a fork can only copy the whole chat.** Chats fork with the SDK's `forkSession`. User items carry no SDK uuid, so a fork from a user message ends at the assistant message before it. Copied items get new ids, which no longer match the forked session's uuids, so branching a fork at an earlier message is refused with a message to fork the original.

**D-043 Checkpoints are hidden commits that carry their own metadata, and a revert restores files only.** After each turn `services/checkpoints.ts` writes the worktree into a throwaway index (a copy of the real one, so `git add -A` stays fast), commits that tree with Kernel's own identity and points `refs/kernel/checkpoints/<workspace>/<turn>` at it. The real index, HEAD and working tree never move. Title, chat, time and stat live in trailers on the checkpoint commit, so the drawer reads one `for-each-ref`, there is no table, and checkpoints survive restarts and archive. `refs/kernel/checkpoint-head/<workspace>` marks the current one. Turn 0 is taken right before the first turn ("start of chat"). A revert first commits the current state to `kernel/backup/<workspace>-<yyyymmdd-hhmmss>`, then writes or removes only the paths that differ, through `checkout-index` on a temp index. HEAD, the real index, ignored files and submodules are untouched, so an agent's commits stay and the reverted files show as working tree changes. Every checkpoint is taken after the workspace started, so a current-branch baseline is in all of them and survives any revert. Reverting is refused while an agent in the workspace is running. Rows are titled with the turn's prompt (acceptance criteria). The PNG's sample rows read like reply lines, and the fixture keeps them as drawn. KERNEL-13.

**D-044 Failure banners are derived from the store, one at a time, and every hold reuses the pause gate.** `screens/workspace/banners/model.ts` picks one banner from pushed state, in this order: signed out, offline, setup failed, weekly limit, 5-hour limit, the chat's own model limit, overloaded retry, context from 90%, hook server down. Signed out, setup failed and the weekly limit block the composer; the others let a message queue. Offline and signed out hold every room the way a pause holds one (`Sessions.holdAll`, by reason, so offline coming back does not release a sign-out): agents finish their step at the next PreToolUse and sends queue in the composer (D-030), not as a transcript note as the canvas draws it. A 5-hour or weekly rejection pauses every room with `pausedBy: 'limit'` and a timer at `resetsAt` (epoch seconds) lifts it and fires "Notify me". `api_retry` with a status pushes `retry`; one with a null status is a connection error and asks main's network check instead. Main checks the network with a DNS lookup of api.anthropic.com every 30s, every 5s while offline, and only when the app passes a probe, so tests never go offline. A failed setup holds the first prompt in the chat's queue (memory only, so a restart drops it) and Run again sends it once setup passes. Hooks down means Kernel's hook server stopped listening; the footer then says "Hooks down" where the PNG footer still says "Hooks live". Discard is `git reset --hard` plus `git clean -fd` after a checkpoint, refused on current-branch workspaces (it would take CJ's own changes) and while the agent runs. Archive never deletes a branch that has commits the remote lacks, whatever the checkbox says. One workspace could fill three lines of a message, "ready to merge" read like a review verdict when it only means checks passed with no conflicts, and the 160-character reply excerpt cut links in half, so the Lead couldn't pass on a reviewer's details. `LeadUpdates` now keeps typed events (`TeamEventKind`) and collapses each workspace's events at send time: the last turn end, the PR opening, merge and close once each, and the last PR state event only while the PR is still in that state, so a failure fixed since says nothing. A batch with nothing left to say is dropped. The message starts "Team update from Kernel, not from the user.", then one block per workspace: "Kai (kai) · <task> · workspace <id>", a sentence per event in the order they happened, and the teammate's last reply quoted. A reply is cut near 1,500 characters, the replies in one message share 6,000, and `capText` cuts between words, so a link stays whole. A turn with a reply shows only the reply, which says the turn ended. A message carries at most 8 workspaces, the newest, shown in the order they happened, and counts the rest. The item carries the Team update card's data (`update`), its rows in the text's order. A passed-checks line says nothing about review yet: Kernel can't see a review it isn't linked to, and "no review is running" was false in the very case that started KERNEL-111, where Theo was already reviewing. The review link (KERNEL-130) adds the review status and folds a reviewer's turn into its verdict. A PR change for a workspace with events waiting restarts its 5-second wait, so a PR that settles is checked again before the message goes. Every event still starts a Lead turn; the wake policy comes next. Amends D-070 and D-101. KERNEL-117.

**D-116 A teammate update wakes the Lead only when something needs it.** Every teammate event started an Opus turn in Rowan's chat, including a PR opening or checks passing while Theo was already reviewing, and Rowan answered with filler such as "Theo is already reviewing PR #108. I'll wait for his verdict." `LeadUpdates` now decides at send time, against each workspace as it is then, which events need the Lead, and posts only when one does. The rest wait and go out with the next update that does. An error, a crashed session, a failed setup and a review verdict always wake the Lead, except an error in a turn the user started in the teammate's own chat. Failed checks, requested changes and conflicts wake it while the PR is still in that state, and a close while the PR is still closed. A PR that passed checks wakes it in three cases: every current review approved it ("tell the user it is ready to merge"), the team has a reviewer and no review is linked or running ("hand it over"), or the team has no reviewer ("tell the user it is ready for them to review"). That last case isn't in KERNEL-111's table, but without it a team with no reviewer never heard about finished work until everything merged. A merge wakes it only when it completes every task the chat handed off. Left out of that count: review workspaces, the Lead's own, work archived without merging, and the reviewer's own workspaces that never opened a PR, which are reviews nothing marks as such before KERNEL-130. A finished turn wakes it when Rowan or Kernel started the turn, the PR isn't being created or checked, and no newer PR event follows it. A PR opening and a setup that passed on retry never do. Work no Lead chat handed off, and a turn the user started in the teammate's own chat, never wake it but ride along. A draft PR never passes to ready, so a turn that opened one waits for the next event. While events wait, each workspace keeps only what could still be sent (its last turn end, last PR state, last setup and review events, and one opening, merge and close per PR), so a long wait can't grow the queue. The 8-workspace limit keeps workspaces that need the Lead first, then the newest, amending D-115, and the left-out line says "updates on N more workspaces". The failed-setup rule doesn't yet skip a failure `create_workspace` already reported; that lands with KERNEL-126. Each update ends with a "To do:" list Kernel writes, one line per event that woke the Lead, and the card marks those events. Until the review link (KERNEL-130), Kernel can't see a review it isn't linked to, so the review line says "unless a review of it is already running". Amends D-070. KERNEL-121.

**D-117 Stop on the Lead holds its teammate updates.** `LeadUpdates` delivered on any Lead turn end, interrupted or not, so pressing Stop on Rowan with an update waiting started a Kernel turn at once. An interrupted Lead turn now marks its chat stopped. The 5-second wait and the 45-second poll skip a stopped chat, and its next turn that isn't stopped, usually the user's next message, clears the mark and delivers what waited. Only the user stops a Lead turn, with Stop or Send now; Send now's own turn follows right after, so it doesn't hold anything for long. Only the stopped chat waits; the room's other Lead chats still get theirs. KERNEL-122.

**D-118 Teammate updates that wait for the Lead are saved.** D-070 said nothing is lost, but the waiting updates lived in memory, so quitting Kernel while Rowan was busy, or while a batch waited out its 5 seconds, dropped them. `LeadUpdates` now saves what waits, its event counter and the chats Stop marked (D-117) under the meta key `leadUpdates` after every change, and loads them when Kernel starts. Loading drops events for workspaces that are gone or are the Lead's own, and stop marks of chats that are closed or gone. Loading itself sends nothing: the next event, the next Lead turn end or the 45-second PR poll delivers what waited, so the first poll after launch can deliver an update that needs the Lead. A saved value Kernel can't read is dropped instead of stopping Kernel from starting. Amends D-070. KERNEL-123.

**D-119 A teammate session that dies mid-turn is a teammate update.** A session whose process exits on its own went offline in the logs, but its turn never ended, so `LeadUpdates` never heard and the Lead thought the teammate was still working. `onExit` now says whether a turn was running, and a teammate's mid-turn exit is a `crash` event that wakes the Lead, for work a Lead chat handed off, with what Claude Code said and "the user can restart it from the workspace". Kernel never restarts a session on its own, so it doesn't claim to. An idle process that goes away harms nothing, since the next message starts a new one, so it isn't reported. A Lead chat whose own session died mid-turn takes no more of Kernel's messages until the user sends one, restarts it, or a turn there succeeds (as after Retry on an update), so updates can't loop a broken session, for example after a sign-out. KERNEL-124.
